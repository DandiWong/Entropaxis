# 项目结构与整理执行套件 (Project Layout)

归属判据、决策落盘规则与 Dashboard 边界的唯一真源是 [`../../rules/项目组织.md`](../../rules/项目组织.md)；文件命名与落盘打开规范的唯一真源是 [`../../rules/文件交付.md`](../../rules/文件交付.md)。本 Skill 只承载结构清单与归位动作，不重复判据。

---

## 1. 事务胶囊目录树

```text
YYYYMMDD_主题/
├── 01_调研.md          # [探索者] 业务背景、竞品分析、法规文献查新（为什么做）
├── 02_方案.md          # [设计师] 系统架构、业务流程、非目标与决策取舍（做什么）
├── 03_设计.md / 原型/  # [设计师] 视觉图样、交互原型 HTML、设计规范（长什么样）
├── 04_Spec_<ID>.md     # [构建者] 技术规格、数据模型、接口契约与 TDD 设计（怎么实现）
├── 05_审计报告.md      # [审查者] 安全审查、合规门禁、红队对抗与坏味道审查（有何风险）
└── 07_验收报告.md      # [守门者] 真实执行证据、测试通过证明与量化指标（交付凭据）
```

细粒度变更记录（改了什么）链接库根 `Changelog.md` 真源，不在胶囊内另写 `06_Changelog.md` 副本。

按需创建，不为凑齐结构建空文件（纯业务调研仅出 `01`、`02`；非代码工程不设 `04_Spec`）。

**上图是阶段文件的完整形态参照，不是初始化清单。** 子目录（`00_原始素材/`、`assets/`、`prototypes/` 等）一律按《项目组织》懒创建铁律，**只在确有材料落盘那一刻创建**，不随容器预建；脚手架 `python3 .system/tools/init_capsule.py` 同样只生成阶段文件与 `capsule.yaml`，不预建任何空目录。

## 2. 通用项目分层结构（4 域 + 2 底册 + RawInput + Archive）

适用于兼具「业务资料管理 + 会议调研论证 + 软件研发交付 + 运营成效沉淀」的综合项目。

```text
<工作区根目录>/
├── 00_知识库/                         # ════════【工作区共享知识域】════════
│   │                                  # 跨项目复用的权威规范、行业标准、文献、手册、说明书
│   │                                  # 只读事实源；项目内通过 _知识库/index.md 引用，不复制
│   └── <领域名称>/                    # 按学科/业务域组织
│
<项目根目录>/
├── CLAUDE.md                          # [Claude Code 入口] 导入 @AGENTS.md
├── AGENTS.md                          # [Agent 控制面] 本项目路由、硬约束与 RawInput 整理规则
├── README.md                          # [总纲] 项目定位、目标、里程碑与目录全景导航（只导航，不存正文）
├── RawInput/                          # [暂存投递箱] 随手丢入的原始文件（触发"整理"后自动归位并清空）
│   └── .gitkeep
│
├── 01_项目管理/                       # ════════【业务与管理域 · 输入与过程】════════
│   ├── DECISIONS.md                   # [决策持久化] 跨会话唯一事实（已拍板生效的决策、基线与口径）
│   ├── 01_项目资料/                   # 项目专属原件：方案、报告、参考数据集（只读事实源）
│   │                                  # 跨项目通用规范/文献 → 工作区 00_知识库/，不放此处
│   ├── 02_调研评估/                   # 行业调研、PoC 评估、迭代评测、方案规划（按 YYYYMMDD_事件名/ 组织）
│   │                                  # 含评估过程会议纪要；判断标准：产出是"认知"而非正式决策
│   ├── 03_决策记录/                   # 正式决策节点：立项批准、方案选定、上线放行、里程碑评审决议
│   │                                  # 判断标准：有明确决策结论（可含会议纪要、邮件批复、审批截图）
│   └── 04_价值回收/                   # 立项文件、战略汇报 PPT、高管演示看板、成效推介、业务 ROI 测算
│
├── 02_产品设计/                       # ════════【产品定义域 · 需求与体验】════════
│   ├── 01_需求清单/                   # 业务功能列表、优先级跟进表、用户故事
│   ├── 02_原型Demo/                   # 交互原型、静态/动态 UI Mockup、体验演示包
│   └── 03_设计规范/                   # PRD、设计系统与交互规则定义
│
├── 03_工程研发/                       # ════════【工程实现域 · 技术与代码】════════
│   └── <app-repo-name>/               # 独立 Git 代码仓库
│       ├── PRODUCT.md                 # 产品边界定义
│       ├── src/ / server/             # 源代码
│       ├── test/ / tests/             # 测试套件
│       └── docs/                      # 工程工作流真源与按事项组织的工程证据
│           ├── Tasks.md               # 应用实现任务与规划真源
│           ├── Changelog.md           # 研发变更履历
│           ├── Benchmark.md           # 量化成效基准
│           ├── ReleaseNote.md         # 工程版本发版说明
│           └── YYYYMMDD_主题/          # 同一工程事项的规格、审计与评估报告
│
├── 04_运营增长/                       # ════════【交付与运营域 · 推广与赋能】════════

└── Archive/                           # [废弃归档域] 已被新方案替代的历史文件与过期备份（注明替代路径）
```

## 3. `RawInput/` 整理机制

**定位**：无负担的暂存投递区，用于临时放置聊天/邮件附件、会议转写、截图、未命名草稿。

**触发**：用户说「整理」「整理 RawInput」「归档收件箱」。

**归位映射**：

| 材料类型 | 去向 |
|---|---|
| 官方凭据/合同/底册/项目专属输入资料 | `01_项目管理/01_项目资料/` 对应子目录（规范重命名后） |
| 权威规范/文献/手册 | 工作区 `00_知识库/` |
| 调研/评估/方案 | `01_项目管理/02_调研评估/` |
| 有明确决策结论的会议纪要/批复 | `01_项目管理/03_决策记录/`，并提炼已拍板决策写入 `DECISIONS.md` |
| 立项文件/汇报 PPT/成效推介 | `01_项目管理/04_价值回收/` |
| 需求清单/原型/PRD 设计 | `02_产品设计/` 对应子目录 |
| 代码/技术 Spec/系统实现 | `03_工程研发/<app>/` 或其 `docs/` |
| 交付样稿/培训材料/宣发/运营数据 | `04_运营增长/` 对应子目录 |
| 历史作废版本 | `Archive/`，并注明替代来源 |

**收尾**：清空 `RawInput/`（保留 `.gitkeep`），向用户输出归档清单。

## 4. 代码工程 `docs/` 事件容器布局

`docs/` 只保存与实现直接绑定、必须随代码演进的工程证据；每个事项一个日期主题容器：

```text
03_工程研发/<app-repo-name>/docs/
├── README.md                                      # 文档导航、真源层级和当前入口
├── .board.json                                    # 跨系统绑定（启用时）
└── YYYYMMDD_主题/
    ├── Tech-19_主题方案.md                         # 实施规格（独立 Spec 新命名：<ID>_中文主题.md）
    ├── Audit_Tech-19_主题方案审计.md               # 审计或评审
    └── Report_Tech-19_主题评估报告.md              # 评估报告
```

- 容器日期取工程事项首次形成或正式立项日期；主题使用简洁中文名。三个文件按实际产出创建。
- Spec 命名见《文件交付》§2.3（`<ID>_中文主题.md`，既有 `Spec_<ID>_主题方案.md` 只读兼容）；`Audit_` / `Report_` 分别标识审计评审、评估报告；同一事项必须使用相同 Task ID 与主题。
- 产品、视觉、调研、项目计划、普通报告及归档材料分别回归项目根的 `01_项目管理/`、`02_产品设计/`、`04_运营增长/` 或 `Archive/`，不在代码仓库 `docs/` 重复保存。
- `PRODUCT.md`（存在时）定义最高层产品边界；`docs/Tasks.md` 是应用实现任务真源；`docs/README.md` 只导航，不复制正文。
- `docs/README.md` 与 `.board.json` 留根。通用项目不创建根级 `docs/`；需要时在 `03_工程研发/<app-repo-name>/` 运行 `init_app.py` 创建最小布局。

## 5. `README.md` 总纲内容规范

- 项目身份、用途、目标和相关人员；
- 4 域目录分层结构全景导航；
- 按日期排列的关键里程碑与事件索引；
- 当前有效状态入口、最新产物与下一关键事件。

事件完成后追加或更新一行，不在总览中复制详细正文。
