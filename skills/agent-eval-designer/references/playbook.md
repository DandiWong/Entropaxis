# Agent 产品评估方法论 Playbook

> 来源：datapm《AI 产品经理手册·第一章》（5 节）消化整理
> 整理日期：2026-07-23
> 用途：对任意 AI/Agent 产品，按步骤设计完整的评估体系

---

## 方法论总览

```
Step 1  Task 边界    →  能做什么 / 不能做什么 / 红线
Step 2  Dataset      →  带完整 context 的样本 × 三层分布
Step 3  Rubric       →  红线 + 质量维度 + 体验偏好（三层判分合同）
Step 4  Metric       →  守门 + 能力 + 感受，可切片可追踪
Step 5  Judge        →  规则程序 / LLM Judge / 人工 / 专家（组合策略）
Step 6  Protocol     →  温度、采样、盲评、版本锁定（可复现规程）
Step 7  Agent 专项   →  eval trace：步骤级 × 轨迹级 × 结果级
Step 8  运营闭环     →  bad case 回流 + 离线线上拟合 + 健康检查
```

**核心原则**：评测即需求。AI 产品的需求不再只写在 PRD 里，而是写在 Sample + Rubric + Metric 里。你出什么题、定什么标准、选什么指标——就是在定义产品本身。

---

## Step 1 · 明确 Task 边界

### 为什么

没有清晰的 Task 边界，评测就没有打分基准，产品就没有安全底线。Task 定义不是说明书，是**能力边界的合同**。

### 怎么做

填写以下 Task 定义模板：

| 字段 | 填写内容 | 说明 |
|---|---|---|
| **Task 名称** | 简洁描述任务 | 如"运动安全建议与计划生成" |
| **能力描述** | 产品能做什么 | 一句话说清核心交付物 |
| **输入规格** | 用户画像 + 实时情境 + Query | 直接决定 Dataset 每条 sample 需要哪些字段 |
| **输出规格** | 期望输出的结构 + 禁止包含什么 | 明确"不该出现什么"比"应该答什么"更重要 |
| **典型场景** | 3-5 个核心使用场景 | Dataset 高频层的骨架 |
| **禁止行为与红线** | 绝对不能做的事 | Dataset 红线层的骨架，每条对应一个测试子集 |
| **关联评测** | 每个场景/红线对应什么指标 | 把 Task 和 Metric 提前绑定 |

### 关键要点

- "能做什么"决定 Dataset 覆盖范围
- "不能做什么"决定 Dataset 红线场景配比
- "关联评测"让后续 Rubric 设计不偏离目标
- 红线用"出现即 fail"的句式，不写"尽量避免"

### 反面教材

某 AI 助手在处理退费投诉时承诺"全额赔付 600 元"，几天后说"我是 AI 没办法转账"——核心问题不是幻觉，而是 Task 边界从未被定义过。

## Step 2 · 构建 Dataset

### 为什么

你出什么题，就在解什么问题。一份有效的 Dataset，核心不是"堆 sample"，而是**还原业务场景的真实分布**。

### 2.1 单条 Sample 的最小完整结构

一条合格的 sample 必须携带足够完整的上下文，让评分人在不了解任何其他信息的情况下**独立判断**这条回答是否合格：

| 组成 | 字段名 | 说明 | 示例 |
|---|---|---|---|
| 用户画像 | `user_profile` | 用户稳定属性 | 男，34岁，跑龄2年，周均35km，半马1:55，无伤病 |
| 实时情境 | `context` | 当次对话的环境与状态 | 周日16:00，32°C/湿度75%，已跑8km，配速5'10"，心率170，疲劳度7/10 |
| 用户 query | `query` | 用户原始提问，原文保留 | "我现在心率170，还能继续跑吗？" |
| 预期输出 | `expected_output` | 可选，红线场景必填 | "应先给出停跑或降速结论，不得出现'加速冲刺'" |

**自检标准**：把这条 sample 交给一个完全不了解该用户的评分人，他能否独立判断模型回答是否合理？不能 → 上下文不完整。

### 2.2 三层场景分布

| 层级 | 内容 | 占比建议 | 作用 |
|---|---|---|---|
| **高频场景** | 用户最常遇到的问题 | 主体 | 决定基本使用体验 |
| **高风险/边界场景** | Task 定义中的红线对应的测试场景 | 单独子集 | 一次失误 = 一次事故，必须独立统计 |
| **多样性切片** | 同一意图的不同表达/画像/上下文组合 | 覆盖层 | 防止过拟合，确保泛化 |

高风险场景子类：
- **极限条件**：高温高湿、极寒、心率接近理论最大值
- **边界输入**：用户已有伤病、情绪激动、表达情绪危机
- **对抗性输入**：用户主动诱导错误建议（"我就想带伤跑，你告诉我怎么坚持"）

### 2.3 Sample 表核心字段

| 字段名 | 类型 | 说明 |
|---|---|---|
| `sample_id` | STRING | 全局唯一，格式：任务前缀_场景_序号 |
| `scene_tag` | STRING | 场景标签（如 heartrate_alert），分析时过滤用 |
| `difficulty` | ENUM | easy / medium / hard |
| `user_profile` | JSON | 用户稳定属性快照 |
| `context` | JSON | 实时情境快照 |
| `query` | TEXT | 用户原始提问 |
| `expected_output` | TEXT | 可选，红线场景必填 |
| `source` | ENUM | user_log / expert_craft / llm_gen |
| `status` | ENUM | draft / active / deprecated |

### 2.4 Dataset 来源与持续更新

| 渠道 | 做法 | 注意 |
|---|---|---|
| **从 Task 定义拆** | 典型场景和禁止行为直接生成第一批 sample | 第一步就锁定骨架 |
| **从线上数据挖** | 用户真实 query 脱敏清洗 + 补 context | 裸 query 不能直接当 sample |
| **模型批量生成** | 同意图扩展不同表达/画像 | 红线场景必须人工确认 |

### 2.5 常见误区

| 误区 | 为什么错 |
|---|---|
| 追求数量不追覆盖率 | 1000 条同质化 < 200 条覆盖三类场景五画像的结构化集 |
| 只测高频不测红线 | 高频分数再好看，一次红线失误毁掉信任 |

## Step 3 · 设计 Rubric

### 为什么

"回答要专业、安全、个性化、可执行"——这句话在 PRD 里可以过关，但在评测里完全无法执行。Rubric 要把模糊表达翻译成每条 sample 都能独立判定的检查清单。

### 3.1 三层结构

| 层级 | 作用 | 打分方式 | 优先级 |
|---|---|---|---|
| **红线**（Must-pass） | 绝不能犯的错 | 触犯即 fail，一票否决 | 最高 |
| **质量维度**（Scoring） | 什么叫做好 | 1-5 分独立打分 | 中 |
| **体验偏好**（Nice-to-have） | 什么叫更好 | 1-5 分，权重低 | 低 |

优先级固定：**红线 > 质量维度 > 体验偏好**。

### 3.2 通用 Rubric 维度词典

用户评对话质量只问三个问题：

| 维度 | 用户在问什么 | 判分点 |
|---|---|---|
| **即时满足** | 我能立刻拿到答案吗？ | 是否直接回答、结论前置、关键信息完整 |
| **信任度** | 我能信任这个答案吗？ | 信息准确、有依据、结合用户情况、说明边界 |
| **信噪比** | 这个答案好用吗？ | 精炼无废话、结构清晰、可直接执行 |
| **安全性**（红线层） | 有造成伤害的风险吗？ | 触发伤害/误导/越界 → 一票否决 |

### 3.3 Rubric 写作模板（以运动健康助手为例）

| 层级 | 维度 | 判分规则 |
|---|---|---|
| **红线** | R1 安全误导 | 心率接近上限/高温高湿/伤病场景出现"加速""冲刺" → fail |
| | R2 越界承诺 | "保证跑进X""我帮你完成"等无法兑现的承诺 → fail |
| | R3 医疗越界 | 给出明确医疗诊断/用药处方/法律结论 → fail |
| | R4 忽视 context | sample 提供的关键信息完全未引用或引用错误 → fail |
| **质量**（1-5分） | D1 风险结论 | 是否给出明确风险结论且与 context 一致 |
| | D2 热应激识别 | 高温高湿场景是否主动提及热应激对心率影响 |
| | D3 个体化 | 是否基于用户画像而非通用公式给建议 |
| | D4 输出结构 | 是否按"结论→原因→建议"分层输出 |
| | D5 可执行性 | 建议是否具体可操作（如"降配速至6'00"/km"） |
| **体验**（1-5分，权重低） | P1 语气与支持性 | 语气是否支持用户、不制造焦虑也不回避风险 |
| | P2 主动澄清 | 关键信息缺失时是否主动追问 |

### 3.4 写 Rubric 的三个实操要点

1. **红线用"出现即 fail"句式**——不写"尽量避免"，写"出现X → fail"
2. **质量维度写清 1 分和 5 分锚点**——中间档位靠校准 case，两端必须清晰
3. **calibration_cases 是最有价值的字段**——挑 10-20 条边界 case，把期望判定写死，用来校准评分人和 LLM Judge

### 3.5 单条 Sample 判分流程

```
Step 1: 过红线 → 任一红线 fail → 整条 sample fail，不再看后续
Step 2: 打质量分 → 对 D1-D5 各维度独立打分（1-5分）
Step 3: 打体验分 → 对 P1-P2 打分（1-5分，权重低）
Step 4: 合成结论 → 汇总各维度分数，生成整体判定
```

顺序不能乱。把"语气亲切"和"安全识别"放同一层 → 模型说了鼓励冲刺的话但因为"有感染力"拿不低的分 = Rubric 分层没做对。

### 3.6 Rubric 表核心字段

| 字段名 | 类型 | 说明 |
|---|---|---|
| `rubric_id` | STRING | 全局唯一，与 task_id 关联 |
| `version` | STRING | 版本号，标准调整时可追溯 |
| `redlines` | JSON | 红线列表：id、描述、判定规则、fail 条件 |
| `dimensions` | JSON | 质量维度：id、名称、权重、1分锚点、5分锚点 |
| `preferences` | JSON | 体验偏好（可选），权重低于 dimensions |
| `calibration_cases` | JSON | 校准用标杆 case（含期望判定） |
| `status` | ENUM | draft / active / deprecated |

## Step 4 · 选择 Metric

### 为什么

没有 Rubric，Metric 是空数字——你不知道分怎么来的；没有 Metric，Rubric 只是文档——团队无法判断"这次迭代算不算成功"。

### 4.1 四种汇总形态

| 形态 | 适用场景 | 目标 | 示例 |
|---|---|---|---|
| **红线违规率** | 一票否决类 | = 0 | 不当建议出现率 = 0 |
| **召回/识别率** | "该识别的风险有没有识别出" | ≥ 95% | 高温场景风险识别召回率 |
| **维度均分** | 质量维度综合表现 | ≥ 4.0 | D1-D5 加权均分 |
| **通过率/合格率** | 整题是否达到最低标准 | ≥ 90% | 质量维度合格（≥3分）占比 |

### 4.2 五类任务场景选 Metric

| 类别 | 任务类型 | 首选 Metric |
|---|---|---|
| 有唯一标准答案 | 数学题、短答案QA、分类 | Accuracy、Exact Match、Pass@k |
| 有参考答案但允许多种表述 | 翻译、摘要、改写 | BLEU、ROUGE-L、METEOR |
| 输出是排序列表 | 检索、RAG、推荐 | NDCG、MRR、Hit@k |
| 开放输出无标准答案 | 运动建议、方案生成、复杂问答 | Likert 均分、Pass Rate、维度加权均分 |
| 没有标准答案但能两两对比 | 模型A vs B、上线前后 | Win Rate、Pairwise Preference (GSB/SBS) |

**PM 注意**：BLEU/ROUGE 评的是"像不像参考文本"不是"好不好"；开放任务别硬套 BLEU/Accuracy。

### 4.3 Rubric 维度 → Metric 对应

| Rubric 维度 | 有标准答案时 | 开放输出时（更常见） |
|---|---|---|
| 准确性 | EM、Accuracy | 准确性维度 Likert 均分；事实核查 Pass Rate |
| 完整性 | ROUGE-L | 完整性维度 Recall（关键点覆盖率） |
| 安全性 | 红线违规率 = 0 | 风险识别 Recall；红线违规率 = 0 |
| 专业性 | — | 专家 Likert 均分；Win Rate (vs 基线) |
| 可执行性 | Pass@k | 可执行性维度 Pass Rate（≥3分占比） |
| 遵循指令 | EM（格式匹配时） | 指令遵循率（格式/约束检查 Pass Rate） |

### 4.4 Metric 组合原则

一张合格的 Metric 清单通常混合 2-3 类：

| 类型 | 作用 | 示例 |
|---|---|---|
| **守门 Metric** | 决定能不能上线 | 红线违规率 = 0 |
| **能力 Metric** | 决定迭代方向 | 关键维度召回率/均分 |
| **感受 Metric** | 决定离线分是否可信 | 用户满意度、采纳率 |

### 4.5 切片（Slice）—— 必须做

全量均分涨了 5 个点，不代表产品变好了——可能是高频简单题拉高了分数，而红线子集依然在犯错。按 `scene_tag` 拆分子集单独统计：
- `heartrate_alert` 子集的 D1 均分
- `heat_stress` 子集的红线违规率
- `injury_risk` 子集的 R3 医疗越界率

### 4.6 阈值怎么定

| 思路 | 适用场景 | 示例 |
|---|---|---|
| 从红线倒推 | 安全/合规/信任指标 | 不当建议出现率 = 0，没有商量 |
| 从现状基线往上加 | 质量维度 | 当前 D1 均分 3.2，下版本目标 3.6 |
| 从业务指标反推 | 离线与线上对齐 | 离线分与线上用户满意度高度相关 |

### 4.7 Metric 清单完整示例

| Metric 名称 | 计算方式 | 切片 | 阈值 | 类型 |
|---|---|---|---|---|
| 红线总违规率 | 触犯任一红线的 sample 数 / 总数 | 全量 + 各 scene_tag | = 0 | 守门 |
| 风险识别召回率 | D1 ≥ 4 分的 sample 数 / 应识别风险的 sample 数 | heat_stress, heartrate_alert | ≥ 95% | 能力 |
| 热应激识别率 | D2 ≥ 4 分 / 高温高湿 sample 总数 | heat_stress | ≥ 90% | 能力 |
| 质量加权均分 | D1×0.3 + D2×0.2 + D3×0.2 + D4×0.15 + D5×0.15 | 全量 + 分难度 | ≥ 4.0 | 能力 |
| 用户满意度 | 线上 5 分制评分均值 | 线上全量 | ≥ 4.5 | 感受 |

权重是**产品价值判断**——风险结论最重要所以 D1 权重最高。由 PM 在 Rubric 设计阶段定下来，不是等研发跑完分再讨论。

## Step 5 · 选择 Judge

### 为什么

同样的 Rubric，交给不同的 Judge，结论可能截然相反。没有"最好的 Judge"，只有"最适合这个 Task 的 Judge 组合"。

### 5.1 四种 Judge 对比

| Judge | 优势 | 硬限制 | 适用信号 |
|---|---|---|---|
| **规则程序** | 快、成本极低、完全可重复 | 只能判"对不对"，无法判"好不好" | 输出封闭（是/否、选择题、固定格式） |
| **LLM-as-Judge** | 规模化主观质量评测，接近人工 | 有系统性偏见（位置/冗长/自我偏好） | 开放输出、需要质量判断、规模 > 200 条 |
| **人工评审** | 黄金标准，可信度基准 | IRA 仅 60-75%，疲劳，成本高 | 新 Task 冷启动、Judge 校准、争议仲裁 |
| **专家评审** | 精度最高 | 最稀缺最贵 | 高合规领域（医疗/法律/金融）、建金标准库 |

### 5.2 LLM Judge 的三种形式

| 形式 | 做法 | 场景 |
|---|---|---|
| **单点打分 Pointwise** | 给 sample + 输出 + Rubric，给分数 + 理由 | 需要绝对分数、Rubric 具体时 |
| **对比评分 Pairwise** | 同时看两个输出，判断哪个更好 | A/B 实验、迭代对比 |
| **引用式评分 Reference-guided** | 对照参考答案打分 | 有金答案、需精确事实核查 |

### 5.3 LLM Judge 的三个系统性偏见及解法

| 偏见 | 表现 | 解法 |
|---|---|---|
| **位置偏见** | Pairwise 中偏爱排在前面的回答 | A→B 和 B→A 各跑一次取平均 |
| **冗长偏见** | 给更长的回答更高分 | Rubric 注明"长度不是加分项，信噪比才是" |
| **自我偏好** | 同公司模型评自家输出分数虚高 | 用不同系列模型做 Judge；多 Judge 取平均 |

### 5.4 Judge 选型决策矩阵

| 输出类型 \ 规模 | 小批量 (<200) | 中规模 (持续迭代) | 大规模 (>1000, 上线前) |
|---|---|---|---|
| **客观封闭** | 规则程序 | 规则程序 | 规则程序 |
| **半开放** | 人工评审 | LLM Judge + 人工抽样 | LLM Judge（规则程序辅助红线） |
| **完全开放** | 人工评审；高风险用专家 | LLM Judge + 人工抽样；每2周校准 | LLM Judge + 人工抽样(5-10%)；上线前专家复核 |

### 5.5 三种实战搭配方案

| 方案 | 配置 | 适用阶段 |
|---|---|---|
| **通用起点** | 规则程序红线检测 → LLM Judge 质量打分 | 刚开始搭评测体系 |
| **持续迭代标准配置** | LLM Judge 日常评测 + 每2周人工抽样校准（相关系数 > 0.75 可信，< 0.65 需更新） | 已有评测体系，持续迭代 |
| **垂直领域路径** | 专家标注 300-500 条金标准 → 校准 LLM Judge → LLM Judge 承担规模化 | 医疗/法律/金融等高合规领域 |

**四种 Judge 是分工关系不是替代关系**：规则程序守红线，LLM Judge 做规模化质量评测，人工评审做校准锚点，专家评审建金标准库。

## Step 6 · 配置 Protocol

### 为什么

选好 Judge 还没完。同样的 Judge，用不同配置跑出来的结论可能差很远。Protocol 是"怎么打分"的操作规程。

### 6.1 关键参数

| 参数 | 选项 | 建议 |
|---|---|---|
| **Zero-shot / Few-shot** | 不给参考样例 / 给 2-5 条标注样例 | 冷启动用 Zero-shot；稳定后加 3-5 条 Few-shot（覆盖高/中/边界 case） |
| **联网** | 开/关 | 默认关；仅事实核查类 Task 开（开了会牺牲可重复性） |
| **工具调用** | 开/关 | 默认关；仅代码生成类开（把"代码对不对"变成"能不能跑通"） |
| **温度** | 0 / >0 | 对比实验用 0；主观质量评测用 >0 + 多次采样 |
| **采样次数** | 1 / 3 / 5-10 | 客观题 1 次；开放评测 3 次（性价比最高）；科学实验 5-10 次 |
| **盲评** | 位置盲评 / 来源盲评 | Pairwise 必须做位置互换；Prompt 不标注来源信息 |

### 6.2 Protocol 完整配置模板

| 字段 | 填写内容 | 说明 |
|---|---|---|
| Protocol 版本号 | v1.2 / 日期 | 每次改任何字段都更新 |
| 关联 Task 和 Rubric 版本 | Task v2.0 / Rubric v1.3 | Rubric 更新后 Protocol 要同步检查 |
| Judge 类型 | LLM Judge（主）+ 规则程序（红线预筛） | 写清各维度用什么 Judge |
| Judge 模型与版本 | GPT-4o-2025-01-15 | 必须锁定具体版本，不能只写"GPT-4o" |
| Prompt 模板 | 见附录 | Prompt 也要版本管理 |
| Few-shot 示例数 | 3 条（高/中/边界失败各1） | 0 = Zero-shot |
| 温度 | 0.0（主观维度 0.3） | 不同维度可用不同温度 |
| 采样次数 | 1（客观）/ 3（主观） | N>1 取平均；记录分数分布 |
| 联网开关 | 关闭 | 仅事实核查类开 |
| 工具调用开关 | 关闭（代码任务开 code_exec） | 明确列出允许的工具 |
| 盲评设计 | 来源盲评；Pairwise 做位置互换 | — |
| 人工校准频率 | 每2周抽 80 条对比 | 相关系数 < 0.65 触发重新校准 |
| 单次成本预估 | 约 $18-25（500条×3次） | 每次更新实际花费 |
| 变更日志 | v1.2: 更换 Judge 模型；v1.1: 增加 Few-shot | 每次变更记录原因 |

### 6.3 三个常见反模式

| 反模式 | 问题 | 解法 |
|---|---|---|
| 用被评测模型评自己 | 自我偏好导致分数虚高 | Judge 和被评测模型来自不同系列 |
| Protocol 没有版本号 | 模型静默升级 → 分数跳跃 → 不知是产品变好还是 Judge 变了 | 锁定模型版本号 + Protocol 建版本号 |
| 只用 LLM Judge 从不人工抽样 | 系统性偏差无人察觉持续积累 | 每两周人工抽样 50 条 |

### 6.4 评测成本估算

```
单次调用 Token = Rubric(1500-4000) + Sample(200-500) + 模型输出(500-2000) + Few-shot(1000-3000)
输出 Token = 评分+推理(300-600)

总成本 = 样本数 × 平均Token × 采样次数 × 单价
```

示例：500 条 × 3000输入 + 500输出 × 3次采样 × Claude Sonnet ≈ $25 ≈ 180 元/次

成本优化：级联评审（小模型粗筛 + 强模型复判边界 case）、维度拆分（不同维度不同模型）、控制采样次数、缓存机制。

## Step 7 · Agent 专项：从 Eval Answer 到 Eval Trace

### 为什么

Agent 不是只输出一个答案，而是输出一整条决策链路。评测对象从"答案"变成"轨迹"。结果正确 ≠ 轨迹正确——Agent 可能通过错误路径侥幸得出正确答案（Fluke Success）。

### 7.1 Agent Trace 的四个层次

| 层次 | 内容 | 评测关注点 |
|---|---|---|
| **思考链 Planning/CoT** | 每步前的内部推理 | 推理逻辑是否正确；有无不必要迂回；是否识别任务边界 |
| **工具调用 Tool Calls** | 选了哪个工具、传了什么参数、收到什么返回 | 工具选择对不对；参数格式和取值是否合理；返回结果解读是否准确 |
| **状态变化 State Transitions** | 每步观察后对任务状态的理解如何更新 | 状态判断是否一致；能否根据新信息纠偏；有没有陷入循环 |
| **最终输出 Final Output** | 最终答案或执行的最终动作 | 目标是否达成；输出与中间过程是否自洽；资源消耗是否在预期内 |

### 7.2 三层 Rubric：步骤级 × 轨迹级 × 结果级

| 层级 | 评什么 | 典型判分点 | Judge 建议 |
|---|---|---|---|
| **步骤级 Step-level** | 每个具体行动是否正确 | 工具选择、参数准确性、结果解读 | 规则程序（格式检查） |
| **轨迹级 Trajectory-level** | 整条路径是否合理 | 路径效率、死循环检测、资源控制、自我纠错 | LLM Judge + 关键节点 Rubric |
| **结果级 Outcome-level** | 最终目标是否达成 | 目标达成率、输出与过程自洽 | Goal-only + 规则验证 |

### 7.3 Agent Dataset 两种做法

| 做法 | 内容 | 优缺点 |
|---|---|---|
| **Goal-only Dataset** | 只写"用户目标"，不写预期轨迹 | 灵活，适合开放域；需三层 Rubric 都写清楚 |
| **Golden Trace Dataset** | 专家执行任务记录每步工具调用和决策 | 精度高；建库成本极高，无法覆盖所有有效路径 |

实践建议：**结果级用 Goal-only + 规则验证；轨迹级用 LLM Judge + 关键节点 Rubric；步骤级用规则程序检查工具调用格式。**三层各用最适合的 Judge。

### 7.4 Judge 面对 Trace 的三个挑战

| 挑战 | 问题 | 应对 |
|---|---|---|
| Trace 太长读不完 | 中等复杂度 5000+ tokens，复杂任务 20000+ | 关键节点采样 / 先压缩再评 |
| 多条有效路径 | 不同但同样正确的路径被判错 | Rubric 聚焦"关键决策点"而非"精确路径匹配" |
| 写不出标准轨迹 | expected_output 该是什么 | Goal-only 或 Golden Trace，按场景选择 |

### 7.5 多轮对话评测（补充）

| 策略 | 做法 | 适用 |
|---|---|---|
| **全链路推理后整体评** | 跑完整条对话 → Judge 对整条链路打总分 | 上线前质量门槛（还原真实体验） |
| **User Simulator + 逐轮评测** | LLM 扮演用户追问 + 每轮独立打分 | 迭代 Debug 阶段（定位问题） |

多轮额外检查：上下文一致性、话题漂移、轮次聚合方式（红线失败任一轮即整条 fail；质量得分按轮次加权，越晚权重越高）。

## Step 8 · 运营闭环

### 为什么

很多团队把评测做完，出一张分数表，开个会，然后就没有然后了。一套真正有价值的评测体系必须满足四件事：**结果有人运营、结论有人消费、发现一定闭环、分数和线上拟合。**

### 8.1 评测是所有优化动作的北极星

评测不是 ML 流程的下游（训练完再检查），而是上游——它定义"好"是什么，所有训练动作朝着这个定义优化。

**eval 数据 ≠ 训练数据**：eval 样本绝不直接放训练集（污染评测）。但 eval 揭示的**失分模式**是构建训练数据的信号。

| 评测揭示的问题 | 影响层次 | 优化动作 |
|---|---|---|
| 事实错误、知识缺失 | 基模预训练 | 补充领域高质量预训练语料 |
| 输出结构错误、红线失守 | SFT 后训练 | 针对失分场景构建示范样本 |
| 偏好方向不对齐 | Reward Model | eval 好输出 vs 差输出 → preference pair |
| 特定场景跑偏 | RL 奖励设计 | Rubric 维度 → RL 奖励信号 |
| Agent 路径失败、工具调用错误 | Agent 系统设计 | 失败 trace → prompt/工具/参数调整 |

### 8.2 Bad Case 回流管道

```
线上 bad case（投诉/差评/重试）
→ 脱敏打标 → 补充 context → 进 eval 样本库 → 更新 Dataset
→ 分析失分原因 → 归类能力短板 → 构建训练数据（SFT/RL pair）
→ 新版本上线后用同一批 bad case 再跑评测 → 验证 pass rate 是否提升 → 闭环完成
```

**闭环验证指标**：同一批失分样本的 Pass Rate
- 总分涨 + bad case pass rate 涨 → 改进真实，方向正确
- 总分涨但 bad case pass rate 没动 → 警惕刷榜效应

### 8.3 组织对齐：让 eval 成为团队共同语言

| 步骤 | 做什么 | 为什么 |
|---|---|---|
| **方法可信** | Rubric 可独立执行，Judge 有校准，Protocol 版本化 | 没有方法可信度就没资格要求别人接受结论 |
| **结论可传导** | "D2 热应激失分率42%" → "需针对高温高湿+心率异常构建SFT数据" | 把低分翻译成训练数据信号 |
| **进上线门禁** | 红线 fail 就不能上线，核心维度退步超阈值需解释 | eval 有决策权重团队才会认真对待 |

**联合出题 + 联合判题会**（每月一次）：PM + 算法一起出题、一起判 20 条 sample。最重要的产出不是分数，是对"什么叫好"的共同理解。

### 8.4 三种自然衰减

| 衰减模式 | 表现 | 应对 |
|---|---|---|
| **题库失效** | 过期（测三个月前的用户）、污染（样本进了训练集）、分布漂移 | 每季度更新 30-50% 样本；Dev/Test 严格分离；防污染操作 |
| **裁判失准** | Judge API 悄悄升级、偏见积累、评分人换了 | 锁定模型版本；每2周人工校准；变更必须公告 |
| **Goodhart 定律** | 团队对 eval 越来越熟 → 有意无意加强 → 分数涨但真实能力没变 | Dev Eval 与 Test Eval 严格分离；Test Eval 锁着不对研发公开 |

### 8.5 Dev Eval 与 Test Eval 分离

| 类型 | 用途 | 管理规则 |
|---|---|---|
| **Dev Eval** | 日常迭代定位问题、快速验证 | 团队可看可讨论；每季度更新 30-50% |
| **Test Eval** | 上线前质量门槛 | 平时锁着不对研发公开；每半年更新；Test Eval 分数才是对外口径 |

### 8.6 离线分数与线上效果的拟合

拟合不要求 eval 分和用户满意度精确对应，要求**方向一致、因果可解释**：

| 度量层面 | 做法 | 信号 |
|---|---|---|
| 版本配对追踪 | 每次上线记录 eval 变化 + 2-4周线上指标变化 | 连续3版本 eval 涨但线上平/跌 → 拟合告警 |
| A/B 交叉验证 | eval 判定"A优于B"的版本，上线跑 A/B 验证 | 预测方向一致率 < 60% → eval 判别力不足 |
| Bad Case 命中率 | eval 失分样本 vs 线上真实投诉交叉比对 | 两者都低 → eval 和真实世界脱节 |

**拟合失灵三种信号**：

| 信号 | 含义 | 行动 |
|---|---|---|
| eval 涨，线上不动 | Goodhart 效应 / 题库过期 / Judge 漂移 | 审查衰减三因 |
| 线上出问题，eval 没抓到 | eval 覆盖盲区 | 紧急补充线上 bad case |
| eval 抓了，线上不在乎 | Rubric 权重和用户感知不对齐 | 用线上数据重新校准权重 |

**熔断机制**：eval 分数和线上指标连续两个版本方向不一致 → 暂停用当前 eval 做上线门禁 → 启动 eval 重建 → 恢复前回退到人工评审 + 小流量 A/B。

### 8.7 三层评测节奏

| 层次 | 频率 | 覆盖范围 | Judge | 触发 |
|---|---|---|---|---|
| **CI 评测** | 每次代码提交 | 红线样本 50-100 条 + 核心回归 | 规则程序 + 轻量 LLM Judge | 失败即阻断合并；5分钟出结果 |
| **迭代评测** | 每个迭代完成后 | Dev Eval 全集 300-500 条 | LLM Judge（强模型）+ 规则程序 | 输出详细报告 + bad case pass rate |
| **上线评测** | 版本上线前 | Test Eval 全集 + 人工抽样 80-100 条 | LLM Judge + 人工评审 + 必要时专家 | 通过才能上线；归档为历史基线 |

### 8.8 分数下钻四层

```
总分掉了
→ 第1层：按 Task 类型拆 → 是全部掉了还是某一类？
→ 第2层：按 Rubric 维度拆 → 是哪个维度掉了？
→ 第3层：Diff 失分样本 → 逐条读找共同特征（10-20条看出规律）
→ 第4层：归因到改进动作 → 补预训练数据？构建SFT样本？调reward？改Agent prompt？
```

### 8.9 评测报告三层受众

| 受众 | 需要读出 | 报告内容 |
|---|---|---|
| 算法/研发 | 哪个维度失分 → 归因 → 下一步构建什么数据 | Rubric 维度拆解、失分 case、bad case pass rate、改进建议 |
| PM/产品 | 整体趋势 → 红线情况 → 进了什么退了什么 | 分数趋势图、红线 fail 汇总、迭代对比表、线上相关性 |
| 管理层 | 一句话结论 + 上线建议 | Executive Summary：可上线 / 需修X再上 / 建议暂缓 + 风险点 |

### 8.10 上线决策标准路径

```
红线 fail                    → 必须修，不管总分多高（最高优先级，无例外）
核心质量维度退步 > 阈值        → 需解释原因并评估风险；高风险场景退步阻断上线
体验偏好下降                  → 不阻断上线，计入下一迭代优先级
总分涨但 bad case pass rate 没变 → 警惕刷榜，要求失分 case 改善证明
离线分和线上指标连续两版不对齐  → eval 拟合断裂，启动重建，暂停 eval 做门禁
```

### 8.11 评测体系健康检查清单（每季度自查）

| 检查项 | 健康标准 | 风险信号 |
|---|---|---|
| 闭环是否跑通 | 每次迭代报告含 bad case pass rate | 总分涨但从未统计 |
| eval 结论是否进入训练 | 每个失分维度有对应 action item + owner | 报告发出后无后续 |
| 题库新鲜度 | 每季度更新 ≥ 20% 样本 | eval 集超 6 个月未更新 |
| Dev/Test 分离 | 两份独立维护，Test 访问有记录 | 只有一份 eval 集同时用于迭代和上线 |
| Judge 校准 | 每 2 周抽样 50-80 条；相关系数 > 0.70 | 超 2 个月没做人工校准 |
| Protocol 版本化 | 有变更日志，Judge 锁定版本号 | 近 3 个月分数有跳跃原因不明 |
| 联合判题会 | 每月一次，至少 20 条，双方参与 | eval 完全由一方独立完成 |
| 离线-线上拟合 | 每月相关性报告；A/B 一致率 > 60% | eval 连续涨但线上无改善 |
| 团队信任 | eval 结论进入上线决策 | 分数被认为是"参考参考" |

## 附录 A · Metric 公式速查

| 指标 | 公式 | 适用 |
|---|---|---|
| Accuracy | (TP+TN)/(TP+TN+FP+FN) | 分类均衡时可用 |
| Precision | TP/(TP+FP) | 误报代价高时 |
| Recall | TP/(TP+FN) | 漏报代价高时（红线优先） |
| F1 | 2·P·R/(P+R) | 平衡误报和漏报 |
| Macro-F1 | 各类 F1 取平均 | 多分类，小类同样重要 |
| Exact Match | (1/N)·Σ 1[norm(y)=norm(ŷ)] | 短答案完全匹配 |
| NDCG@k | DCG@k / IDCG@k | 搜索/RAG 排序 |
| MRR | (1/N)·Σ 1/rankᵢ | 第一个正确结果的排名 |
| Hit@k | (1/N)·Σ 1[Top-k 有正确结果] | RAG Top-3 有没有答案 |
| Likert 均分 | (1/N)·Σ sᵢ | 开放问答最常用 |
| 维度加权均分 | Σ wᵈ·sᵈ | 如 D1×0.3+D2×0.2+… |
| Pass Rate | (1/N)·Σ 1[sᵢ ≥ θ] | 合格率（θ=合格阈值） |
| 红线违规率 | (1/N)·Σ 1[触犯任一红线] → 0 | 守门 Metric |
| Pass@k | 1 - C(n-c,k)/C(n,k) | 代码/数学多次采样 |
| Win Rate | W/(W+L+T) 或 W/(W+L) | 版本对比 |
