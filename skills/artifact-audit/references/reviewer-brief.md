## 只审这些
- plan：P1 选型结论有实测或一手来源支撑；P2 影响面列全（用 grep 核对入口、消费方、数据契约）；P3 部署与运行约束可行；P4 不违背 G/NG/项目硬约束；P5 AC 可测；P6 失败时的系统状态有定义。
- impl：I1 每条 AC 与 `gate: impl` 问题都有测试，且测试确实能失败；I2 diff 触及函数的调用方、消费方契约兼容；I3 领域正确性（对照黄金集或真值）；I4 失败路径：错误可见、无静默降级、资源清理、超时；I5 部署：镜像、预检、权限、资源；I6 范围：diff 不超出 Spec，全量测试无回归。

## 不审
- plan 阶段的实现细节（函数签名、序列化、异常分支）。
- 措辞与风格偏好（除非导致事实错误）。
- "代码尚未实现""测试尚未运行"不是方案问题：对应要求记 `gate: impl`。

## 每条问题的准入
- `basis`：引用 G-/NG-/AC- 编号或项目硬约束；引用不出来的不要提。
- `evidence`：`measured` 表示本轮实际运行过，正文写命令与结果；`traced` 表示给出可逐项核对的 `文件:行`——代码缺陷从真实入口（前端实际调用的接口、对外 API、CLI、部署后的服务）逐跳到缺陷点，方案缺陷指出原文位置与冲突事实位置；其余填 `inferred`，只能定 Minor。没有 UI 入口不等于不可达，对外 API 同样是真实入口。
- `gate`：方案阶段就能改正的记 `plan`；只能实施后验证的记 `impl`；部署批准、业务签认等上线前提记 `release`；不做本次改动也存在的缺陷记 `none`（由用户确认是否另立事项）。
- 级别：Critical 指按现状交付会让错误数据进入交付物、丢数据或越权，且没有可见信号；Major 指不满足某条 AC 或破坏既有契约，但失败可见；其余为 Minor。
- 实施主审的 open Critical/Major（`gate` 为 plan/impl）须带 `repro`（失败测试或复现命令）。
- 同一根因只登记一条，重复项记 `withdrawn` 并在正文写"重复于 X"。允许零问题，不设数量指标。

## 复核轮
- 先核对 `audit-state` 自上次盖章后的改动（`git diff` 本报告）：被会话降级、改 gate、撤销、关闭的 Critical/Major 逐条确认，不成立就恢复并写明原因。
- 逐条复核上轮 open 问题：接纳项核对正文或代码确已修改；质疑项判断理由是否成立，不成立保持 open 并写明哪条事实不符；用户已裁决的按裁决执行。
- 新问题只能针对本轮 diff，并写明 diff 位置；diff 外的发现写进「观察」节。例外：实测（measured）的 Critical，须写明首轮为何漏掉。
- 已关闭的问题不重开，除非本轮 diff 让它重现（写明是哪一行）。

## 报告结构
结论（通过 / 附条件通过 / 阻断退回，写明是哪道门禁）→ 审计边界 → 已实测证据（命令 + 结果）→ 问题清单 → 观察 → 未覆盖范围；正文恰好一个 `audit-state` 围栏。
