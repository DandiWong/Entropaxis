# Artifact Audit

把审计视为一个有边界的事件，而不是每次修改都生成一份新报告。规则真源见 [`../../rules/知识沉淀.md`](../../rules/知识沉淀.md)；报告落盘、命名与物理交付遵循 [`../../rules/文件交付.md`](../../rules/文件交付.md)。

## 输入

确认以下信息；优先从当前会话、目标文件、最近的 `AGENTS.md` 和既有报告中取得，不重复询问：

- 受审目标：一个文件或一组明确文件；
- 审计目标：要验证的质量、安全、合规或验收门禁；
- 既有审计报告：如有，必须先读取；
- 输出方式：仅会话反馈，或维护磁盘报告。

只有用户明确要求落档、生成报告或继续维护既有报告时才写文件。否则完成一次性审计并在会话中返回结论，不创建报告。

## 工作流

### 1. 界定审计事件

以“同一目标谱系 + 同一审计目标 + 尚未终审通过”判定同一事件：

- 同一事件且已有报告：原地更新该报告，不创建 `v2`、`新版` 或日期不同的副本。
- 既有报告已 `approved`：保持冻结。目标或审计目标出现新变化时创建新事件，并在新报告中引用前序报告。
- 找到多个疑似活动报告：先按目标、目标范围和状态确定唯一真源；无法确定时停止写入，列出冲突证据。

### 2. 固定受审快照

在审计前记录当前快照：

- 单文件：记录相对路径与文件字节的 SHA-256。
- 多文件：按相对路径排序，逐项记录 SHA-256；再对每行 `<sha256>  <relative-path>\n` 的 UTF-8 拼接结果计算 SHA-256，作为 `snapshot_id`。
- 无法读取稳定字节的外部对象：记录可验证版本、来源和取得时间；没有稳定版本时明确写“指纹不可用”，不得伪造哈希。

当前快照与报告最后一轮完全相同时，不增加轮次、不改写报告；直接说明没有新的受审版本。

### 3. 审计并维护问题台账

先复核历史问题，再检查当前工件是否产生新问题：

- 问题 ID 跨轮次稳定；新问题顺序递增，禁止因排序变化重编号。
- 只有当前工件中的可定位证据证明修复完成时才标记 `closed`；承诺、计划或报告文字本身不算关闭证据。
- 每个开放问题写明严重度、证据位置、风险与可验证的关闭条件。
- 区分事实与推断；证据不足时标记待确认，不把推断写成事实。

### 4. 作出轮次结论

结论只使用以下值：

- `rejected`：存在阻止通过的问题；
- `conditional-approval`：主要门禁已满足，但仍有明确的非阻断问题或待确认项；
- `approved`：全部审计门禁满足，阻断问题为零，历史问题均有关闭证据。

不得用“基本通过”“应该没问题”等模糊措辞替代结论。`approved` 后填写终审时间并冻结报告。

### 5. 维护报告

首次创建报告时使用 [`references/report-template.md`](references/report-template.md)，并按项目既有报告位置与《文件交付》命名规范落盘。后续轮次：

1. 更新 frontmatter 中的当前结论、轮次和快照；
2. 更新“当前结论”和问题台账；
3. 在“轮次记录”末尾追加本轮，保留全部历史轮次；
4. 只在更正客观错误时修改历史，并显式记录更正原因；
5. 终审通过后不再改写该报告。

## 输出

会话回复保持简洁，至少包含：

- 审计事件与轮次；
- 当前快照 ID；
- 结论；
- 已关闭、新增、仍开放的问题数量与阻断项；
- 报告路径，或“仅会话反馈，未落盘”。

涉及外部写入、敏感信息、个人信息或受控材料时，继续遵守最近的 `AGENTS.md` 和工作区安全规则；本 Skill 不降低任何授权门禁。
