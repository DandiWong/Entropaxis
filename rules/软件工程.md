# 软件工程

适用于本工作区下的一方开发项目。项目 `AGENTS.md` 或 Spec 可以补充更严格的要求；第三方和上游仓库优先遵循其局部契约。

## 开始前

1. 读取最近的 `AGENTS.md`，再按需读取 README、Spec 和配置说明。
2. 检查 `git status --short --branch`，识别用户改动、生成物和不应提交的文件。
3. 明确本次改动的行为边界、验收方式和文档真源。
4. 多文件或行为性改动应有 Spec；小型、局部且验收明确的修复可直接实施。
5. 大型复杂工程（多阶段流水线、深层调用网）进行架构重构、全景盘点或专利挖掘时，推荐按需调用拓扑分析工具（如 `graphify`）提取中枢节点与调用链；提炼出的架构结论必须收敛至 Spec 或文档真源，其派生缓存（`graphify-out/`）删了可重建，不作为唯一真源。日常局部修改优先使用 `lsp` / `grep`，严禁滥用全量建图。

## 实现原则
- 先复用现有代码、标准库和已安装依赖；不为假想需求增加抽象、兼容层或配置。
- 修复共享根因，不在每个调用点重复打补丁。
- 重构优先删除无用层次与死代码，不盲目新增抽象；保留必要的输入校验、安全防御与可恢复性。
- 尊重现有接口和数据；破坏性迁移必须在 Spec 中写明影响、回滚与验证。
- 配置、密钥和环境差异不得硬编码；示例配置只放占位值。
- 错误和阻断应可见，不用静默降级伪装成功。
- 独立代码库应用自身工程管理机制（内部依赖、私有配置与测试套件），工作区通用规则不强行介入其内部结构。

## 研发迭代与方案审修闭环 (Spec, Branch & Dev Loop)

功能开发与缺陷修复严格区分为**“方案审修”**与**“实施研发”**两个阶段，执行状态隔离：

### 1. 方案设计与审修阶段 (Spec, Audit & Amend)
* **规格设计**：对多文件、跨模块、协议变更或破坏性改动，在 `docs/YYYYMMDD_主题/Spec_<ID>_主题方案.md`（或工作胶囊内 `02_方案.md`）编写实施规格，明确输入输出契约与验收条件；
* **对抗审计与修正**：触发“审计”出具 `Audit_<ID>_主题方案审计.md`（或 `05_审计报告.md`），并通过“修正”逐条判定接纳改写或质疑辩驳并就地更新方案；
* ⚠️ **状态隔离铁律（防提前污染）**：**方案设计、落盘、审计与修正阶段，严禁改动 `docs/Tasks.md`**（防止未定稿方案提前占用 `in_progress` 状态或污染任务看板）。

### 2. 迭代 Spec 编写标准
迭代特性的技术实施规格必须包含以下 4 项：

1. **前置条件**：必要前置是完整的功能方案（业务链路、交互逻辑、业务规则、输入输出预期与边界条件）；原型 Demo 非必需。
2. **字段提取与动静态归属**（存在原型 Demo 时必须执行）：自上而下提取全部可见与交互字段并区分归属——前端静态字段（固定文案、表头 Label、本地枚举、帮助提示、样式映射）与 API 动态字段（业务数据项、状态枚举、统计指标、检索/输入参数、分页数据）。
3. **API 契约**：接口定义（Path、Method、鉴权与权限）、请求参数（Query/Body 类型、必填、校验约束与默认值）、响应契约（HTTP Status、完整 JSON Schema）、错误契约（ErrorCode、行动导向的 ErrorMessage 及异常分支）。
4. **分层编排**：
   - **数据层**：完整 DDL（`CREATE TABLE IF NOT EXISTS`）、主外键与索引（`CREATE INDEX IF NOT EXISTS`）、字段注释、状态机枚举与存量兼容/迁移策略；
   - **后端**：路由定义、Controller/Handler 签名与参数解析、Service 业务流转、事务边界与持久化逻辑；
   - **前端**：组件与页面层级拓扑、状态管理、动静态字段绑定映射、API 请求与异常/Loading/Empty 状态处理及交互事件响应。

### 3. 实施准入与研发闭环 (Branch, Claim & Dev Loop)
只有当方案定稿、明确进入开发实施后，方可启动研发闭环：
1. **新建分支 (New Branch)**：基于最新主干创建独立工作分支（如 `feat/<topic>` 或 `fix/<issue>`），隔离特性代码；
2. **认领任务 (Claim Task)**：**开辟新分支后方可修改 `docs/Tasks.md`**，将对应 Task ID 状态置为进行中 (`in_progress`)；
3. **测试驱动开发 (TDD)**：先编写或更新能复现预期的最小自动化测试用例，再编写实现代码，确保全量测试回归通过；
4. **履历与成效记录 (Changelog & Benchmark)**：
   - 在 `docs/Changelog.md` 追加变更明细；涉及性能、准确率或量化指标变更时，在 `docs/Benchmark.md` 追加前后对比评估快照；
   - 遵循标准 Changelog 语义化规范（用户与系统场景视角、分类 Icon、Task/PR 可追溯、严禁干瘪 commit 堆叠）；
5. **精确提交 (Git Commit)**：单 Task 单 Commit，提交信息必须包含 Task ID 与改动范围摘要（如 `fix(agent): [Bug-31] 模型流式重试...`），严禁包含未授权的无关改动；
6. **合并与状态同步 (Merge & Done)**：将功能分支 Merge 回主干，在 `docs/Tasks.md` 中将对应条目勾选完成 (`done`)。

## 环境交付与发布指令锚定

面向多环境部署与发版交付，自然语言指令与底层工程动作建立严格的确定性映射：

### 1. “发布测试”
* **触发口令**：“发布测试”、“部署测试环境”、“发一版测试”、“跑测试部署”
* **执行**：① 确认当前分支单元与集成测试 100% 通过；② 构建测试镜像或更新测试集群配置，部署至测试环境；③ 运行 Smoke Test 或健康探测确认服务就绪；④ 输出测试环境访问地址、版本号与部署状态。
* ⚠️ **限制**：**不改动生产环境、不打生产 Git Tag、不更新对外正式 ReleaseNote**。

### 2. “发布 / 发布正式”
* **触发口令**：“发布”、“发布正式”、“正式发版”、“上线”、“部署生产”
* **执行**：① 确认待发特性已 Merge 至 `main` 且测试全绿；② 在 `docs/ReleaseNote.md` 写明版本号、核心业务价值、新特性与升级指引；③ 触发生产部署流水线，零停机发布；④ 验证生产可用性与关键业务链路健康度；⑤ 提交 ReleaseNote 并打语义化版本标签（`git tag -a v0.3.0 -m "Release v0.3.0"`）推送远端；⑥ 输出交付确认单、生产入口与 ReleaseNote 摘要。


### 3. “新迭代 / 新 Feature”
触发口令与五步执行闭环见 [`治理指令.md`](治理指令.md)「新迭代 / 新 Feature」，本处不复述；分支命名、Task 认领时机与提交粒度约束适用于本规则「研发迭代与方案审修闭环」。

## Changelog 规范与撰写标准

所有应用代码库与工程项目的变更日志统一命名为 **`Changelog.md`**（首字母大写，其余小写，统一禁止命名为 `ChangeLog.md` 或 `changelog.md`）。

格式严格遵循 [Keep a Changelog 1.1.0](https://keepachangelog.com/zh-CN/1.1.0/) 与 [语义化版本 2.0.0 (SemVer)](https://semver.org/lang/zh-CN/spec/v2.0.0.html)：

### 1. 核心撰写准则
- **为人类编写**：阐述变更的背景、意图与影响，不做 Git Commit 差异的机械堆砌；
- **语义聚合**：同一需求内的多处细微修改聚合成连贯条目，不留琐碎记录；
- **倒序排列**：最新版本与 `[Unreleased]` 区段置顶；
- **日期用 ISO 8601**：`YYYY-MM-DD`；
- **可追溯**：条目末尾附 Task ID、Issue 或 PR 标识（如 `([Tech-92])`）。

### 2. 标准 6 大变更分类 (Standard Categories)

| 分类标题 | 适用场景 |
|---|---|
| `### 新增` / `Added` | 新添加的功能、工作流或能力 |
| `### 变更` / `Changed` | 对现有功能、逻辑、架构或依赖的更改 |
| `### 弃用` / `Deprecated` | 不建议使用、将在未来版本删除的特性 |
| `### 移除` / `Removed` | 本版本已彻底删除的功能或死代码 |
| `### 修复` / `Fixed` | 修复的缺陷、崩溃或异常处理 |
| `### 安全` / `Security` | 漏洞修复、权限隔离与数据安全加固 |

## 测试与验证

- 非平凡逻辑先写或更新能复现预期的最小测试，再实现。
- 优先运行最贴近改动的检查；交付前再运行项目 `AGENTS.md` 指定的完整检查。
- 不宣称未实际运行的测试通过。无法运行时说明原因和剩余风险。
- 纯文档改动至少检查链接、命令、术语和规则冲突。

## Git 与外部操作

- 日常开发严格遵循上述 **研发迭代标准闭环 (Feature / Bug Loop)**；
- 未经明确授权，不拉取、推送、合并、部署、发布或向外部系统写入；
- 只提交本次任务文件，不覆盖、不清理无关改动。

## 文档与任务

- 架构、行为或配置发生变化时，更新其唯一真源；不要在多个 README、规则和 Spec 中复制同一段内容。
- 命名与通用交付文件规范见 `文件交付.md`；项目索引与分层结构见 `项目组织.md`。
- Spec、任务状态和外部看板同步见 `看板联动.md`。
- 表达和图示见 `表达文风.md`；只有在图示显著提升理解时才使用。
