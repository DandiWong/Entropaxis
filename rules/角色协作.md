# 角色协作

适用于需要明确职责归属、跨角色交接或协作验收的任务。它定义规则的归属方法，不预设具体岗位、组织关系、审批链或外部平台。

## 三类对象

- **能力 (Skill)**：Agent 能做什么、如何完成任务 · 唯一真源: `.entropaxis/skills/<skill>/SKILL.md`
- **角色 SOP**：谁对什么结果负责、可作何决定、达何门禁 · 唯一真源: 项目级职责材料（通用约束入 rules/）
- **协作协议**：角色间何时交接、交付何物、由谁验收与升级 · 唯一真源: 项目级协作协议（通用模式入 rules/）
`AGENTS.md` 只负责薄路由与项目差异，不复制完整角色 SOP 或协作协议。角色名、人员、组织关系、实例时限和外部系统映射属于项目或 `.entropaxis/data/` 实例信息，不得写入通用规则。

## 角色 SOP

只有角色具有稳定、可区分的决策权限、输入输出或质量门禁时，才建立角色 SOP。每份 SOP 必须包含：

1. 目标与责任边界；
2. 输入、输出及其真源；
3. 可自主决定的事项与必须升级的事项；
4. 触发条件、前置条件与执行步骤；
5. 质量门禁、验收证据和失败处理；
6. 与协作协议的引用关系。

角色 SOP 不得重复全局安全规则、其他角色的步骤或协作交接细则。

## 协作协议

仅在存在重复、可验证的跨角色交接时建立协作协议。每份协议必须包含：

1. 参与角色、唯一 DRI 与验收责任人；
2. 触发事件、前置条件和交付状态；
3. 交付物、格式、真源和最小验收标准；
4. 通过、退回、升级的条件与时限；
5. 冲突、缺失信息和异常的处理路径；
6. 所引用的角色 SOP；不得复制其正文。

默认状态为 `待提交 → 验收中 → 通过 / 退回 → 升级`。简单协作只指定 DRI、验收人和必要咨询方；只有确有多方权责歧义时才使用 RACI。


## AI 时代认知模态分工 (Cognitive Personas)

在 AI Agent 体系中，当前会话 Agent 天然担任 **Manager (主控调度者)**，负责解析口语指令、编排流水线、调度专家模型并在终点完成物理交付；各专业输出由 **7 大认知模态**（承载 CLI 按三级就近解析确定，降级按调度决策矩阵裁决）承载：

- **0. Manager (主控调度)**：指令解析/流水线编排/任务分发/异常降级/物理交付 · 承载: 当前交互会话 Agent
- **1. Architecture (架构师)**：顶层架构/技术选型/方案设计/接口契约 · 产出: `02_方案.md`
- **2. Researcher (探索者)**：调研（强制联网）/文献查新/竞品与法规 · 产出: `01_调研.md`
- **3. Designer (视觉美学/UI)**：视觉排版/美学呈现/UI交互原型/图表 · 产出: `03_设计.md` + `prototypes/`
- **4. Builder (工程师)**：Spec规格/核心代码/TDD单测实现 · 产出: `04_Spec_<ID>.md` + 代码
- **5. Reviewer (审计/红队)**：安全合规审计/红队对抗/边界漏洞评审 · 产出: `05_审计报告.md`
- **6. Maintainer (守门/验收)**：全流程跑通/端到端验收/交付凭据归档 · 产出: `07_验收报告.md`
- **7. Reporter (汇报者)**：汇报材料提炼/周报双周报/交付总结 · 产出: 汇报容器目录或交付总结

### 角色指派三级解析与调度门禁 (Assignment Resolution & Gates)

角色承载按三级就近解析：① 活跃事务胶囊 `capsule.yaml::roles_manifest`（任务级真源）→ ② 无胶囊时 `<工作目录>/workers.yaml`（Manager 开工时写，供 handoff）→ ③ [workspace-config.md](../data/templates/workspace-config.md) 角色模态表与 `command_profiles`（全局默认，用户维护；`default_dispatch_mode` 缺失时解析为 `strict` 硬默认）。用户本会话显式指令优先于一切（元规则 #2，不建档），可逐任务把任意角色升为硬外置。

硬约束（违反即 fail-closed）：
- **建档**：有活跃胶囊必有第 1 级；无胶囊但产出超出本会话必有第 2 级；纯对话/Trivial 不建档不调度（「归属与演进」#3）。指派记录一律由 `dispatch_role.py run --role <角色> --out|--verify` 直跑时落笔（第 3 级解析 + 判据裁定 + CAS 写回），人不手写 assignment；无前序受审对象的角色（调研/方案/汇报）不填 `target_*`，`--target` 声明输入依据后依据变更即标 `stale`；档案缺失时只出回执不造容器。
- **成功判据按产出形态取**：文档型看交付物是否合规写出；目录型（Designer/Reporter）另需 `deliverable-state` 机器围栏且 `outputs` 非空——目录「存在」不构成产出；代码型（Builder）以 `verify_profile` 退出码为准，产出记 `deliverable_ref`（`git:<sha>`）而非单文件。判据与形态错配即假门禁。
- **同级改写**：指派更新在持有锁与 revision 前提下直接改写该级档案，禁止影子档案；跨会话生效的用户指令由 Manager 撤离前并入第 1/2 级。并发写入由下文「恢复与并发」的锁 + CAS 串行化（实测 4 个并发写入者收敛为一条记录，无损坏）。
- **mode 单向收紧**：`graceful` 仅第 3 级可声明且须携带有效 `dispatch_authorizations` 授权记录（含确认事件、角色范围、失效日；范围出现 Reviewer/Maintainer 即整条无效）；第 1/2 级档案 `mode` 只允许 `strict` 或省略。授权缺失/过期/越范围一律按 `strict`，永不放宽。
- **档案零命令**：两级档案只存 `command_profile` 标识；命令本体只存第 3 级 `command_profiles`（结构化 argv 数组，禁 shell 字符串与 `||` 内联；备选以 `fallback_profile` 单跳表达，链深 ≤3 带环检测）。未知 profile 或档案内联命令 → 拒绝调度。
- **调度五态**：`pending/running/succeeded/failed/blocked`；豁免仅问题级 `waived_by_user`，档案不承载豁免。
- **不得自我重入**：外置角色在 `--cwd` 内拥有 shell，看得见什么就可能执行什么——实测 Reviewer 读到胶囊里的驱动脚本后，自行改写提示词重新调用了 `dispatch_role.py` 三次。故编排脚本、流水线驱动与含调度命令的说明**一律不得置于 Agent 工作目录内**（留证据就去扩展名、去可执行位）；被调度的角色只做本职产出，不得再发起任何角色调度，需要下一棒时把理由写进交付物由 Manager 裁决。
- **恢复与并发**：写回=临时文件+`os.replace` 原子替换+目录锁(owner/lease)+revision CAS；journal 仅追加审计轨迹、非恢复载体（恢复源是档案自身）；锁过期先归档锁目录再 schema 校验，不通过才 corrupt 归档重指派；`target_sha256` 与当前对象不符时 `succeeded` 失效回 `pending`。
- 字段机器契约：`schemas/roles_manifest.schema.json` 与 `command_profile.schema.json`（唯一桶 `schemas/`）；解析、校验与执行唯一入口 `tools/dispatch_role.py`（含 `--migrate-config` 字段级迁移，仅缺失写入不覆盖）。

**门禁划分**：

- **硬外置** Reviewer、Maintainer：独立性是本质契约，缺失即阻断，仅问题级 `waived_by_user`（经 `check_audit_gate.py` 校验）可解锁会话内承载并标「降级+待外置复核」，无豁免不得推进实施准入。**软外置** Architecture/Researcher/Designer/Builder/Reporter：角色指派正确性强制（profile 必须匹配角色映射），外置失败可本地承载 + attempts 留痕（Reporter 应当外置），离线可推进（元规则 #7）。失败裁决一律按下表，本节不复述。

| mode × 门禁 | 失败码 | 唯一结果 |
|---|---|---|
| strict × 硬 | 任意 | `blocked`；仅问题级豁免解锁 |
| graceful × 硬 | 任意 | 同上（graceful 永不适用硬门禁） |
| strict × 软 | `UNCONFIGURED`/`SUBAGENT_AUTO` | 本地承载 + attempts 记 `unconfigured→local`，不阻断 |
| strict × 软 | `NOT_EXECUTABLE`/`TIMEOUT`/`NO_VALID_OUTPUT`/`CHAIN_EXHAUSTED` | 本地承载 + 留痕 + `待外置复核`，计入 Maintainer 终审必查，不阻断 |
| graceful × 软 | 任意 | 本地承载 + 留痕 |

### 调度优先序与降级契约 (Dispatch Hierarchy)

各认知模态在执行时按「角色指派三级解析与调度门禁」确定承载，并遵循：
1. **外置必执行**：`command_profile` 由 `dispatch_role.py` 以结构化 argv（无 shell 拼接）实际执行，`fallback_profile` 备选链按声明顺序穷尽（链深 ≤3、带环检测）；
2. **矩阵裁决**：未配置、`subagent`/`auto`、不可执行、超时、无有效报告、备选穷尽等失败码，按上表唯一裁决——strict×硬一律 `blocked`（fail-closed），无自动降级分支；graceful（仅第 3 级有效授权）×软按表本地承载；
3. **真实留痕**：降级与承载以**三元组** `carrier`/`carrier_ref`（命令原文）/`fallback_reason`（结构化原因）如实记录，严禁伪造外置独立性；三者由 `dispatch_role.py` 依调度回执盖章，不由模型自述，Research/Proposal/Report 缺 `carrier` 即 schema 不通过；Audit 报告的 `reviewer_mode`/`reviewer_ref`/`fallback_reason` 是同一三元组的特化形态。**承载的信任根是回执，不是交付物**：Front Matter 与被调度模型同权限可写，盖在里面的字段不构成证据；签发者在真实执行后于 `data/receipts/`（工作目录之外）落一份 HMAC 回执，绑定角色+argv+正文+依据四项指纹，交付物只携带 `receipt_id`。声称外置却无有效回执、或文内 carrier 与回执不符、或正文被改写，一律判违规；历史交付物无此字段按空态处理。命令原文与输出尾部另落 `data/logs/dispatch-trace.jsonl`（`dispatch_role.py trace`），均不随版本库分发。

### 方案生命周期指令与模态映射

用户使用日常动词发起任务时，Manager 自动映射至对应认知模态并组装串行流水线（上一步产出即下一步输入）：

- **调研 / 查查**（`出调研`、`做调研`、`调研报告`、`找找开源方案`）：Researcher ➔ `01_调研.md`（按《方案调研》执行）
- **出方案 / 定架构 / 选型**（`出方案`、`设计架构`、`技术选型`、`做顶层设计`）：Architecture ➔ `02_方案.md`
- **美化 / 画原型**（`出原型`、`做个demo`、`排版美化`、`UI设计`）：Designer ➔ `03_设计.md` + `prototypes/`
- **写代码 / 实施**（`写代码`、`实施`、`实现`、`修bug`、`跑测试`）：Builder ➔ `04_Spec_<ID>.md` + 代码
- **审一下 / 挑挑刺**（`审计`、`审方案`、`代码评审`、`找漏洞`）：Reviewer ➔ `05_审计报告.md`（对抗评审）
- **跑通 / 验收**（`全流程跑通`、`验收`、`归档`、`交付检查`）：Maintainer ➔ `07_验收报告.md`
- **汇报 / 总结**（`出汇报`、`写周报`、`双周报`、`写交付总结`）：Reporter ➔ 汇报容器目录
### 审计角色选择与降级（唯一正文）

审计角色的选择、降级判定与字段留痕，本节为唯一正文；《治理指令》「审计」节只保留触发意图与受审对象定位，其他文件引用本节，不重复维护。

1. 优先使用用户自定义的审计角色（当前指令明确指定时优先于既有配置），否则读取 [`.entropaxis/data/templates/workspace-config.md`](../data/templates/workspace-config.md) 的审计角色配置。
2. 审计是硬门禁角色，失败裁决一律按上文「mode × 门禁」矩阵，本节不复述；会话内承载须引用一条经 `check_audit_gate.py` 校验的问题级 `waived_by_user`，Critical 的关闭在任何模式下仍须外置复核。
3. 无论何种承载，修正方先响应、审计角色再复核；承载与降级留痕见「调度优先序」#3，轮次上限与僵局停止条件见「方案审修协同闭环」#5，本节不复述。

### 问题终态三分 (Issue Terminal States)

审计问题的状态不是二值（待处理/已关闭），而是三分：

- **`closed`**（Reviewer 复核通过）：Critical 必须由外置 Reviewer 复核；Major/Minor 会话内承载即可
- **`open`**（未复核或不通过）：默认态；Designer 的质疑在被 Reviewer 采纳前同样按 open 处理
- **`waived_by_user`**（用户显式风险接受）：绑定问题 ID、受审指纹、确认事件与适用范围四项，缺一不可
`waived_by_user` 允许实施继续推进，**但不得宣称“独立审计通过”，也不得记为 Reviewer `closed`**；报告与交付说明中必须原样呈现该终态。外置环境恢复后，被豁免的 Critical 仍应补一次外置复核，复核通过才转 `closed`。会话内 Reviewer 不是独立审计的降级形态而是独立性能力缺失——`waived_by_user` 是用户对该缺失的风险接受，不是审计证据，二者不可互相顶替。字段的机器可读契约见 `audit_report.schema.json`。

### 方案审修协同闭环 (Design-Audit-Amend Loop)

方案演进通过认知模态协同形成确定性闭环：
1. **方案初稿**：Designer / Builder 产出业务方案或技术实施规格（`02_方案.md` / `Spec_*.md`）；
2. **对抗审计**：通过“审计”指令唤起 Reviewer 开展独立对抗性评审，在同容器目录下出具 `05_审计报告.md`（或 `Audit_*.md`），给出分级问题与整改建议；
3. **响应修正**：Designer / Builder 通过“修正”指令逐条响应审计报告：接纳项直接改写方案正文（补齐契约、加固防御、调整架构），质疑项阐明客观辩驳理由，并在方案末尾维护《审计意见响应与修订记录》；
4. **复核关闭（Reviewer 独立否定权的落地）**：Reviewer 对第 3 步的每条裁定二次复核——接纳项核验方案正文是否已实质修订，质疑项核验辩驳是否成立；复核通过方可将该问题标记 `closed`，复核不通过则问题保持 `open`，退回步骤 3 进入下一轮；
5. **终审判据与人工锚点**：Reviewer 将全部问题标记 `closed`（或用户对指定 Critical 显式记录 `waived_by_user`）即终审通过；`closed` 状态的 Critical 额外需要人工批量签字确认；同一事件循环达到轮次上限（默认 3 轮，可在方案 Front Matter 的 `audit_max_rounds` 覆盖）仍未收敛，或单条问题连续 2 轮双方立场无变化（僵局），停止自动循环，汇总未收敛问题与双方立场转人工仲裁；外置 Reviewer 连续不可用时，会话内可继续发现问题、复核关闭 Major/Minor、准备修订，Critical 保持 `open` 直至外置复核或用户豁免；
6. **实施准入触发任务流**：方案审修全过程聚焦于方案文档本身，严禁改动 `Tasks.md`；待方案定稿并通过“新迭代/开分支”正式进入开发实施后，方可在 `Tasks.md` 中将对应任务认领为 `active`。

## 归属与演进

1. 同一职责或交接规则只保留一个正文；其他规则和项目入口只链接说明用途。
2. 具体项目的角色 SOP 与协作协议应随项目材料维护；跨项目规则只抽象可移植的共同行为。
3. 当仅是一次性分工、同一 Agent 串行完成工作，或尚无独立验收与交接需求时，使用任务卡，不建立角色或协作规则。
4. 当至少存在两个稳定角色且有重复协作链路、规则已混写，或不同角色需要不同路由、权限或质量门禁时，再考虑按 `roles/` 与 `collaboration/` 目录物理拆分。
5. 新增或修改本规则、角色 SOP、协作协议时，遵循元规则与相应项目的 `AGENTS.md`；涉及 `.entropaxis/` 时同时遵循 `01_根系统治理.md`。
