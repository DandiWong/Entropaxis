# 角色协作

适用于需要明确职责归属、跨角色交接或协作验收的任务，以及方案生命周期（调研→方案→原型→实施→审计→验收→汇报）的角色调度。不预设具体岗位、组织关系、审批链或外部平台。

## 三类对象

- **能力 (Skill)**：Agent 能做什么、如何完成 · 唯一真源: `.entropaxis/skills/<skill>/SKILL.md`
- **角色 SOP**：谁对什么结果负责、可作何决定、达何门禁 · 唯一真源: 项目级职责材料（通用约束入 rules/）
- **协作协议**：角色间何时交接、交付何物、由谁验收与升级 · 唯一真源: 项目级协作协议（通用模式入 rules/）

`AGENTS.md` 只做薄路由，不复制完整角色 SOP 或协作协议。角色名、人员、组织关系、实例时限和外部系统映射属于项目或 `.entropaxis/data/` 实例信息。

## 角色 SOP 与协作协议

只有角色具有稳定、可区分的决策权限、输入输出或质量门禁时才建角色 SOP，须含：目标与责任边界；输入输出及真源；可自主决定与必须升级的事项；触发条件、前置条件与步骤；质量门禁、验收证据与失败处理；所引用的协作协议。不重复全局安全规则或其他角色的步骤。

只有存在重复、可验证的跨角色交接时才建协作协议，须含：参与角色、唯一 DRI 与验收人；触发事件、前置条件与交付状态；交付物、格式、真源与最小验收标准；通过/退回/升级的条件与时限；冲突与异常处理路径；所引用的角色 SOP。默认状态 `待提交 → 验收中 → 通过 / 退回 → 升级`；简单协作只指定 DRI、验收人和必要咨询方，确有多方权责歧义时才用 RACI。

## 认知模态分工
**任何新会话开始时，会话 Agent 默认指派为 Manager 角色**，无需用户显式指定；用户显式指派其它角色时以用户指令为准（元规则第 2 条）。

当前会话 Agent 担任 **Manager**（解析指令、编排流水线、调度角色、异常降级、物理交付）。**Manager 边界禁区**：任何场景与时段（不限开发，无论是否建立物理胶囊），Manager 严禁直接产出或修改专业交付物（即下列 7 角色的产出：调研、方案、设计、代码、审计、验收、汇报），必须按「方案生命周期指令与模态映射」调度对应角色；宿主临时 task/subagent 仅用于只读检索与探索，严禁替代业务角色。**直接执行豁免（唯一正文）**仅三种：① 用户本轮明确要求由当前会话直接做（如「直接改」「你来写」）；② 只读动作：问答、检索、跑测试、排查诊断；③ 《工作流指令》中的事务性动作（定位、同步、任务、记录、工时、报销等）及事务型 Skill（看板、发票、初始化、目录整理、自检、系统演进等）。Manager 自行发现需要专业产出的问题（如代码缺陷、证据缺口、汇报缺项）不属豁免：先报告并提议调度对应角色，待用户确认。动用豁免前先声明「按豁免直接执行：<①/②/③>」。

专业产出由 7 个角色承载：

- **Architecture**：顶层架构/技术与业务方案/项目计划/接口契约 · 产出 `02_方案.md`（含「审计基准」节）
- **Researcher**：调研（强制联网）/文献查新与综述/竞品与法规/技术选型对比/新领域专题学习；有样本或代码时先实测 · 产出 `01_调研.md`（止于选型、证据与决策点）
- **Designer**：视觉排版/UI 交互原型/图表/PPT 与配图插画 · 产出 `03_设计.md` + `prototypes/`
- **Builder**：Spec/核心代码/TDD 实现 · 产出 `04_Spec_<ID>.md` + 代码
- **Reviewer**：方案轻审与实施主审/安全合规/红队对抗 · 产出 `03_方案审计报告.md`（方案轻审）/ `05_实施审计报告.md`（实施主审）
- **Maintainer**：全流程跑通/端到端验收/交付凭据核验 · 产出 `07_验收报告.md`
- **Reporter**：文稿与报告产出（汇报、周报、会议纪要、论文与专利文稿、翻译、公文邮件、数据分析报告、学习笔记与课件文稿） · 产出容器目录（成品 + `README.md` 交付说明）

### 角色指派三级解析与调度门禁

承载按三级就近解析：① 活跃事务胶囊 `capsule.yaml::roles_manifest`（任务级）→ ② 无胶囊时 `<工作目录>/workers.yaml`（供 handoff）→ ③ [`roles.yaml`](../data/templates/roles.yaml)（全局默认，契约 `schemas/roles_config.schema.json`，由用户经「自定义角色」维护；文件缺失或角色未配置时由会话内承载，`default_dispatch_mode` 缺失按 `strict`）。用户本会话的显式指令优先于一切（元规则第 2 条）。

硬约束（违反即 fail-closed）：
- **建档时机**：有活跃胶囊必有第 1 级；无胶囊但产出超出本会话必有第 2 级；纯对话与「直接执行豁免」内的动作不建档不调度。**符合以下任一情形即属「产出超出本会话」，必须建第 2 级**：① 用户一次点名两个及以上角色；② 要产出方案/调研/审计/验收类文档（`01_`–`07_` 编号产物）；③ 产出物需跨会话被引用或续接；④ 涉及硬门禁角色（Reviewer/Maintainer）。指派记录只由 `dispatch_role.py run --role <角色> --out|--verify` 落笔，人不手写；需跨会话生效的用户指令由 Manager 撤离前并入第 1/2 级档案，不建影子档案。
- **成功判据按产出形态取**：文档型看交付物是否合规写出；目录型（Designer/Reporter）另需 `deliverable-state` 围栏且 `outputs` 非空；代码型（Builder）以 `verify_profile` 退出码为准。
- **mode 单向收紧**：`graceful` 只能在第 3 级声明，且须有有效 `dispatch_authorizations`（含确认事件、角色范围、失效日；范围含 Reviewer/Maintainer 即整条无效）；其余一律按 `strict`。
- **档案零命令**：第 1/2 级只存 profile 标识；第 3 级 `command_profiles` 存 agent/model 配对（保留 provider 前缀）或自定义 argv。`roles.preferences` 按序引用配对，序号从 1 起；`profile` 是选中偏好，null 不自动选取。调度从指定/选中偏好起顺序转移，attempts 与回执记录实际成功序号；独立自定义 argv 链可用 `fallback_profile`，带环检测。
- **不得自我重入**：编排脚本与含调度命令的说明不得放在被调度角色的工作目录内；被调度角色只做本职产出，不得再发起调度，需要下一棒时写进交付物由 Manager 裁决。
- **Prompt 留痕与持久化**：Manager 调度角色所构建的任务提示词文件，统一定名 `prompt_<角色小写>.txt`（如 `prompt_maintainer.txt`、`prompt_reviewer.txt`）；有活跃胶囊时统一持久化收敛于胶囊目录的 `prompts/` 子目录下（如 `prompts/prompt_maintainer.txt`），无胶囊时存放在工作目录的 `prompts/`，调度完成后严禁删除，作为审计与复核的过程证据留存。
- 档案写回、并发与恢复的实现不变量见 `tools/dispatch_role.py` 头注释「设计不变量」；回执见 `tools/dispatch_receipt.py`。
- **超时与颗粒度约束**：超时三层解析——`command_profiles.<profile>.timeout_s` > `roles.<角色>.timeout_s` > `default_timeout_s`（缺省 900s），执行时按角色取值，故同一 agent/model 配对被多个角色共享时各自设超时。任一层都受 schema 约束（1..7200s）；硬门禁（Reviewer/Maintainer）解析后须 ≤1800s 防级联雪崩与误阻断，profile 级覆盖同样受限；Builder 推荐 ≤3600s。严禁以单次数小时的长 Agent 替代任务切分；大特性须在 Spec 中拆解为 15~30 分钟粒度的独立子 Task。

**门禁划分**：Reviewer、Maintainer 为**硬外置**（独立性是本质契约，缺失即阻断，仅问题级 `waived_by_user` 可解锁会话内承载并标「降级+待外置复核」）；Architecture、Researcher、Designer、Builder、Reporter 为**软外置**（profile 必须匹配角色；外置失败可本地承载并留痕，离线可推进）。失败裁决唯一表：

| mode × 门禁 | 失败码 | 唯一结果 |
|---|---|---|
| strict × 硬 | 任意 | `blocked`；仅问题级豁免解锁 |
| graceful × 硬 | 任意 | 同上（graceful 不适用硬门禁） |
| strict × 软 | `UNCONFIGURED`/`SUBAGENT_AUTO` | 本地承载 + attempts 记 `unconfigured→local`，不阻断 |
| strict × 软 | `NOT_EXECUTABLE`/`TIMEOUT`/`NO_VALID_OUTPUT`/`CHAIN_EXHAUSTED` | 本地承载 + 留痕 + `待外置复核`，计入 Maintainer 终审必查 |
| graceful × 软 | 任意 | 本地承载 + 留痕 |

### 调度优先序与降级契约

1. **外置必执行**：`command_profile` 由 `dispatch_role.py` 以结构化 argv（无 shell）执行，备选链按声明顺序穷尽。
2. **矩阵裁决**：失败一律按上表，无其他自动降级分支。
3. **真实留痕**：承载以 `carrier`/`carrier_ref`/`fallback_reason` 记录，由 `dispatch_role.py` 依调度回执盖章，不由模型自述；Research/Proposal/Report 缺 `carrier` 即 schema 不通过，Audit 的 `reviewer_mode`/`reviewer_ref`/`fallback_reason` 为同一三元组。**信任根是回执不是交付物**：回执落 `data/receipts/`（工作目录之外，HMAC 绑定角色+argv+正文+依据），交付物只带 `receipt_id`；声称外置却无有效回执、carrier 与回执不符或正文被改写，一律判违规。

### 方案生命周期指令与模态映射

用户用日常动词（含「实施」、「继续」、「推进」等接续推进动词）发起任务，或 Manager 判定需要专业产出时，Manager 必须严格映射并调度对应专业角色串行推进（上一步产出即下一步输入；遇下列确认门禁即停，用户指令后才接下一棒），严禁 Manager 会话直接编写业务源码或产出专业交付物：

- **调研 / 选型**（`出调研`、`做调研`、`调研报告`、`找找开源方案`、`技术选型`、`文献综述`、`系统学习 <领域>`）：Researcher ➔ `01_调研.md`（按《方案调研》）
- **出方案 / 定架构**（`出方案`、`写方案`、`设计架构`、`做顶层设计`、`业务方案`、`项目计划`）：Architecture ➔ `02_方案.md`
- **原型 / 美化**（`出原型`、`做个demo`、`排版美化`、`UI设计`、`做PPT`、`配图`、`画插画`）：Designer ➔ `03_设计.md` + `prototypes/`；产出前端页面时，Manager 用 `open_file.py --on-deliver <页面.html>` 打开页面，请用户确认设计是否合理，确认前不进入下一棒
- **实施**（`按方案实施`、`按 Spec 实现`、`迭代实施`、或经上一轮提议确认进入实施）：Builder ➔ `04_Spec_<ID>.md` + 代码，完成后先过《软件工程》「本地预览确认门禁」，用户指令后才进入 Reviewer 实施主审、收尾或发布；`修bug` 等无定稿方案的修复同样调度 Builder，仅「直接执行豁免」除外
- **审计**（`审计`、`审方案`、`找漏洞`）：Reviewer ➔ `03_方案审计报告.md`（方案轻审）/ `05_实施审计报告.md`（实施主审）（触发与产物见《治理指令》）
- **验收**（`全流程跑通`、`验收`、`交付检查`）：Maintainer ➔ `07_验收报告.md`
- **汇报 / 文稿**（`出汇报`、`写交付总结`、`写周报`、`整理纪要`、`写论文`、`写专利`、`翻译`、`写邮件/通知`、`数据分析`、`做课件`、`整理学习笔记`）：Reporter ➔ 容器目录
- **Skill 归类**：产出型 Skill 按交付物归入上表角色并由该角色执行（如周报、纪要、专利类 Skill 归 Reporter，PPT、生图、插画类 Skill 归 Designer，`artifact-audit` 归 Reviewer）；事务型 Skill 属「直接执行豁免」③
- **指派 / 调度**（`安排给`、`交给`、`让 <角色> 做`、`找 <角色> 出`、`派 <角色>`、`协调 <角色A> 和 <角色B>`、`换个模型/厂家看看`）：按点名的角色走 `dispatch_role.py run --role <角色>`，Manager 不得以其它工具（子代理、MCP、直接执行）替代；点名多个角色时按上表顺序串行推进，上一棒产出即下一棒输入

### 审计角色选择与降级（唯一正文）

1. 优先使用当前指令明确指定的审计承载，否则读 `roles.yaml` 的 `roles.Reviewer`。
2. 审计是硬门禁角色，失败裁决按上表；会话内承载须引用一条经 `check_audit_gate.py` 校验的问题级 `waived_by_user`，Critical 的关闭在任何模式下仍须外置复核。
3. 无论何种承载，修正方先响应、审计角色再复核。

### 问题终态三分

- **`closed` / `withdrawn`**（Reviewer 复核通过 / 误报、重复或前提已删除而撤销）：Critical 必须由外置 Reviewer 复核；Major/Minor 会话内承载即可
- **`open`**（未复核或不通过）：默认态；方案作者的质疑在被 Reviewer 采纳前同样为 open
- **`waived_by_user`**（用户显式风险接受）：绑定问题 ID、受审指纹、确认事件与适用范围四项，缺一不可

`waived_by_user` 允许实施继续，但不得宣称"独立审计通过"或记为 `closed`；报告与交付说明须原样呈现该终态。外置环境恢复后，被豁免的 Critical 仍应补一次外置复核，通过才转 `closed`。字段契约见 `audit_report.schema.json`。

### 方案审修协同闭环

审修分两道门禁：方案轻审定方向，实施主审定正确性。契约为 `audit_report.schema.json` v4；外置任务书用 `artifact-audit` Skill 的 `references/reviewer-brief.md` 填写，不临场自拟。

1. **何时轻审**：命中不可逆数据迁移或删除、权限/身份/隐私边界变化、可能静默改变交付数据含义、新增关键外部依赖或跨系统协议、部署或运行形态重大变化、用户要求之一才做方案轻审；其余直接实施，只做实施主审。
2. **审计基准**：受审方案或 Spec 须含「审计基准」节：目标 `G-n`、非目标 `NG-n`（不修的既有缺陷列于此）、可测验收 `AC-n`、影响面（入口、消费方、数据契约，逐项附 `文件:行`）、失败时的系统状态、决策点 `D-n`。缺此节不发起审计。
3. **问题准入**：每条 open 问题带 `gate`（`plan`/`impl`/`release`/`none`）、`basis`（引用 G/NG/AC 或项目硬约束）与 `evidence`（`measured`/`traced`/`inferred`），`inferred` 只能定 Minor。只能实施后验证的记 `impl`；上线前提（部署批准、业务签认）记 `release`；不做本次改动也存在的缺陷记 `none`，经用户确认后另立事项。级别定义见任务书。
4. **阻断与放行**：`gate` 为 `plan`/`impl` 且不晚于当前 `audit_phase` 的 open Critical/Major 即阻断；Minor、`release`、`none` 不阻断审计门禁，`release` 项由 Maintainer 验收核对，未满足不得上线。方案轻审阻断清零（或 `waived_by_user`）并经用户确认后，按「新迭代 / 开新分支」开发再把任务置 `active`，`gate: impl` 的问题写进 Spec 验收；审修期间不改 `Tasks.md`。实施主审阻断清零即终审通过，其 Critical/Major 须附 `repro`；任务置完成前须实施主审通过。
5. **分诊与响应**：Manager 把多份报告合并为一份，同根因只留一个 ID、其余 `withdrawn`。作者按《治理指令》「修正」逐条裁定，优先删减范围或改决策；新增机制须写明新增的影响面。范围与可达性争议由用户裁决。
6. **复核**：先核对自上次盖章后 `audit-state` 被会话改动的条目（状态工具写入即清回执，报告须经 Reviewer 重新盖章）；再只核上轮 open 问题与本轮 diff，diff 外的新发现记「观察」，实测的 Critical 例外。
7. **熔断**：方案轻审默认 5 轮（`audit_max_rounds` 可覆盖），实施主审默认 7 轮；复核后阻断数（`update_audit_state.py --list` 末行）未下降、达到上限或单条问题连续 2 轮立场不变，即停止自动循环，把阻断项与裁决选项转用户。不自动放行、不自动豁免、不换承载求通过。外置 Reviewer 持续不可用时，会话内可继续发现问题、关闭 Major/Minor，Critical 保持 `open`。
8. **事件与冻结**：两道门禁是两个审计事件、各一份报告，各自轮次在本报告内原地追加。方案轻审本阶段阻断清零即置 `status: completed` 冻结，open 的 `gate: impl` 问题由实施主审首轮引用该报告并沿用原 ID 登记；实施主审阻断清零即冻结。Critical 转 `closed`/`withdrawn` 须过 `check_audit_gate.py`；外置不可用时按「审计角色选择与降级」处理。

## 归属与演进

1. 同一职责或交接规则只保留一个正文；其他规则和项目入口只链接说明用途。
2. 具体项目的角色 SOP 与协作协议随项目材料维护；跨项目规则只抽象可移植的共同行为。
3. 一次性分工、同一 Agent 串行完成、或尚无独立验收与交接需求时，用任务卡，不建角色或协作规则。
