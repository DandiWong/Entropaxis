# 角色协作

适用于需要明确职责归属、跨角色交接或协作验收的任务。它定义规则的归属方法，不预设具体岗位、组织关系、审批链或外部平台。

## 三类对象

| 对象 | 回答的问题 | 唯一真源 |
|---|---|---|
| 能力（Skill） | Agent 能做什么、如何完成一类任务？ | `.system/skills/<skill>/SKILL.md` |
| 角色 SOP | 谁对什么结果负责、可作何种决定、如何达到质量门禁？ | 项目级职责材料；仅稳定且跨项目通用的约束才进入 `.system/rules/` |
| 协作协议 | 两个或多个角色何时交接、交付什么、由谁验收及如何升级？ | 项目级协作协议；仅通用的协议模式才进入 `.system/rules/` |

`AGENTS.md` 只负责薄路由与项目差异，不复制完整角色 SOP 或协作协议。角色名、人员、组织关系、实例时限和外部系统映射属于项目或 `.data/` 实例信息，不得写入通用规则。

## 角色 SOP

只有角色具有稳定、可区分的决策权限、输入输出或质量门禁时，才建立角色 SOP。每份 SOP 必须包含：

1. 目标与责任边界；
2. 输入、输出及其真源；
3. 可自主决定的事项与必须升级的事项；
4. 触发条件、前置条件与执行步骤；
5. 质量门禁、验收证据和失败处理；
6. 与协作协议的引用关系。

角色 SOP 不得重复全局安全规则、其他角色的步骤或协作交接细则。

## 协作协议

仅在存在重复、可验证的跨角色交接时建立协作协议。每份协议必须包含：

1. 参与角色、唯一 DRI 与验收责任人；
2. 触发事件、前置条件和交付状态；
3. 交付物、格式、真源和最小验收标准；
4. 通过、退回、升级的条件与时限；
5. 冲突、缺失信息和异常的处理路径；
6. 所引用的角色 SOP；不得复制其正文。

默认状态为 `待提交 → 验收中 → 通过 / 退回 → 升级`。简单协作只指定 DRI、验收人和必要咨询方；只有确有多方权责歧义时才使用 RACI。


## AI 时代认知模态分工 (Cognitive Personas)

在 AI Agent 具备全栈端到端生产力的体系中，传统职能分工（产品/设计/研发/测试）升级为按 **5 种认知模态** 进行协同演进。各模态可在单人端到端或多 Subagent 流水线中灵活切换，产出统一收敛至事务胶囊：

| 认知模态 (Persona) | 核心职责 | 胶囊内标准产出 | 质量门禁 (Quality Gate) | 默认承载 (Default Runner) |
|---|---|---|---|---|
| **1. Researcher (探索者)** | 业务背景、文献查新、市面竞品、法规合规 | `01_调研.md` | 收敛为**结论 / 依据 / 风险 / 置信度**四段式，严分客观事实与主观推断。 | 当前 Agent 内置 Subagent (`scout`/调研子代理) 或会话模态 |
| **2. Designer (架构/设计师)** | 业务边界、系统方案、非目标、UI/交互原型 | `02_方案.md`、`03_设计.md` | 定义清晰的非目标 (Non-goals)，产出可交互原型验证体验。 | 当前 Agent 内置会话上下文或通用 task |
| **3. Builder (构建者/工程师)** | 技术规格 (Spec)、接口契约、TDD代码实现 | `04_Spec_Tech-N.md`（细粒度变更记录链接库根 `Changelog.md` 真源，不另写胶囊内副本） | 遵循最小作用量原则，TDD 契约驱动，单 Task 闭环。 | 当前 Agent 内置通用 task 或直接实施 |
| **4. Reviewer (审计/红队)** | 安全合规审计、边界测试、对抗性评审 | `05_审计报告.md` | 具身证据对抗审查，具有独立否定权，阻断隐患（触发指令：“审计”）。 | 当前 Agent 内置 `reviewer` 子代理或只读会话对抗切换 |
| **5. Maintainer (守门/验收者)** | 端到端执行验证、交付凭据归档、基线沉淀 | `07_验收报告.md` | 必须提供真实执行证据；将拍板决策与发版记录同步至全局真源。 | 当前 Agent 内置会话端到端验证 |

### 调度优先序与优雅降级契约 (Dispatch Hierarchy)

各认知模态在执行时的调度解析遵循以下三级优先序：
1. **实例配置优先**：优先读取 [`.data/templates/workspace-config.md`](../../.data/templates/workspace-config.md) 中用户为该角色声明的外置 CLI 与启动命令；
2. **优雅降级兜底**：若实例配置未声明、声明为 `subagent`/`auto`，或探测外置 CLI 不可执行（`which <cli>` 失败）、启动失败、超时或未返回有效报告，系统自动且无缝降级为上表定义的**系统默认承载方式（当前 Agent 内置 Subagent / 会话模态）**；环境恢复可用时，同一事件的后续轮次仍应优先重试外置；
3. **真实留痕声明**：降级时如实在交付物（如审计报告 Front Matter）中记录降级原因，严禁隐式伪造外置独立性；字段契约见「问题终态三分」。

### 方案生命周期指令与模态映射

方案类工作按「调研 → 原型 demo → 方案设计 → 方案审计 → 方案实施 → 汇报落盘」六步指令推进，每步绑定唯一认知模态；落盘门禁、命名与自检统一遵循《文件交付》，本表只做编排映射：

| 指令 | 触发意图（示例） | 模态 | 胶囊产出 | 质量门禁要点 |
|---|---|---|---|---|
| 调研 | `调研`、`出调研`、`做调研`、`调研报告`、`查一下业界方案` | Researcher | `01_调研.md` | 结论/依据/风险/置信度四段式；可联网，来源可溯，事实与推断分离 |
| 原型 demo | `出原型`、`做个原型`、`原型图`、`交互原型`、`demo` | Designer | `03_设计.md` + `prototypes/` | 可打开验证的交互载体；非目标（Non-goals）明确 |
| 方案设计 | `出方案`、`写方案`、`设计方案`、`方案设计` | Designer | `02_方案.md` | 边界、非目标、验收条件齐备；接续「审计/修正」回环 |
| 方案审计 | `审计`、`审一下方案` 等 | Reviewer | `05_审计报告.md` | 执行语义唯一正文为《治理指令》「审计」节，本表仅收录映射 |
| 方案实施 | `实施`、`按方案实施`、`落地方案`、`按方案开发` | Builder | `04_Spec_<ID>.md` + 代码/产物 | 须方案审计终审通过；Spec 契约 + TDD；Tasks.md 认领时点见「方案审修协同闭环」第 6 步 |
| 汇报落盘 | `出汇报`、`写汇报`、`做汇报`、`写周报`、`双周报` | Maintainer | 汇报容器目录 | 数据与事实源 100% 对应；受众与格式先明确；拍板结论同步 `DECISIONS.md` |

各步按「调度优先序与优雅降级契约」解析承载：优先读 [`.data/templates/workspace-config.md`](../../.data/templates/workspace-config.md) 对应角色行；未配置、声明 `subagent` 或外置 CLI 不可执行时，降级为当前 Agent 会话模态自行承载并如实留痕。多步连续触发时按表序串行推进，上一步产出即下一步输入。

### 审计角色选择与降级（唯一正文）

审计角色的选择、降级判定与字段留痕，本节为唯一正文；《治理指令》「审计」节只保留触发意图与受审对象定位，其他文件引用本节，不重复维护。

1. 优先使用用户自定义的审计角色（当前指令明确指定时优先于既有配置），否则读取 [`.data/templates/workspace-config.md`](../../.data/templates/workspace-config.md) 的审计角色配置。
2. 检查配置、启动命令和实际执行结果：未配置、命令不可用、启动失败、超时或未返回有效报告时，降级为当前 Agent 在会话内切换审计角色处理 Major/Minor；Critical 问题的关闭仍须外置复核，或走下方 `waived_by_user` 人工豁免路径。
3. 报告如实记录实际承载、降级原因和审查证据，不把会话内切换标成独立外部审计；不限制同一事件的会话内降级次数。
4. 无论使用何种承载，修正方先响应，审计角色再复核；保留最多 3 轮、同一问题连续 2 轮僵持后转人工的停止条件，避免无限审修。

### 问题终态三分 (Issue Terminal States)

审计问题的状态不是二值（待处理/已关闭），而是三分：

| 终态 | 含义 | 准入条件 |
|---|---|---|
| `closed` | Reviewer 复核通过 | Critical 必须由外置 Reviewer 复核；Major/Minor 会话内承载即可 |
| `open` | 未复核或复核不通过 | 默认态；Designer 的质疑（Challenge）在被 Reviewer 采纳前同样按 `open` 处理 |
| `waived_by_user` | 用户显式风险接受 | 绑定问题 ID、当前受审文件指纹、确认事件与适用范围四项，缺一不可 |

`waived_by_user` 允许实施继续推进，**但不得宣称“独立审计通过”，也不得记为 Reviewer `closed`**；报告与交付说明中必须原样呈现该终态。外置环境恢复后，被豁免的 Critical 仍应补一次外置复核，复核通过才转 `closed`。会话内 Reviewer 不是独立审计的降级形态而是独立性能力缺失——`waived_by_user` 是用户对该缺失的风险接受，不是审计证据，二者不可互相顶替。字段的机器可读契约见 `audit_report.schema.json`。

### 方案审修协同闭环 (Design-Audit-Amend Loop)

方案演进通过认知模态协同形成确定性闭环：
1. **方案初稿**：Designer / Builder 产出业务方案或技术实施规格（`02_方案.md` / `Spec_*.md`）；
2. **对抗审计**：通过“审计”指令唤起 Reviewer 开展独立对抗性评审，在同容器目录下出具 `05_审计报告.md`（或 `Audit_*.md`），给出分级问题与整改建议；
3. **响应修正**：Designer / Builder 通过“修正”指令逐条响应审计报告：接纳项直接改写方案正文（补齐契约、加固防御、调整架构），质疑项阐明客观辩驳理由，并在方案末尾维护《审计意见响应与修订记录》；
4. **复核关闭（Reviewer 独立否定权的落地）**：Reviewer 对第 3 步的每条裁定二次复核——接纳项核验方案正文是否已实质修订，质疑项核验辩驳是否成立；复核通过方可将该问题标记 `closed`，复核不通过则问题保持 `open`，退回步骤 3 进入下一轮；
5. **终审判据与人工锚点**：Reviewer 将全部问题标记 `closed`（或用户对指定 Critical 显式记录 `waived_by_user`）即终审通过；`closed` 状态的 Critical 额外需要人工批量签字确认；同一事件循环达到轮次上限（默认 3 轮，可在方案 Front Matter 的 `audit_max_rounds` 覆盖）仍未收敛，或单条问题连续 2 轮双方立场无变化（僵局），停止自动循环，汇总未收敛问题与双方立场转人工仲裁；外置 Reviewer 连续不可用时，会话内可继续发现问题、复核关闭 Major/Minor、准备修订，Critical 保持 `open` 直至外置复核或用户豁免；
6. **实施准入触发任务流**：方案审修全过程聚焦于方案文档本身，严禁改动 `Tasks.md`；待方案定稿并通过“新迭代/开分支”正式进入开发实施后，方可在 `Tasks.md` 中将对应任务认领为 `active`。

## 归属与演进

1. 同一职责或交接规则只保留一个正文；其他规则和项目入口只链接说明用途。
2. 具体项目的角色 SOP 与协作协议应随项目材料维护；跨项目规则只抽象可移植的共同行为。
3. 当仅是一次性分工、同一 Agent 串行完成工作，或尚无独立验收与交接需求时，使用任务卡，不建立角色或协作规则。
4. 当至少存在两个稳定角色且有重复协作链路、规则已混写，或不同角色需要不同路由、权限或质量门禁时，再考虑按 `roles/` 与 `collaboration/` 目录物理拆分。
5. 新增或修改本规则、角色 SOP、协作协议时，遵循元规则与相应项目的 `AGENTS.md`；涉及 `.system/` 时同时遵循 `01_根系统治理.md`。
