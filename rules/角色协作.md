# 角色协作

适用于需要明确职责归属、跨角色交接或协作验收的任务。它定义规则的归属方法，不预设具体岗位、组织关系、审批链或外部平台。

## 三类对象

| 对象 | 回答的问题 | 唯一真源 |
|---|---|---|
| 能力（Skill） | Agent 能做什么、如何完成一类任务？ | `.system/skills/<skill>/SKILL.md` |
| 角色 SOP | 谁对什么结果负责、可作何种决定、如何达到质量门禁？ | 项目级职责材料；仅稳定且跨项目通用的约束才进入 `.system/rules/` |
| 协作协议 | 两个或多个角色何时交接、交付什么、由谁验收及如何升级？ | 项目级协作协议；仅通用的协议模式才进入 `.system/rules/` |

`AGENTS.md` 只负责薄路由与项目差异，不复制完整角色 SOP 或协作协议。角色名、人员、组织关系、实例时限和外部系统映射属于项目或 `.data/` 实例信息，不得写入通用规则。

## 角色 SOP

只有角色具有稳定、可区分的决策权限、输入输出或质量门禁时，才建立角色 SOP。每份 SOP 必须包含：

1. 目标与责任边界；
2. 输入、输出及其真源；
3. 可自主决定的事项与必须升级的事项；
4. 触发条件、前置条件与执行步骤；
5. 质量门禁、验收证据和失败处理；
6. 与协作协议的引用关系。

角色 SOP 不得重复全局安全规则、其他角色的步骤或协作交接细则。

## 协作协议

仅在存在重复、可验证的跨角色交接时建立协作协议。每份协议必须包含：

1. 参与角色、唯一 DRI 与验收责任人；
2. 触发事件、前置条件和交付状态；
3. 交付物、格式、真源和最小验收标准；
4. 通过、退回、升级的条件与时限；
5. 冲突、缺失信息和异常的处理路径；
6. 所引用的角色 SOP；不得复制其正文。

默认状态为 `待提交 → 验收中 → 通过 / 退回 → 升级`。简单协作只指定 DRI、验收人和必要咨询方；只有确有多方权责歧义时才使用 RACI。


## AI 时代认知模态分工 (Cognitive Personas)

在 AI Agent 具备全栈端到端生产力的体系中，传统职能分工（产品/设计/研发/测试）升级为按 **5 种认知模态** 进行协同演进。各模态可在单人端到端或多 Subagent 流水线中灵活切换，产出统一收敛至主题工作胶囊：

| 认知模态 (Persona) | 核心职责 | 胶囊内标准产出 | 质量门禁 (Quality Gate) |
|---|---|---|---|
| **1. Researcher (探索者)** | 业务背景、文献查新、市面竞品、法规合规 | `01_调研.md` | 严分客观事实与主观推断，标明权威来源，严禁虚构。 |
| **2. Designer (架构/设计师)** | 业务边界、系统方案、非目标、UI/交互原型 | `02_方案.md`、`03_设计.md` | 定义清晰的非目标 (Non-goals)，产出可交互原型验证体验。 |
| **3. Builder (构建者/工程师)** | 技术规格 (Spec)、接口契约、TDD代码实现 | `04_Spec_Tech-N.md`、`06_Changelog.md` | 遵循最小作用量原则，TDD 契约驱动，单 Task 闭环。 |
| **4. Reviewer (审计/红队)** | 安全合规审计、边界测试、对抗性评审 | `05_审计报告.md` | 具身证据对抗审查，具有独立否定权，阻断隐患（触发指令：“审计”）。 |
| **5. Maintainer (守门/验收者)** | 端到端执行验证、交付凭据归档、基线沉淀 | `07_验收报告.md` | 必须提供真实执行证据；将拍板决策与发版记录同步至全局真源。 |

### 方案审修协同闭环 (Design-Audit-Amend Loop)

方案演进通过认知模态协同形成确定性闭环：
1. **方案初稿**：Designer / Builder 产出业务方案或技术实施规格（`02_方案.md` / `Spec_*.md`）；
2. **对抗审计**：通过“审计”指令唤起 Reviewer 开展独立对抗性评审，在同容器目录下出具 `05_审计报告.md`（或 `Audit_*.md`），给出分级问题与整改建议；
3. **响应修正**：Designer / Builder 通过“修正”指令逐条响应审计报告：接纳项直接改写方案正文（补齐契约、加固防御、调整架构），质疑项阐明客观辩驳理由，并在方案末尾维护《审计意见响应与修订记录》；
4. **复核关闭（Reviewer 独立否定权的落地）**：Reviewer 对第 3 步的每条裁定二次复核——接纳项核验方案正文是否已实质修订，质疑项核验辩驳是否成立；复核通过方可将该问题标记关闭，复核不通过则问题保持开放，退回步骤 3 进入下一轮；
5. **终审判据与人工锚点**：Reviewer 将全部问题标记关闭即终审通过；其中 Critical/阻断级问题的关闭额外需要人工批量签字确认（无 Critical 问题的事件全程无需人工介入）；同一事件循环达到轮次上限（默认 3 轮，可在方案 Front Matter 的 `audit_max_rounds` 覆盖）仍未收敛，或单条问题连续 2 轮双方立场无变化（僵局），停止自动循环，汇总未收敛问题与双方立场转人工仲裁；
6. **实施准入触发任务流**：方案审修全过程聚焦于方案文档本身，严禁改动 `Tasks.md`；待方案定稿并通过“新迭代/开分支”正式进入开发实施后，方可在 `Tasks.md` 中将对应任务认领为 `in_progress`。

Reviewer 优先外置（按 `.data/workspace-config.md` 启动独立 CLI 进程），不可执行时降级为会话内切换；降级条件、降级留痕、Critical 必须外置、同事件降级次数上限详见 `指令解析.md`「审计」节。本节遵循的范式即『跨 CLI 审修协调 + 优雅降级』。

## 归属与演进

1. 同一职责或交接规则只保留一个正文；其他规则和项目入口只链接说明用途。
2. 具体项目的角色 SOP 与协作协议应随项目材料维护；跨项目规则只抽象可移植的共同行为。
3. 当仅是一次性分工、同一 Agent 串行完成工作，或尚无独立验收与交接需求时，使用任务卡，不建立角色或协作规则。
4. 当至少存在两个稳定角色且有重复协作链路、规则已混写，或不同角色需要不同路由、权限或质量门禁时，再考虑按 `roles/` 与 `collaboration/` 目录物理拆分。
5. 新增或修改本规则、角色 SOP、协作协议时，遵循元规则与相应项目的 `AGENTS.md`；涉及 `.system/` 时同时遵循 `01_根系统治理.md`。
