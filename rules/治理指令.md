# 审修与系统治理指令

方案审修（审计、修正）与 Entropaxis 控制面治理（自检、工具化、Skill 分发）的显式指令语义。通用任务解析见《指令解析》；日常业务动作见《工作流指令》；新迭代、开分支、发版见《软件工程》。

## 审计

对当前项目、目录或分支中最新的方案或实施规格做对抗性审计，输出结构化报告。

1. **触发意图**：`审计`、`方案审计`、`审核方案`、`评审方案`、`独立审计`、`找独立审计师`、`审一下这个方案`、`审修`、`审修回环` 等。`审修`、`审修回环`同时唤起审计与修正。只审一段代码或一个函数（`审一下这段代码`）按普通代码评审处理，不触发本机制。
2. **受审对象定位**：在当前项目、事务胶囊或 Git 分支中检索最新的 `02_方案.md`、`04_Spec_<ID>.md`、独立 Spec `<ID>_中文主题.md` 或最近修改的独立方案文档；多个候选时先列出并确认。
3. **审查维度**：以 Reviewer 模态独立评审——业务完备性（需求与边界是否覆盖、有无悬空分支）、架构与技术可行性（YAGNI、接口契约、过度设计、性能瓶颈）、安全与边界防御（越权、数据敏感、单点故障、降级缺失）、可验证性（验收标准可测、验证路径完备）。
4. **承载与降级**：Reviewer 是硬门禁角色，调度与失败裁决见 [`角色协作.md`](角色协作.md)「门禁划分」，问题终态见同文「问题终态三分」，本节不复述。
5. **产物与生命周期**：
   - 事务胶囊内落盘 `05_审计报告.md`；独立 Spec 对应 `Audit_<ID>_主题方案审计.md`（同容器目录）。
   - 字段与结构契约唯一真源：[`audit_report.schema.json`](../schemas/audit_report.schema.json)（`schema_version: 3` 起机器状态只在正文唯一的 ````audit-state```` 围栏 JSON 中；旧版本报告只读兼容，不批量改写）。报告须含受审对象路径与指纹、结论总览（通过/附条件通过/阻断退回）与分级问题（Critical/Major/Minor，含现象、根因、整改建议）。
   - 同一目标谱系且尚未终审通过的复审属同一审计事件：在原报告中逐轮追加受审指纹、结论与问题关闭情况，不新建副本；终审通过后冻结，目标变化时新建事件并引用前序报告。
   - 报告模板与逐步执行见 `artifact-audit` Skill；审修全过程不改 `Tasks.md`。
6. **关闭门禁**：任何 Critical 改为 `closed` 或 `waived_by_user` 前，必须运行并确认退出码为 0：
   ```bash
   python3 .entropaxis/tools/check_audit_gate.py --candidate <候选报告路径> --commit <目标路径>
   ```
   该工具校验报告契约、外置承载、目标指纹与豁免记录，全部通过才原子写入。
7. **物理动作闭环**：按《文件交付》第 4 节用 `open_file.py` 打开审计报告。

## 修正

根据审计报告逐条接纳或质疑，并把结论写回方案真源。

1. **触发意图**：`修正`、`修正方案`、`根据审计修正`、`响应审计报告`、`方案修正`、`审修`、`审修回环` 等。
2. **定位**：在当前上下文定位最新方案（`02_方案.md` / `Spec_*.md`）及其审计报告（`05_审计报告.md` / `Audit_*.md`），确认二者属于同一审计事件。
3. **逐条裁定**：以方案作者模态（`02_方案.md` 为 Architecture，Spec 为 Builder）处理每条意见：
   - **接纳**：写明修订点，并把实质变更改写进方案正文对应章节；
   - **质疑**：对超出需求范围、脱离实际约束或存在技术误解的意见，列出事实、边界依据与理由。
   - 裁定不等于关闭：是否关闭由 Reviewer 下一轮复核决定（《角色协作》「方案审修协同闭环」第 4 步）。
4. **就地更新**：直接改写原方案，不新建 `v2.md` / `修正方案.md`；在方案末尾维护 `## 审计意见响应与修订记录`（问题与级别、决策、修订说明或理由、章节锚点）；更新 Front Matter 的 `status: revised` 与日期；不改 `Tasks.md`。
5. **物理动作闭环**：按《文件交付》第 4 节打开更新后的方案。

## 系统自检

对 Entropaxis 控制面自身做一次全面检查，不涉及业务项目内容。

1. **触发意图**：`系统自检`、`自检`、`Entropaxis 自检`、`分发自检`、`检查一下根系统` 等。`分发自检`指本机制第三遍的收件方视角求值，不是独立机制。
2. **执行**：唤起 `self-check` Skill，一条命令跑完元规则公理核对、双重体检门禁与收件方视角分发求值：
   ```bash
   python3 .entropaxis/tools/report_selfcheck.py
   ```
   退出码 0=全绿、1=有阻断项；检查范围与人工补充项见该 Skill。
3. **产物**：会话内输出「验证结论 + 可优化项」两节，结论取 通过 / 阻断 / 未验证。无机械检查器承接的公理报未验证，不因"本轮未改动"判通过；可优化项只列有实质动作的条目。不强制落盘。

## 机制转工具 / 制作工具 (Tool Crafter)

把高频机制、复合命令、脚手架或数据校验逻辑按《工具设计》规范转成系统级 Python 工具。

1. **触发意图**：`机制转工具`、`制作工具`、`创建工具`、`机制工具化`、`自动化`、`tool-crafter`、`toolify` 等。`自动化`仅指把重复机制转为 Tool 或 Skill；`自动化测试`、`自动化部署`属软件工程语境，不触发本机制。
2. **执行**：唤起 `tool-crafter` Skill，按 [`工具设计.md`](工具设计.md) 第 2 节五维准入审查（不满足即说明理由并转为 Rule 或 Skill），再按其第 4 节六步闭环实现、测试、体检、装配与交付验证。

## 分发 / 打包 Skill

用户明确说"分发 `<skill-name>` skill""打包 `<skill-name>` skill"或同义表达时，按《技能设计》2.3 节执行：仅生成本地 ZIP、核验内容并打开 ZIP 所在目录。此操作不构成对外发送；上传、发送或公开发布须另行授权并遵循《文件交付》第 5 节。
