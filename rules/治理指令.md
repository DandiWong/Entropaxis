# 治理指令

面向 Entropaxis 控制面与工程仓库自身的显式指令语义。通用任务解析见 [`指令解析.md`](指令解析.md)；日常业务动作见 [`工作流指令.md`](工作流指令.md)。

## 审计

用于对当前项目、文件夹或分支中已经出现的最新的方案进行对抗性审计，并输出结构化审计报告。

1. **触发意图**：用户输入 `审计`、`方案审计`、`审核方案`、`评审方案`、`对最新方案进行审计`、`审修`、`审一下这个方案` 等。`审修`指代审计+修正整个回环，两个机制同时唤起。
2. **受审对象定位**：
   - 自动在当前上下文（当前所在项目、当前目录/主题工作胶囊文件夹、或当前 Git 分支）中检索最新出现的方案或实施规格；
   - 优先匹配当前主题工作胶囊内的 `02_方案.md` 或 `04_Spec_Tech-N.md`、代码工程库内的 `docs/YYYYMMDD_主题/Spec_<ID>_主题方案.md`、或最近修改的独立方案文档；
   - 存在多个候选或方案歧义时，先向用户说明已定位的候选方案并确认。
3. **审计认知模态与审查维度**：
   - 切换为 **Reviewer (审计/红队)** 认知模态，开展独立对抗性评审与深度合规/架构/可行性核验；
   - 审计维度涵盖：
     - **业务完备性**：是否覆盖既定业务需求与全流程边界，有无悬空逻辑或未定义分支；
     - **架构与技术可行性**：是否遵循最小作用量（YAGNI）、接口契约是否清晰、是否存在过度设计或性能瓶颈；
     - **安全性与边界防御**：是否存在越权漏洞、数据敏感性隐患、单点故障或异常降级缺失；
     - **可验证性与质量门禁**：验收标准是否清晰可测，测试用例与验证路径是否完备。
4. **Reviewer 承担与降级**：调度优先序、降级判定、字段留痕唯一正文见 [`角色协作.md`](角色协作.md)「审计角色选择与降级」与「问题终态三分」，本节不复述。
5. **产物规范与连续生命周期**：
   - 主题工作胶囊内落盘为 `05_审计报告.md`；代码工程独立 Spec 对应落盘为 `Audit_<ID>_主题方案审计.md`（收敛于同容器目录下）；
   - 报告须包含 YAML Front Matter（`type: Audit`、`topic`、`date`、`author: Reviewer`、`status: active`、`schema_version`、`reviewer_mode`、`reviewer_ref`、`target_path`、`target_sha256`）、受审对象路径与指纹、审计结论总览（通过/附条件通过/阻断退回）、分级问题清单（Critical 阻断级、Major 严重级、Minor 建议级，包含现象、根因、整改建议）；每条问题须以 `级别: Critical/Major/Minor`、`ID:` 与 `状态: open/closed/waived_by_user` 标注，供 `check_audit_gate.py` 机械识别；完整字段契约见 [`.system/schemas/audit_report.schema.json`](../schemas/audit_report.schema.json)；`schema_version < 2`（或缺失）的历史报告按旧 `independence` 字段只读兼容解析，不批量改写；
   - 遵循连续审计事件生命周期：同一审计事件复审时在原报告中逐轮追加受审指纹与问题关闭记录，不新建碎片副本；方案审计全过程严禁改动 `Tasks.md`。
6. **终审判据与人工锚点**：终审通过条件、轮次上限与人工仲裁触发见 [`角色协作.md`](角色协作.md)「方案审修协同闭环」第 5 步，本节不复述。**任何一条 Critical 问题状态改为 `closed` 前，必须运行 `python3 .system/tools/check_audit_gate.py --candidate <候选报告路径> --commit <目标路径>` 并确认退出码为 0**；该工具校验 `reviewer_mode` 为 `external`（会话内承载不可将 Critical 置 `closed`）、`target_sha256` 与目标文件实测哈希一致、拟置 `waived_by_user` 的问题有结构完整且指纹匹配的 `critical_ack`，全部通过才原子写入，任一项不通过则非零退出且不写入。
7. **物理动作闭环**：严格遵循《文件交付》第 4 节，落盘后通过 `open_file.py` 打开生成的审计报告。

## 修正

用于根据当前项目、文件夹或分支中出具的审计报告，对审计意见逐条进行质疑或接纳，并把质疑或接纳更新到方案真源。

1. **触发意图**：用户输入 `修正`、`修正方案`、`根据审计修正`、`响应审计报告`、`方案修正`、`审修` 等。
2. **方案与审计报告定位**：
   - 自动在当前上下文（当前项目/文件夹/分支）中定位最新出具的方案文档（如 `02_方案.md` / `Spec_*.md`）及对应的审计报告（如 `05_审计报告.md` / `Audit_*.md`）；
   - 确认二者属于同一次方案设计与审计事件。
3. **执行决策响应矩阵 (Accept vs. Challenge)**：
   - 切换为 **Designer / Builder** 认知模态，逐条审查审计报告中列出的各级问题与建议；
   - 对每条审计意见进行明确裁定：
     - **接纳 (Accept)**：认可该意见，明确具体修订点，并将实质变更直接改写到方案正文的对应章节（如补全接口契约、加固防御机制、调整架构设计）；
     - **质疑 (Challenge / Reject)**：对不合理、超出需求范围（Non-goals）、脱离实际约束或存在技术误解的意见，列出充分客观的辩驳事实、边界依据与理由。
   - 本步骤产出的接纳/质疑均为 Designer/Builder 的裁定意见，不直接构成问题关闭：是否关闭由 Reviewer 在下一轮复核确认（见 `角色协作.md` 方案审修协同闭环第 4 步），Reviewer 驳回裁定则问题保持开放。
4. **方案真源更新闭环**：
   - **单一真源就地更新**：直接在原方案文档中改写，严禁新建 `v2.md` / `修正方案.md` 等冗余副本；
   - **响应记录持久化**：在方案文档末尾维护 `## 审计意见响应与修订记录` 章节，以表格或结构化条目完整记录：审计问题与级别、响应决策（接纳/质疑）、修订说明或辩驳理由、对应章节锚点；
   - 更新方案 Front Matter 中的状态（如 `status: revised`）与修改日期；方案修正阶段聚焦于方案本身，严禁改动 `Tasks.md`。
5. **物理动作闭环**：严格遵循《文件交付》第 4 节，落盘后通过 `open_file.py` 打开更新后的方案文件。

## 系统自检

用于对 Entropaxis 控制面自身健康度做一次全面检查，不涉及业务项目内容本身。

1. **触发意图**：用户输入 `系统自检`、`自检`、`Entropaxis 自检`、`分发自检`、`检查一下根系统` 等。`分发自检`不是独立机制，指本机制第四遍的收件方视角求值。
2. **检查范围**：`.system/` 各子目录（清单以 `lint_workspace.py` 的 `SYSTEM_REQUIRED_DIRECTORIES` 为准，不在此复制会漂移的名单）及其部署产物（根 `AGENTS.md`/`CLAUDE.md`）；不含 `.data/` 与各业务项目自身内容，但需递归核验全工作区项目 `AGENTS.md`/`CLAUDE.md` 的结构契约（单锚点回链、零废弃引用、薄壳纯净度、声明外置悬空兜底），不评判项目业务内容本身。
3. **两遍检查**：
   - 第一遍依据 `00_元规则.md` 九条公理逐条核对 Entropaxis 现状；
   - 第二遍依据 `01_根系统治理.md` 规则审计流程与完成标准执行，含运行 `python3 -m unittest discover -s .system/tests -t .system` 与 `python3 .system/tools/lint_workspace.py` 双重体检。
   - 第三遍运行 `python3 .system/tools/audit_routing.py` 核验指令路由覆盖率与各场景上下文成本：正向命中与防误触发须全清，语义盲区条目须逐条判断是否补登触发词。
   - 第四遍运行 `python3 .system/tools/check_distribution.py` 完成收件方视角求值（[`01_根系统治理.md`](01_根系统治理.md) 演进准则第 8 条「多状态求值」）：以版本库跟踪集重建收件方工作区并实跑初始化链路，阻断项非空即判定本轮自检不通过。
4. **CLAUDE.md 违规自动改写**：追加执行 `python3 .system/tools/lint_workspace.py --fix-claude-md`，检测到非纯薄壳的项目 `CLAUDE.md` 直接改写为标准形式（一行标题 + `@AGENTS.md`）；既有排除名单、符号链接例外与嵌套独立 git 仓库排除照旧生效，不触碰上游/第三方内容。
5. **产物（路由审计 + 验证结论 + 可优化项）**：会话内输出系统自检报告，章节严格仅保留三部分：
   1. **路由审计**：含①覆盖率（正向命中/防误触发/语义盲区计数）；②各场景上下文成本明细表（3 列：场景、消耗 token 数（纯场景增量，不含首行核心常驻，用 K/M 量级缩写）、价值（按 Sonnet-5 折算，$2/MTok，格式 $0.0001）；「核心常驻」单独列首行表示零动作基线；末行「所有场景总计」含核心常驻不重复计算）；③最重场景逐文件明细；④语义盲区逐条列出。
   2. **验证结论**：给出「检查对象、证据、结论、未覆盖范围」，结论取通过/阻断/未验证；证据一律引用本轮双重体检的实测锚点与命中数，严禁凭语感给结论。五个审阅维度的提示与已知盲区见 [`软件工程.md`](软件工程.md)「检查按影响选」，命中已知盲区条目时须补一句人工核查结论。
   3. **可优化项**：实行异常上报制，**只列举存在实质优化空间的条目，严禁罗列“维持现状”、“无需整改”、“予以保留”等无动作项目**：包含 Token 差额 >50% 且具备明确兑现方式的机制、有待补登的语义盲区口语词、待仲裁退役的规则候选，或体检/分发中需实质改进的建议项。若全项健康无可优化动作，则直接说明本轮无待优化项。不强制落盘报告；确有必要落盘时遵循《文件交付》第 1 节触发门禁与 2.6 节根系统研究产物归属。

## 新迭代 / 新 Feature

用于检查当前分支健康度，完成测试验证与原子提交，合入主干并检出新工作分支开启新迭代。

1. **触发意图**：用户输入 `新迭代`、`新 feature`、`new feature`、`feature`、`开始新迭代`、`开新分支` 等。
2. **适用范围**：应用代码仓库与工程项目（遵循《软件工程》研发迭代标准闭环）。
3. **五步执行闭环**：
   1. **分支健康度检查 (Health Check)**：检查 `git status --short --branch` 与未追踪文件，排查未完成改动、未暂存脏数据或未闭环状态；
   2. **自动化测试与质量门禁（该测测）**：运行项目全量单元测试、集成测试与代码检查（Lint/体检），确保当前分支 100% 绿灯通过；若存在失败测试或编译报错，必须就地修复或提示阻断，严禁带病推进；
   3. **履历记录与原子提交（该提交提交）**：核对本次已完成任务，在 `docs/Changelog.md` 追加变更条目（遵循 Keep a Changelog 规范），在 `docs/Tasks.md` 中将对应 Task 标记为完成 (`done`)，执行规范的单 Task Git Commit（提交信息注明 Task ID 与摘要）；
   4. **合入主干（该合并到 main 合并到 main）**：切换至主干分支（`main` 或默认主干），将已验证通过的功能分支合并至主干（Fast-Forward 或 Merge/Squash），并在主干确认测试通过与工作区干净；
   5. **检出新分支开启新迭代（开新分支）**：从干净的 `main` 主干检出并创建新的独立工作分支（命名规范：`feat/<topic>` 或 `feat/Task-<ID>-<topic>`，用户已指定分支名时按指定名称创建）。**开辟新分支正式进入开发实施后，方可在 `docs/Tasks.md` 中将新迭代的任务认领并置为 `active`**（外部看板端仍可能显示 `in_progress`，本地真源统一为 `active`）。

## 机制转工具 / 制作工具 (Tool Crafter)

用于扫描工作区高频机制、复合命令、脚手架或数据校验逻辑，按照《工具设计》的 ApX 工程规范，标准化转化为系统级 Python 工具。

1. **触发意图**：用户输入 `机制转工具`、`制作工具`、`创建工具`、`机制工具化`、`自动化`、`tool-crafter`、`toolify` 等。`自动化`仅指把重复机制转为 Tool 或 Skill；`自动化测试`、`自动化部署`属于软件工程语境，不触发本机制。
2. **执行流程（唤起 `tool-crafter` Skill）**：
   1. **五维准入审查**：对照 [`工具设计.md`](工具设计.md) 第 2 节核验确定性、频次>2、安全收敛、Token ROI与零系统绑定 5 项判据；不满足则说明理由并转为 Rule 或 Skill；
   2. **接口契约设计 (Spec)**：设计动词_名词命令名、参数类型、结构化输出及行动导向的 `ToolError` 自愈指引；
   3. **纯标准库实现 (Code)**：基于 `tool.template.py` 编写 `.system/tools/<name>.py`，严格使用纯 Python 内置标准库，杜绝外部 pip 依赖；
   4. **自动化单测驱动 (TDD)**：在 `.system/tests/test_<name>.py` 编写完整单元测试，覆盖正常输出与异常阻断；
   5. **双重体检门禁 (Verify)**：运行 `unittest` 与 `lint_workspace.py`，确保单元测试与工作区体检 100% 绿灯；
   6. **路由装配与验证**：在 `.data/rules/tips.md` 注册操作入口，按《软件工程》「检查按影响选」给出交付验证结论。

## 分发 / 打包 Skill

用户明确说“分发 `<skill-name>` skill”“打包 `<skill-name>` skill”或同义表达时，按《技能设计》6.3 节执行：仅生成本地 ZIP、核验内容并打开 ZIP 所在目录。此操作不构成对外发送或发布；用户若要求上传、发送或公开发布，仍须另行取得对应授权并遵循《对外发布》。

## 注册 Skill / 注册到 Entropaxis / 注册到根系统

用于将第三方、开源或新开发的 Skill 导入、自检并纳管至 Entropaxis 根系统（`.system/skills/`）中，建立长期标准能力支持。

1. **触发意图**：用户输入 `把xx skill注册到Entropaxis`、`注册到根系统`、`注册Skill`、`安装并注册Skill`、`将xx纳入Entropaxis` 等。
2. **执行流程（标准 5 步）**：
   1. **获取与落位**：通过 `npx skills add <package>` 或源码拉取，将 Skill 完整目录落位至 `.system/skills/<skill-name>/`；
   2. **架构合规化改造（对照《技能设计》）**：
      - 检查并确保包含合规的 `SKILL.md`（YAML Frontmatter 需包含动名词 `name` 及符合第三人称的 `description`）；
      - 检查并补齐 `CHANGELOG.md`（遵循 Keep a Changelog 1.1.0 规范）；
      - 核验依赖与脚本安全，去除对外部私有环境或不必要外部依赖的硬绑定；
   3. **双重体检门禁 (Verify)**：运行 `python3 -m unittest discover -s .system/tests -t .system` 与 `python3 .system/tools/lint_workspace.py`，确保 Skill 命名、元数据及工作区体检全绿；
   4. **入口联动与同步**：在 `.data/rules/tips.md` 追加该 Skill 的操作提示（如适用），执行 `python3 .system/tools/bootstrap.py` 确保根入口物理同步；
   5. **验证与交付**：按《软件工程》「检查按影响选」给出交付验证结论并交付。
