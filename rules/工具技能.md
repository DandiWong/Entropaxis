# 工具与技能治理 (工具技能)

本规则是工作区中**能力扩展形态判定（Rule vs Skill vs Tool vs Script）、Tool 工具化准入与 ApX 设计契约、Skill 设计方法与 Claude 官方最佳实践**的唯一真源。所有在工作区内新增、重构或维护 Tool 与 Skill 的操作均遵循本规则。

---

## 0. 能力扩展形态判定模型 (Taxonomy)

面对任意业务需求、机制沉淀或流程自动化时，按以下模型裁定唯一主形态，严禁形态错位：

| 扩展形态 | 核心适用特征 | 归属路径与载体 | 典型示例 |
|---|---|---|---|
| **1. 规则 (Rule)** | 长期行为约束、安全红线、主观裁决标准、防错机制 | `.system/rules/*.md` 或项目 `AGENTS.md` | 《文件交付》、《01_根系统治理》 |
| **2. 工具 (Tool)** | 纯确定性算法、机械 I/O 计算、安全收敛 CLI、体检脚本 | `.system/tools/<name>.py`（纯标准库） | `init_project.py`、`lint_workspace.py` |
| **3. 技能 (Skill)** | 多阶段复合 SOP、交互式访谈引导、包含模板渲染的业务能力 | `.system/skills/<name>/SKILL.md` | `tool-crafter`、`ppt-design`、`init-project` |
| **4. 局部脚本 (Script)** | 单项目专属的一次性数据修复、私有迁移临时脚本 | `03_工程研发/<app>/scripts/` | `migrate_db.py`、`generate_test_report.py` |

# 第一篇：Tool 工具设计、准入与工程治理 (ApX 体系)

## 1. 机制检索四大信号源 (Signal Sources)

Agent 在日常开发、复盘与系统治理中，通过扫描以下 4 类信号识别潜在工具化候选：

1. **高频复合终端命令 (Terminal Drift)**：会话中频繁出现 3 步以上长管道命令（如 `find | grep | awk | sed`、复合 git log 处理），跨平台语法脆弱；
2. **规则文档中的机械硬算 (Rule Bloat)**：规则中描述了大量路径深度、正则校验、Front Matter 回填等纯机械步骤，耗费 Token 且易漂移；
3. **模型易幻觉盲区 (Hallucination Hotspots)**：涉及 SHA-256 计算、字节精确比对、AST 语法检查等，大模型难以保证字符级精确；
4. **高危易扩散破坏动作 (Blast Radius Hazards)**：涉及批量清理、状态重置，需收敛为受控参数 API 防范破坏。

## 2. 工具化五维准入漏斗 (Five-Dimensional Admission Funnel)

必须同时满足以下 5 项硬性判据方可准予转化为 Tool：

| 判据维度 | 核心衡量标准 | 准入要求 (Pass) | 淘汰标准 (Reject ➔ 转入 Rule/Skill) |
|---|---|---|---|
| **1. 确定性 (Determinism)** | 是否具备唯一的、无歧义的输入输出映射？ | 纯确定性计算、I/O 转换、格式校验 | 依赖主观审美、开放式创意生成、复杂语义理解 |
| **2. 复用频次 (Frequency)** | 是否跨 2 个以上项目复用，或核心工作流高频刚需？ | 跨项目通用原子能力，或核心工作流高频刚需 | 一次性特定数据修复、孤立单点操作 |
| **3. 安全收敛 (Safety)** | 能否将开放式危险操作收敛为参数受控的 API？ | 将危险 Shell 收敛为带前置类型与白名单校验的 CLI | 依然需要完全开放的任意命令执行能力 |
| **4. 效能收益 (Token ROI)** | 转化为工具后是否显著节省 Token 与执行轮次？ | 1 行 Tool 调用替代 50+ Token 的 CoT 思考与多轮试错 | 逻辑极其微小（1 行普通命令），工具化反而增加认知负荷 |
| **5. 零系统绑定 (Neutrality)** | 能否与具体商业系统名、端口、私有协议解耦？ | 纯 Local-First 标准库实现，配置声明外置 | 强依赖特定远程商业 SaaS 私有 API 且不可降级 |

## 3. ApX 高级工具设计契约 (Tool Interface Design)

1. **语义化 CLI 契约**：采用 `动词_名词.py` 命名，`argparse` 标准自省参数与前置清洗；
2. **行动导向的错误契约 (Actionable Error Contract)**：报错严禁仅抛裸异常堆栈，必须输出 `❌ 错误原因` + `👉 修复建议`（明确指导 Agent 如何自愈修改参数）；
3. **结构化输出**：标准输出（stdout）必须为纯 JSON 或固定 Key-Value 分段纯文本，杜绝无意义废话；
4. **原子组装与幂等性**：新建/写入类工具必须在 `tempfile.TemporaryDirectory` 中原子组装校验，全部通过后再原子替换，支持幂等重入。

## 4. 机制转 Tool 标准 6 步自迭代闭环 (SOP)

```text
Step 1: 契约设计 (Spec)     ➔ 定义参数列表、输入输出 Schema 与行动导向错误自愈指引
Step 2: 标准库实现 (Code)   ➔ 编写 .system/tools/<tool_name>.py（纯标准库 + 原子暂存）
Step 3: 测试驱动验证 (TDD)  ➔ 编写 .system/tests/test_<tool_name>.py（覆盖正常与异常分支）
Step 4: 双重体检门禁 (Lint) ➔ 运行 unittest（100%通过）与 lint_workspace.py（编译与体检全绿）
Step 5: 路由与上层装配 (Wire)➔ 挂载至对应 Skill（如 tool-crafter），并在 .data/tips.md 登记
Step 6: 五维架构评估 (5D)   ➔ 依据五维评估模型输出量化打分表准予交付
```

# 第二篇：Skill 技能设计、架构与最佳实践 (Claude 体系)

## 5. Skill 核心设计哲学 (Core Principles)

### 5.1 极度克制与 Token 预算意识 (Conciseness is Key)
- **上下文窗口是共享公共资源**：Skill 正文与系统提示词、对话历史、其他 Skill 元数据竞争上下文窗口；
- **默认假设模型已经很聪明**：只提供模型尚不具备的领域专有上下文，避免过度解释通用编程或文件基础概念；
- **自问自查准则**：对编写的每句话质问：*“模型真的需要这个解释吗？这一段值得它的 Token 成本吗？”*；
- **冷启动轻量化**：系统启动时仅预加载所有 Skill 的 Frontmatter 元数据（`name` 与 `description`），正文仅在触发相关时按需读取。

### 5.2 自由度阶梯匹配 (Degree of Freedom Ladder)
根据任务的脆弱性与可变性，精准设定 Skill 的指导自由度：
1. **高自由度（启发式指引，开阔田野）**：
   - 适用场景：多种解法均有效、决策强依赖上下文、由原则指导（如代码审查、设计评估、头脑风暴）；
   - 表达形式：文本要点清单、评估维度与设计准则。
2. **中自由度（参数化模板，带护栏小径）**：
   - 适用场景：存在首选模式但允许根据输入定制（如生成特定格式报告、配置生成）；
   - 表达形式：可填空的模板框架、伪代码或带可选参数的脚本。
3. **低自由度（确定性脚本，狭窄桥梁）**：
   - 适用场景：操作脆弱易错、必须严格按顺序执行、零容错（如数据迁移、环境发布、特定字节级格式导出）；
   - 表达形式：精确命令与强制脚本（如 `python scripts/migrate.py --verify`），显式约束“严禁修改参数或跳步”。

## 6. 渐进式披露架构 (Progressive Disclosure Architecture)

### 6.1 单跳引用与 500 行预算铁律 (Single-Hop & 500-Line Budget)
- **入口极简**：`SKILL.md` 正文严格控制在 **500 行以内**，仅作为高层概览与导航目录；
- **单跳引用铁律 (Single-Hop Rule)**：所有参考资料从 `SKILL.md` 直接链接（深度严格为 1），**严禁深层嵌套引用**（如 `SKILL.md` ➔ `A.md` ➔ `B.md`），防止模型在部分读取时丢失完整上下文；
- **大文件顶部目录**：超过 100 行的参考文档（`references/*.md`），顶部必须包含 Markdown 目录大纲，便于切片读取。

### 6.2 读写分离与自包含目录结构 (Directory Organization)
标准 Skill 采用自包含模块化目录树：
```text
.system/skills/<skill-name>/
├── SKILL.md                 # [必选] 触发条件、高层概述与步骤工作流 (≤500行，按需加载)
├── CHANGELOG.md             # [必选] 遵循 Keep a Changelog 的语义化版本记录
├── references/              # [可选] 领域详细规范、API 说明、词表 (按需加载，单跳引用)
├── templates/               # [可选] 可执行或可填充的模板 (如 generate_deck.py, spec 模板)
└── scripts/                 # [可选] 供 Agent 物理执行而非加载阅读的工具脚本 (执行不占上下文)
```
- **可分发边界**：可分发 Skill 的正文、元数据、内置资产与出处说明不得引用工作区专属 `.data/` 声明、内部项目目录、绝对路径或仅内部可访问的定位信息；运行所需资产必须随包内置。内部源定位、更新记录与审核信息仅存于受控维护记录，且不得成为阅读或运行该 Skill 的前置条件。

### 6.3 Skill 分发包 (Distribution Package)

用户明确说“分发 / 打包 / 导出 `<skill-name>` skill”时，执行本节；该动作只生成本地 ZIP，不发送、发布或上传至外部系统。

1. **先审计，再暂存**：从 `.system/skills/<skill-name>/` 定位当前有效目录，依据 `SKILL.md` 的直接工作流、脚本导入与内置资产引用建立分发清单；在临时目录组装，不直接把整个工作区或父目录压缩。
2. **仅纳入运行必需内容**：保留 `SKILL.md`、`CHANGELOG.md`、运行直接引用的 `references/`、`templates/`、`scripts/`，以及内置上游资产依法必须保留的许可证。非运行必需的测试、样例、演示/生成器、开发清单、构建产物、日志、旧归档与本机配置不入包。
3. **硬性排除**：严禁纳入 `.git/`、`.data/`、凭证、绝对路径、`__pycache__/`、`*.pyc`、`node_modules/`、编辑器/系统缓存或其他工作区实例文件。无法判定某文件是否为运行必需时，保留并在交付中说明，不得为缩包猜测删除。
4. **归档契约**：生成与 Skill 目录同级的 `<skill-name>.zip`，ZIP 顶层仅含 `<skill-name>/`；用户的“分发”指令构成覆盖同名本地归档的明确授权。创建后核验归档可读、顶层目录正确且无第 3 条排除项。
5. **物理交付**：核验通过后，调用系统默认文件管理器**打开 ZIP 所在目录**，而非仅回报路径；最终回复写明归档路径、校验结果和未纳入的类别。

## 7. 元数据与精准发现机制 (YAML Frontmatter & Discovery)

### 7.1 Frontmatter 规范
- **`name`**：小写字母、数字和连字符，≤64 字符，推荐**动名词形式**（如 `ppt-design`、`tool-crafter`、`processing-pdfs`）；
- **`description`（发现核心）**：
  - **强制第三人称**：必须以第三人称编写（如 `"Generates executive presentations..."`，严禁使用 `"I can help..."` 或 `"You can use..."`，防止系统提示词视角混乱）；
  - **明确“做什么 + 何时触发”**：同时阐明核心能力与具体触发场景、意图关键词、文件后缀（≤1024 字符）。

## 8. 工作流、可复制清单与反馈循环 (Workflows & Feedback Loops)

### 8.1 复杂任务 Progress Checklist 模式
对于多阶段任务，在 `SKILL.md` 中提供模型可复制到对话中逐项打勾的进度清单：
```markdown
Task Progress:
- [ ] Step 1: 扫描并提取上下文 (Phase 1)
- [ ] Step 2: 方案契约设计 (Phase 2)
- [ ] Step 3: 代码/制品生成 (Phase 3)
- [ ] Step 4: 质量门禁验证 (Phase 4)
```

### 8.2 质量门禁与反馈闭环 (Self-Correction Loop)
- 每个阶段设置明确的验收证据（Pass/Fail 判据）；
- 验证失败时显式指导回退步骤，形成确定性自愈闭环。

# 第三篇：共同合规红线 (Compliance Redlines)

1. **Local-First 纯标准库铁律**：Tool 与 Skill 辅助脚本严格仅使用 Python 内置标准库，零外部第三方 pip 依赖；
2. **零系统绑定与声明外置**：严禁硬编码具体业务机构名、商业品牌名、测试环境端口（`127.0.0.1`）或私有密钥；
3. **凭证隔离存储**：Skill 所需凭证统一保存于 `.data/credentials/<skill-name>/`，由 `.gitignore` 排除；
4. **物理交付与双保险契约**：凡生成/导出 `.pptx`、`.docx`、`.xlsx`、`.pdf`、图片或独立文件的 Skill，尾部必须显性包含调用系统默认程序打开文件的物理交付闭环；
5. **三权分立与空间纯净**：控制面在 `.system/`，凭证与实例数据在 `.data/`，严禁污染工作区根目录。
