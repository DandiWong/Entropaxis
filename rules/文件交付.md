# 文件交付

> **适用范围**：工作区内所有涉及新建、修改、导出、生成、存储或移动通用传递格式文件（如 `.docx`、`.xlsx`、`.csv`、`.pptx`、`.pdf`、`.png`、`.jpg`、`.svg` 等）及独立文档交付物时的通用规范与交付门禁。

---

## 1. 文档落盘触发门禁

并非每个问答、讨论或验证动作都要生成磁盘文件。日常技术咨询、命名建议、方案探索直接在对话中交互完成；运行测试默认只保留终端结果，不据此自动生成 HTML/Markdown 测试报告。

**仅当用户明确要求落档，或 Agent 询问“是否需要落入文档”并获得明确许可后，方可创建调研、方案、说明、报告/汇报等独立交付物。**

---

## 2. 交付物命名规范（单一真源）

新建调研、方案、汇报、设计、原型、报告、需求等业务交付物及软件开发 Spec 时，统一采用如下规范：

### 2.1 业务与通用交付物命名规范（中文主命名，强制铁律）
适用于工作区内所有一般文件、调研、方案、汇报、设计、原型、评估、报告、会议纪要等业务与管理交付物：

* **标准命名格式（容器带日期，文件不带日期）**：
  * **容器目录格式**：
    * **含甲乙方 / 双边合作场景**：`{{yyyymmdd}}_{{甲方}}&{{乙方}}_{{主题}}/`
    * **单方 / 通用场景**：`{{yyyymmdd}}_{{主题}}/`
  * **主文件命名格式（文件本身不加日期）**：
    * **含甲乙方 / 双边合作场景**：`{{甲方}}&{{乙方}}_{{主题}}.<ext>`（例如 `20260901_某公司&某医院_某课题协作方案/某公司&某医院_某课题协作方案.docx`、`20260901_某甲方&某乙方_合作会议纪要/某甲方&某乙方_合作会议纪要.docx`）
    * **单方 / 通用场景**：`{{主题}}.<ext>`（例如 `20260901_智能质检方案/智能质检方案.pptx`、`20260901_多租户协作设计/多租户协作设计.md`）
* **中文主题结构约束**：
  * **结构公式**：`[≤8字核心主词/定语] + [交付物类型词]`（核心主题词一般不多于 8 个中文字符，后接标准类型词）。
  * **标准类型词**：`调研`、`方案`、`汇报`、`设计`、`原型`、`报告`、`评估`、`评审`、`纪要` 等（例如：`智能质检方案`、`协作架构设计`、`临床评估报告`、`知识库接入调研`）。
* **容器化目录强制铁律**：
  * 所有独立交付物必须以容器目录组织（`{{yyyymmdd}}_{{甲方}}&{{乙方}}_{{主题}}/` 或 `{{yyyymmdd}}_{{主题}}/`），严禁在父级目录平铺散落单文件；
  * 容器目录内主文档与容器去日期后的主题名一致（即 `{{主题}}.<ext>` 或 `{{甲方}}&{{乙方}}_{{主题}}.<ext>`）；
  * 该主题交付物配套的配图（`.png`/`.svg`/`.jpg`）、交互原型（`prototypes/` 或 `.html`）、办公导出物（`.docx`/`.pptx`/`.pdf`）、中间审计稿与附件等，一律收敛存放于该主题容器目录下，形成自闭环资产包。
* **日期约束**：容器目录上的日期必须为有效事件日期（`yyyymmdd`，8 位数字，不含连字符）。

### 2.2 软件工程 Spec 命名规范（中文主题 + ID）
适用于 `03_工程研发/<app-repo-name>/` 代码工程内部**带 Spec ID** 的技术实施规格（`Tech-`/`Task-`/`B-`/`R-`/`SC-`/`M-`/`Bug-` 等既有 ID 前缀体系）：

* **标准格式**：`{{ID}}_{{中文主题}}.md`（例如 `Tech-11_多租户权限改进.md`、`Task-13_成员管理控制台.md`；若采用容器目录管理，则容器目录为 `{{yyyymmdd}}_{{ID}}_{{中文主题}}/`，主文件为 `{{ID}}_{{中文主题}}.md`）。
* **中文主题**：遵循 2.1 节"核心词+类型词"结构；Spec 场景类型词可用领域动作词（如"改进"、"新增"、"修复"、"重构"、"接线"），不强制套用 2.1 的通用类型词表。
* **不带 ID 的代码工程内技术文档**（架构设计、需求文档、产品说明等无 Spec ID 归属的文档）直接适用 2.1 节中文主命名规范，容器带日期、文件本身不带日期。
### 2.3 组织名称默认口径
后续新建文件夹、文件或内容涉及组织名称时，如无明确说明，一律使用 [`.data/workspace-config.md`](../../.data/workspace-config.md) 中的默认名称口径（含禁用缩写与对外例外）；对外正式材料以收件方或官方品牌要求为准。

### 2.4 命名例外
只有入口和工作流真源（`README.md`、`AGENTS.md`、`DECISIONS.md`、`PRODUCT.md`、`Tasks.md`、`Changelog.md`、`ReleaseNote.md`、`Benchmark.md`）、机器契约以及有正式收件方命名要求的专用模板保持固定名称。

### 2.5 根系统自身演进与研究产物归属
关于 `.system/` 根系统自身的架构推演、重构方案、调研记录、设计原型或配图等研究产物，**严禁散落在工作区根目录**，一律存放于 `.data/docs/` 下，且**严格遵循 2.1 节容器化目录规范与中文主命名铁律**（即 `.data/docs/{{yyyymmdd}}_{{主题}}/{{主题}}.<ext>`；主题一律中文主命名，专有技术名词/产品代号可原样嵌入中文主题，不设英文例外），确保根系统研究产物清晰自闭环。

## 3. 交付前质量自检门禁

在完成文件落盘与交付前，必须执行完整质量自检：
1. **可解析与完整性**：生成的 Office 文档（`.docx`/`.pptx`/`.xlsx`）与 PDF 必须能正常解析渲染，无语法报错、损坏或占位符残留；
2. **排版与字阶对齐**：图表、PPT 与文档必须遵循对应领域排版规范（如 16:9 画布、字阶层级、无文本框溢出折叠）；
3. **事实一致性**：交付物中的数据、日期、图示必须与上下文事实源 100% 对应，严禁虚构。

---

## 4. 办公文件落盘后必开文件夹（刚性执行铁律）

本轮任务生成 `.docx`、`.xlsx`、`.csv`、`.pptx`、`.pdf` 或图片（`.png`/`.jpg`/`.gif`/`.webp`/`.svg`）等通用传递格式文件后，**在任务结束交付前，必须调用系统文件管理器打开该文件所在目录，方便用户直接取用**。

* **各操作系统平台命令**：
  * **macOS**：`open "<dir>"`
  * **Windows**：`explorer "<dir>"`
  * **Linux**：`xdg-open "<dir>"`
* **执行约束**：
  * 同一任务多个文件位于同一目录时只打开一次；位于不同目录时逐一打开。
  * 必须在最终回复前完成执行，不得遗漏或跳过。

---

## 5. 讨论沉淀文档结构（6 要素）

经充分讨论后落盘的调研、方案、问题排查、bug 修复记录等文档，按以下固定结构组织，保证日后回查可定位：

1. **主题与场景**：讨论对象是什么，锚定的具体场景/触发事件；
2. **Baseline**：讨论开始时公认的现状、口径或参照基线（含来源链接）；
3. **问题**：本次要解决的具体问题，与 baseline 的偏差；
4. **原因**：经查证的原因分析；未查明的直接写“原因未查明”，不写推测；
5. **解决方案**：已确认采用的方案及关键取舍；多方案对比时保留落选理由；
6. **遗留问题**：未决事项、待确认项、后续动作；已拍板的决策另按“决策落盘”规则同步 `_契约/当前状态.md`。
