# 文件交付

> **适用范围**：工作区内所有涉及新建、修改、导出、生成、存储或移动通用传递格式文件（如 `.docx`、`.xlsx`、`.csv`、`.pptx`、`.pdf`、`.png`、`.jpg`、`.svg` 等）及独立文档交付物时的通用规范与交付门禁。

---

## 1. 文档落盘触发门禁

并非每个问答、讨论或验证动作都要生成磁盘文件。日常技术咨询、命名建议、方案探索直接在对话中交互完成；运行测试默认只保留终端结果，不据此自动生成 HTML/Markdown 测试报告。

**仅当用户明确要求落档，或 Agent 询问“是否需要落入文档”并获得明确许可后，方可创建调研、方案、说明、报告/汇报等独立交付物。**

**触发意图**：`落盘`、`落档`、`出方案`、`写方案`、`设计方案`、`出报告`、`写报告`、`出调研`、`做调研`、`调研报告`、`出汇报`、`写周报`、`双周报`，含插入量词的变体（`出个方案`、`出份报告`、`做个调研`）。命中后按第 2 节命名、第 3 节自检、第 4 节物理打开闭环执行；各类型对应的认知模态质量门禁（如调研须给结论/依据/风险/置信度四段式）见 [`角色协作.md`](角色协作.md)。

## 2. 交付物命名规范（单一真源）

新建调研、方案、汇报、设计、原型、报告、需求等业务交付物及软件开发 Spec 时，统一采用如下规范：

### 2.1 业务与通用交付物命名规范（中文主命名，强制铁律）
适用于工作区内所有一般文件、调研、方案、汇报、设计、原型、评估、报告、会议纪要等业务与管理交付物：

* **事务胶囊命名规范（多阶段聚合首选）**：
  * **容器目录格式**：`{{yyyymmdd}}_{{主题}}/` 或 `{{yyyymmdd}}_{{甲方}}&{{乙方}}_{{主题}}/`（例如 `20260901_智能质检方案/`、`20260901_某公司&某医院_协作方案/`）；
  * **胶囊内文件命名格式（去冗余铁律）**：胶囊内部文件直接采用 **`序数_类型.ext`**（如 `01_调研.md`、`02_方案.md`、`03_设计.md`、`04_Spec_<ID>.md`、`05_审计报告.md`、`07_验收报告.md`），**文件名严禁重复拼接主题名**；细粒度变更记录链接库根 `Changelog.md` 真源，不在胶囊内另写 `06_Changelog.md` 副本；
  * **Front Matter 元数据**：主题与上下文信息统一在 Markdown 文件顶部的 YAML Front Matter 中声明（含 `type`、`topic`、`date`、`author`、`status`）。
* **单体独立交付物命名格式（单文件交付场景）**：
  * **容器目录**：`{{yyyymmdd}}_{{主题}}/`；
  * **主文件命名**：`{{主题}}.<ext>`（例如 `20260901_智能质检方案/智能质检方案.pptx`）。
* **中文主题结构约束**：
  * **结构公式**：`[≤8字核心主词/定语] + [交付物类型词]`（核心主题词一般不多于 8 个中文字符，后接标准类型词）。
  * **标准类型词**：`调研`、`方案`、`汇报`、`设计`、`原型`、`报告`、`评估`、`评审`、`纪要` 等。
* **容器化目录强制铁律**：
  * 所有独立交付物必须以容器目录组织，严禁在父级目录平铺散落单文件；
  * 该主题交付物配套的配图（`.png`/`.svg`/`.jpg`）、交互原型（`prototypes/` 或 `.html`）、办公导出物（`.docx`/`.pptx`/`.pdf`）、中间审计稿与附件等，一律收敛存放于该主题容器目录下，形成自闭环资产包。
* **日期约束**：容器目录上的日期必须为有效事件日期（`yyyymmdd`，8 位数字，不含连字符）。

### 2.2 交付物 Front Matter 元数据标准

胶囊内部各阶段 Markdown 文档统一在顶部维护 Front Matter 元数据：

```yaml
---
type: Spec | Proposal | Research | Audit | Report | Changelog
topic: 具体的中文主题名
date: YYYY-MM-DD
author: Researcher | Designer | Builder | Reviewer | Maintainer
id: Tech-11 (研发/Spec 事项必填)
status: draft | active | revised | completed
---
```

字段取值域、必填项与 `type: Spec` 的条件必填由 [`front_matter.schema.json`](../schemas/front_matter.schema.json) 声明，`validate_schema.py <file.md>` 可单文件校验。可选扩展 `audit_max_rounds`（整数，方案审修轮次上限覆盖值，仅 `type: Proposal` 需覆盖默认值时声明，缺省沿用 `角色协作.md` 定义）。

### 2.3 软件工程 Spec 命名规范（中文主题 + ID）
适用于 `03_工程研发/<app-repo-name>/` 代码工程内部**带 Spec ID** 的技术实施规格（`Tech-`/`Task-`/`B-`/`R-`/`SC-`/`M-`/`Bug-` 等既有 ID 前缀体系）：

* **标准格式**：`{{ID}}_{{中文主题}}.md` 或胶囊内部的 `04_Spec_{{ID}}.md` / `04_Spec_{{ID}}_{{中文主题}}.md`。
* **中文主题**：遵循 2.1 节"核心词+类型词"结构；Spec 场景类型词可用领域动作词（如"改进"、"新增"、"修复"、"重构"、"接线"）。
* **不带 ID 的技术文档**（架构设计、需求文档、产品说明等无 Spec ID 归属的文档）直接适用 2.1 节事务胶囊规范。
* **命名判定边界**：事务胶囊容器目录以 `NN_` 数字前缀识别，日期主题目录（`YYYYMMDD_主题/`）只是容器，不参与 ID 解析；`04_Spec_<ID>.md` 中 `<ID>` 取下划线分隔的第三段；独立 Spec 形态为 `<ID>_中文主题.md`，与之配套的审计报告为 `Audit_<ID>_*.md`，两者以同一 `<ID>` 关联。既有 `Spec_<ID>_主题方案.md` 等历史命名保留只读识别能力，不批量改名。

### 2.4 组织名称默认口径
后续新建文件夹、文件或内容涉及组织名称时，如无明确说明，一律使用 [`.data/templates/workspace-config.md`](../../.data/templates/workspace-config.md) 中的默认名称口径（含禁用缩写与对外例外）；对外正式材料以收件方或官方品牌要求为准。`.data/templates/workspace-config.md` 缺失或字段为占位符时按工作区目录名兜底，不阻断交付。

### 2.5 命名例外
只有入口和工作流真源（`README.md`、`AGENTS.md`、`DECISIONS.md`、`PRODUCT.md`、`Tasks.md`、`Changelog.md`、`ReleaseNote.md`、`Benchmark.md`）、机器契约以及有正式收件方命名要求的专用模板保持固定名称。

### 2.6 根系统自身演进与研究产物归属
关于 `.system/` 根系统自身的架构推演、重构方案、调研记录、设计原型或配图等研究产物，**严禁散落在工作区根目录**，一律存放于 `.data/docs/` 下，且**严格遵循 2.1 节容器化目录规范与中文主命名铁律**（即 `.data/docs/{{yyyymmdd}}_{{主题}}/{{主题}}.<ext>`；主题一律中文主命名，专有技术名词/产品代号可原样嵌入中文主题，不设英文例外），确保根系统研究产物清晰自闭环。

## 3. 交付前质量自检门禁

在完成文件落盘与交付前，必须执行完整质量自检：
1. **可解析与完整性**：生成的 Office 文档（`.docx`/`.pptx`/`.xlsx`）与 PDF 必须能正常解析渲染，无语法报错、损坏或占位符残留；
2. **排版与字阶对齐**：图表、PPT 与文档必须遵循对应领域排版规范（如 16:9 画布、字阶层级、无文本框溢出折叠）；
3. **事实一致性**：交付物中的数据、日期、图示必须与上下文事实源 100% 对应，严禁虚构。

## 4. 文件落盘与定位查阅必开文件（刚性执行铁律）

### 4.1 触发格式范围
本轮任务中新建、修改、导出、生成或定位查找以下格式，均触发物理打开闭环：

| 类别 | 后缀 |
|---|---|
| 办公文档 | `.docx` `.doc` `.xlsx` `.xls` `.csv` `.pptx` `.ppt` `.pdf` |
| 视觉图表 | `.png` `.jpg` `.jpeg` `.gif` `.webp` `.svg` |
| 文本与原型 | `.md` `.markdown` `.asciidoc` `.adoc` `.html` `.htm` |
| 结构化数据 | `.yaml` `.yml` `.json` |
| 独立交付物 | 凡触发第 1 节落盘门禁的调研/方案/说明/报告，不论后缀 |

### 4.2 触发场景
1. **场景一：通用文件交付（落盘自动打开）**：新建、修改、导出或生成上述任一格式文件后，在任务结束交付或回复用户前，必须执行 `python3 .system/tools/open_file.py <path>` 打开生成文件；
2. **场景二：文件/目录查找与定位**：用户明确发起查找、定位、索取文件或询问“xx文件在哪”、“找一下xx”、“定位xx”、“打开xx所在文件夹”等意图，定位后使用同一工具打开目标文件或目录。

### 4.3 程序映射、自动检测与人类仲裁
1. **声明外置**：候选程序与跨平台启动命令的模板真源为 `.system/templates/data/file-opener.template.json`；本机生效映射持久化于 `.data/templates/file-opener.json`。
2. **初始化检测**：首次初始化时扫描宿主机已安装软件生成映射；此后再次初始化仅按 [`控制面布局.md`](控制面布局.md)「`.data/` 写入规约」合并补全缺失字段（人工仲裁值不覆盖，全量重扫须显式执行 `python3 .system/tools/bootstrap.py --force-rescan-opener`）。
3. **人类仲裁**：同一格式检测到多个候选程序，或用户提出“配置打开方式”/“修改默认打开软件”时，列举候选请用户仲裁，确认后按字段更新 `.data/templates/file-opener.json`。
4. **优雅降级**：`open_file.py` 优先执行生效映射中的 `command`；配置缺失、格式未配置或已配置命令失败时，才降级为系统默认关联程序，并逐项输出降级原因。

### 4.4 唯一执行入口

文件和目录只允许通过以下入口打开：

```bash
python3 .system/tools/open_file.py <path> [<path> ...]
```

Agent 不得直接调用 `open`、`start`、`xdg-open` 或具体应用 CLI；这些平台命令只允许由 `open_file.py` 在受控降级分支内部调用。需要机器可读执行结果时添加 `--json`。

### 4.5 执行约束
同一任务生成多个交付物时一次传入或逐项调用；必须检查每个结果的 `ok`、`selected_app`、`used_fallback` 和 `reason`。任一项降级或失败均须告知用户，不得用整体成功掩盖部分失败。
