# 项目组织

> 20260818 精简：Dashboard 写入的操作细节（curl、source_ref、任务分流判据）已收敛至看板操作技能；本文件只保留项目组织与任务解析原则。

## 系统与项目

- `.system/` 只放通用规则、模板、初始化工具和系统专用 Skill。
- 每个项目放在系统工程之外，默认与系统工程同级。
- 不按需求、POC、Spec、交付等固定阶段预建目录。

## 工作区项目索引

> **唯一真源**：`.data/registry.md`（工作区实例数据，不分发）。
> Agent 需要项目 ID、主目录或口语关键词时，先读 `.data/registry.md`；
> 共享资料层目录（不属于 Dashboard 项目）以 [`.data/workspace-config.md`](../../.data/workspace-config.md) 为准。
> 若 `.data/registry.md` 不存在，先创建空白文件（保留表头与列定义），提示用户补填项目信息，再继续任务；不得以"未找到注册表"为由跳过项目解析。

## 时间线与交付物规范（主题工作胶囊架构）

有真实事件、特性研发或独立交付物时，统一创建 `YYYYMMDD_[甲方&乙方_]主题/` 容器目录（主题工作胶囊，Topic Capsule）。

### 主题工作胶囊结构（去冗余命名与生命周期闭环）

同一主题的调研、方案、设计原型、实施规格、安全审计、变更履历与验收凭据，**必须全生命周期高内聚收敛于同一个主题胶囊目录内**，严禁跨部门大目录割裂平铺。

胶囊内部文件采用**纯净序数类型命名**，**文件名不带主题名**（主题与上下文在文件 Front Matter 元数据中声明）：

```text
YYYYMMDD_主题/
├── 01_调研.md          # [探索者] 业务背景、竞品分析、法规文献查新（为什么做）
├── 02_方案.md          # [设计师] 系统架构、业务流程、非目标与决策取舍（做什么）
├── 03_设计.md / 原型/  # [设计师] 视觉图样、交互原型 HTML、设计规范（长什么样）
├── 04_Spec_Tech-N.md   # [构建者] 技术规格、数据模型、接口契约与 TDD 设计（怎么实现）
├── 05_审计报告.md      # [审查者] 安全审查、合规门禁、红队对抗与坏味道审查（有何风险）
├── 06_Changelog.md     # [构建者] 本特性的细粒度代码与配置变更记录（改了什么）
└── 07_验收报告.md      # [守门者] 真实执行证据、测试通过证明与量化指标（交付凭据）
```

> **裁剪规则**：胶囊文件按需创建（如纯业务调研仅产出 `01_调研.md` 与 `02_方案.md`；非代码工程不设 `04_Spec`），不为凑齐结构建空文件。

### 双层流转机制：胶囊过程态与全局主干真源

1. **工作胶囊（过程全量）**：作为特性研发全生命周期的完整上下文单元，随项目永久留存与回溯；
2. **全局主干（增量沉淀）**：
   - **决策持久化**：胶囊通过后，仅将拍板生效的 1 句话核心基线写入 `01_项目管理/DECISIONS.md`，并超链回 `02_方案.md`；
   - **工程实现**：源码与测试入库 `03_工程研发/<app>/src/` 与 `test/`；
   - **变更履历**：从 `06_Changelog.md` 提炼 1-2 行高价值摘要（Added/Changed）追加到代码库根目录 `Changelog.md`；
   - **状态流转**：任务看板与台账状态翻转为 `done`。

### 交付物命名与打开规范
所有文件命名分流、Front Matter 元数据、质量自检与**落盘后调用默认程序打开文件**要求，一律遵循 [`文件交付.md`](文件交付.md)。
材料少时直接平铺；材料明显变多后再建立 `原始材料/工作稿/定稿/`。
不为了满足结构而创建空事件目录。

### 通用项目分层结构（4 域 + 2 底册 + RawInput + Archive）

针对兼具“业务资料管理 + 会议调研论证 + 软件研发交付 + 运营成效沉淀”的综合项目，采用如下标准通用分层结构：

```text
<工作区根目录>/
├── 00_知识库/                         # ════════【工作区共享知识域】════════
│   │                                  # 跨项目复用的权威规范、行业标准、文献、手册、说明书
│   │                                  # 只读事实源；项目内通过 _知识库/index.md 引用，不复制
│   └── <领域名称>/                    # 按学科/业务域组织，如：权威资料与规范/、医学文献/
│
<项目根目录>/
├── CLAUDE.md                          # [Claude Code 入口] 导入 @AGENTS.md
├── AGENTS.md                          # [Agent 控制面] 本项目路由、硬约束与 RawInput 整理规则
├── README.md                          # [总纲] 项目定位、目标、里程碑与目录全景导航（只导航，不存正文）
├── RawInput/                          # [暂存投递箱] 随手丢入的原始文件（触发”整理”后自动归位并清空）
│   └── .gitkeep
│
├── 01_项目管理/                       # ════════【业务与管理域 · 输入与过程】════════
│   ├── DECISIONS.md                   # [决策持久化] 跨会话唯一事实（记录已拍板生效的决策、基线与口径）
│   ├── 01_项目资料/                   # 项目专属原件：临床方案、CSR/实验报告、参考数据集（只读事实源）
│   │                                  # 跨项目通用规范/文献 → 工作区 00_知识库/，不放此处
│   ├── 02_调研评估/                   # 行业调研、PoC体验评估、迭代评测、方案规划（按 YYYYMMDD_事件名/ 组织）
│   │                                  # 含评估过程会议纪要；判断标准：产出是”认知”而非正式决策
│   ├── 03_决策记录/                   # 正式决策节点：立项批准、方案选定、上线放行、里程碑评审决议
│   │                                  # 判断标准：有明确决策结论（可含会议纪要、邮件批复、审批截图）
│   └── 04_价值回收/                   # 立项文件、战略汇报PPT、高管演示看板、成效推介、业务ROI测算
│
├── 02_产品设计/                       # ════════【产品定义域 · 需求与体验】════════
│   ├── 01_需求清单/                   # 业务功能列表、优先级跟进表、用户故事 (User Stories)
│   ├── 02_原型Demo/                   # 交互原型、静态/动态 UI Mockup、体验演示包
│   └── 03_设计规范/                   # 详细产品需求文档 (PRD)、设计系统 (Design System) 与交互规则定义
│
├── 03_工程研发/                       # ════════【工程实现域 · 技术与代码】════════
│   └── <app-repo-name>/               # 独立 Git 代码仓库
│       ├── PRODUCT.md                 # 产品边界定义
│       ├── src/ / server/             # 源代码
│       ├── test/ / tests/             # 测试套件
│       └── docs/                      # 工程工作流真源与按事项组织的工程证据
│           ├── Tasks.md               # 应用实现任务与规划真源
│           ├── Changelog.md           # 研发变更履历
│           ├── Benchmark.md           # 量化成效基准
│           ├── ReleaseNote.md         # 工程版本发版说明
│           └── YYYYMMDD_主题/          # 同一工程事项的规格、审计与评估报告
├── 04_运营增长/                       # ════════【交付与运营域 · 推广与赋能】════════

│   ├── 03_营销推广/                   # 宣发文章、宣传彩页、对外推介材料
│   ├── 04_数据/                       # 运营监控大屏、提效数据底册、使用量与成效统计
│   └── 05_用户反馈/                   # 试点/用户反馈跟进台账、用户痛点与改进建议
│
└── Archive/                           # [废弃归档域] 已被新方案替代的历史文件与过期备份（注明替代路径）
```

#### `RawInput/` 暂存投递箱与“整理”机制

1. **定位**：无负担的暂存投递区，用于临时放置微信/邮件附件、会议转写、截图、未命名草稿等。
2. **“整理”指令 SOP**：当用户在会话中发出“整理”、“整理 RawInput”或“归档收件箱”时，Agent 自动执行：
   - 扫描 `RawInput/` 下所有文件，解析文件名与正文内容；
   - 官方凭据/合同/底册/项目专属输入资料 $\rightarrow$ 规范重命名后移入 `01_项目管理/01_项目资料/` 对应子目录；权威规范/文献/手册 $\rightarrow$ 工作区 `00_知识库/`；
   - 调研/评估/方案 $\rightarrow$ `01_项目管理/02_调研评估/`；有明确决策结论的会议纪要/批复 $\rightarrow$ `01_项目管理/03_决策记录/`；提炼已拍板决策写入 `01_项目管理/DECISIONS.md`；
   - 立项文件/汇报PPT/成效推介 $\rightarrow$ `01_项目管理/04_价值回收/`；
   - 需求清单/原型/PRD设计 $\rightarrow$ 移入 `02_产品设计/` 对应子目录；
   - 代码/技术Spec/系统实现 $\rightarrow$ 移入 `03_工程研发/<app>/` 或其 `docs/`；
   - 交付样稿/培训材料/宣发/运营数据 $\rightarrow$ 移入 `04_运营增长/` 对应子目录；
   - 历史作废版本 $\rightarrow$ 移入 `Archive/` 并注明替代来源；
   - **清空 `RawInput/` 目录（保留 `.gitkeep`）**，向用户输出归档清单。

### `docs/` 事件容器布局（代码工程内部文档）

代码仓库的 `docs/` 只保存与实现直接绑定、必须随代码演进的工程证据；每个事项使用一个日期主题容器：

```text
03_工程研发/<app-repo-name>/docs/
├── README.md                                      # 文档导航、真源层级和当前入口
├── .board.json                                    # 跨系统绑定（启用时）
└── YYYYMMDD_主题/
    ├── Spec_Tech-19_主题方案.md                    # 实施规格
    ├── Audit_Tech-19_主题方案审计.md               # 审计或评审
    └── Report_Tech-19_主题评估报告.md              # 评估报告
```

- 容器日期取工程事项首次形成或正式立项日期；主题使用简洁中文名。三个文件按实际产出创建，不为凑齐结构预建空文件。
- `Spec_`、`Audit_` 与 `Report_` 分别标识实施规格、审计/评审、评估报告；同一事项文件必须使用相同 Task ID 与主题。
- 产品、视觉、调研、项目计划、普通报告及归档材料分别回归项目根的 `01_项目管理/`、`02_产品设计/`、`04_运营增长/` 或 `Archive/`；工程工作流固定文件除外，不得在代码仓库 `docs/` 重复保存。
- `PRODUCT.md`（存在时）定义最高层产品边界；`docs/Tasks.md` 是应用实现任务真源；`docs/README.md` 只导航，不复制正文。
- 同一内容只有一个真源，其他文档使用链接；不保留旧路径副本。
- `docs/README.md` 与 `.board.json` 留根。
- 通用项目不创建根级 `docs/`；需要代码工程文档时，在 `03_工程研发/<app-repo-name>/` 运行 `init_app.py` 创建最小布局。
## 项目总览 (README.md)

`README.md` 承担项目全局总纲与导航：

- 项目身份、用途、目标和相关人员；
- 4 域目录分层结构全景导航；
- 按日期排列的关键里程碑与事件索引；
- 当前有效状态入口、最新产物与下一关键事件。

事件完成后追加或更新一行，不在总览中复制详细正文。

## 决策与基线底册 (01_项目管理/DECISIONS.md)

`01_项目管理/DECISIONS.md` 是项目跨会话唯一的当前事实真源（Single Source of Truth）：

- 只写已经确认或当前明确采用的内容（业务基线、核心架构选型、接口标准、排除范围）；
- 每项基线链接到时间线中的证据或产物；
- 新结论覆盖旧结论时更新当前状态，旧版本仍留在原事件目录或保留演进说明；
- 未确认内容放在"待确认/待决事项"，不冒充当前事实。

### 决策落盘（跨会话记忆）

`01_项目管理/DECISIONS.md` 同时是**跨会话、跨 agent 的持久记忆层**——没有落盘的决策等于没有记住，下一次会话或换一个 agent 就会丢失。因此：

- 每当在对话或事件中**确认**一个决策、结论、基线或口径（不是临时讨论、不是待确认项），就把它写入所属项目的 `01_项目管理/DECISIONS.md`，并链接到时间线中的证据或产物。
- 触发点：用户明确表态"就这么定 / 确认 / 采用 X"、评审形成结论、机制或口径敲定、选型拍板等。纯讨论、假设、候选方案不落盘（放"待确认"或留在事件记录里）。
- 与 Dashboard 的边界：Dashboard 记**任务/状态/截止/相关人**，`DECISIONS.md` 记**当前以什么为准**（事实/决策/基线/口径），两者不重复。
- 存量项目目录尚无 `DECISIONS.md` 时，**首次出现确认决策**才创建它（用模板），不为占位预建空文件。
- 覆盖旧决策时更新 `01_项目管理/DECISIONS.md`，旧版本仍留在原事件目录，保留可追溯的演进。

不使用 `node`、`handoff_to`、`fields_origin` 或统一状态机。只有法规、验收或正式审批确有要求时，才增加独立契约文件。

## Agent 工作闭环

1. 读根 `AGENTS.md` 常驻层，按任务路由表按需读取规则与项目导航文档。
2. 把用户自然语言解析为任务卡，并用项目文件、Dashboard、日历和素材查证。
3. 确认本次事件目录和目标。
4. 在事件目录中处理材料。
5. 更新 README.md 和 DECISIONS.md 中发生变化的部分；确认决策落盘。
6. 需要登记任务时按看板操作技能标准同步 Dashboard，并重新读取验证。
7. 报告产物位置、确认项、未决事项、下一步和 Dashboard 同步结果。

自然语言任务解析（任务卡元素、查证顺序、追问边界与示例）见 [`指令解析.md`](指令解析.md)。

## 与 Dashboard 的边界

- 项目目录保存材料、产物、时间线、结论、基线和知识。
- Dashboard 保存执行任务、状态、截止日期、相关人及通知状态。
- `DECISIONS.md` 的"下一步"只记录高层方向或关键事件，不复制 Dashboard 的详细任务清单。
- Agent 看板读写统一经看板操作技能（本地 CLI + Bearer Token）；不手写 HTTP 请求，不走本地端口或公开 Tunnel。
- 新任务必须带稳定 `source_ref`（格式与幂等行为见看板操作规范）。
- 对话中的结论、知识或材料不自动转成任务；只有明确行动项才进入 Dashboard。
- 安排会议只有在用户明确要求时才写入日历。
