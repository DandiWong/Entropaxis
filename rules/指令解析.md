# 指令解析

本文件涵盖两类场景：

1. **通用任务解析**：收到任意自然语言指令时，将其解析为任务卡并查证关键元素。
2. **显式指令语义**：当用户以”同步””同步任务””任务””记录/沉淀””复盘””审计””修正””新迭代/新 feature”或”机制转工具/制作工具”明确发起操作时，按下方各节解释意图。普通问答或提到这些词不自动触发写入。

所有外部写入仍受根 `AGENTS.md` 安全边界约束。精确命令以对应工具和专项规则为准，本文件不复制 CLI 参数。

## 通用任务解析

收到任意自然语言指令时，先在内部形成任务卡，不要求用户按表单重述：


| 元素   | 含义                         |
| ---- | -------------------------- |
| 时间   | 事件时间、执行时间和截止日期，三者分别识别      |
| 项目   | 项目名称、简称、Dashboard ID 和工作目录 |
| 动作   | 整理、撰写、评审、修改、汇报、发送等         |
| 对象   | 会议纪要、需求、合同、报告、课件等          |
| 素材   | 附件、链接、录音、转写、笔记、历史文件和知识依据   |
| 产出   | 内容目标、格式、受众、保存位置和完成标准       |
| 执行信息 | 负责人、相关人、截止日期、敏感性和是否需要通知    |


### 解析与查证顺序

1. 优先采用用户本句中的明确表达，其次采用本轮附件和链接，再采用当前对话上下文。
2. 项目按”精确名称或 ID → 已登记简称 → 当前项目 → 上下文”解析；用
 `/api/board` 和 `/api/project/{id}` 查证。多个项目都可能匹配时必须追问。
3. “今天、明天、下周五”等相对时间以当前会话日期和时区换算为绝对日期。
 时间修饰会议、材料或事件名时视为事件时间；修饰”完成、提交、交付”时视为截止日期。
 语义仍会改变素材选择或期限时才追问。
4. 素材按”本轮附件或明确路径 → 对话中已引用文件 → 同日期事件目录 →
 Calendar 对应事件 → 项目知识索引”查找。日历标题只能证明会议存在，不能代替会议内容。
5. 动作和对象共同决定产出。命中专用 Skill 或项目模板时优先使用；否则内部文字产出默认
 Markdown，正式对外文件、PPT、Word 或 PDF 格式不明确时再确认。
6. 默认保存到匹配的 `YYYYMMDD_事件名/`；已有事件目录则复用，没有实际材料或产出时不创建空目录。

### 追问边界

能通过现有文件、Dashboard、日历或上下文唯一确定的内容不要询问。只有以下情况暂停：

- 项目存在多个有效匹配；
- 找不到完成任务所需的实质素材，或候选素材互相冲突；
- 受众或格式会显著改变产出，且无法从”内部/正式对外”判断；
- 涉及发送、发布、删除、覆盖、个人或医疗数据等需要授权的动作；
- 用户明确表述与 `DECISIONS.md`（或 `_契约/当前状态.md`）中已有基线存在明显冲突——询问确认后，由用户决定是否更新决策底册。

其余缺省项采用最保守的内部工作默认值，并在结果中说明。执行前只需用一句话复述关键理解；若用户已经说清且任务可直接完成，不把复述变成确认门槛。

### 示例

在 `<YYYY-MM-DD>` 收到”整理今天 `<项目简称>` 的会议纪要”：

- 时间：事件日期 `<YYYY-MM-DD>`，不是截止日期；
- 项目：`<项目名>` / `<project_id>`；
- 动作与产出：依据真实会议素材整理会议纪要；
- 素材：先找本轮附件和同日事件目录，再核对 Calendar；只有会议标题而没有记录时询问素材位置；
- 保存：复用或建立 `<YYYYMMDD>_会议主题/`，按专用会议纪要 Skill 或项目模板生成；
- Dashboard：复用已有任务，或以 `<project_id>:<YYYYMMDD>:会议纪要` 建立进行中任务，产物验证后完成；纪要内提取的行动项不自动写入 Dashboard，待人工完善后由「同步任务」指令触发。

## 工作区初始化 / 新机配置

用于新电脑上手、新协作者接入或工作区入口配置自愈。

**触发场景**：用户输入 `初始化`、`新电脑`、`我是新人`、`配置工作区`、`系统初始化`、`配置打开方式`、`修改打开程序` 或首次使用。

**执行步骤**：

1. **自动同步根入口配置**：后台执行 `python3 .system/tools/bootstrap.py`，确保 `AGENTS.md` 和 `CLAUDE.md` 物理同步就绪。
2. **检查看板凭证**：
  - 若已配置：直接读取并向用户回显用户名及看板可用状态；
  - 若未配置：使用通俗大白话向用户索取 API Token（*“请将管理员发放给您的 43 位看板 Token 粘贴发送给我”*），获得后在后台执行看板初始化脚本（如可用）完成一键注册与日历同步。
3. **检测并配置本机文件打开程序（含人类仲裁）**：
  - 读取并自动检测本机安装的应用程序（Word/Excel/PPT/PDF/Markdown/HTML/图片/配置数据等）；
  - 若某格式检测到多个可选程序（如既有 WPS 又有 Word，既有 Typora 又有 VS Code/Cursor）或用户显式要求定制，列举候选并向用户提请仲裁，确认后将配置持久化至 `.data/file-opener.json`。
4. **就绪反馈**：提示用户已就绪，可直接通过自然语言使用各类业务功能（如“看下待办”、“记个任务”、“生成会议纪要”等）。
## Tip

当用户指令仅为 `tip`（忽略首尾空白，不区分大小写）时，从 `.data/tips.md` 中回显一条以 `- TIP：` 开头的原文。文件缺失、为空、不可读取或不含有效条目时静默说明无可用 Tip；不得因此修改文件、创建任务或触发其他动作。

## 定位 / 查找文件

用于根据用户意图查找并定位工作区内的特定文件、资料或目录。

1. **触发意图**：用户询问“xx文件在哪”、“找一下xx”、“定位xx”、“打开xx所在目录”或索取特定文件。
2. **定位与查证**：在工作区（或项目资料、知识库）中检索匹配的目标路径，核对最新有效版本。
3. **物理动作闭环**：在输出路径和简要说明的同时，**严格遵循《文件交付》第 4 节铁律，主动调用系统打开文件能力（macOS `open` / Windows `start ""` 或 `explorer` / Linux `xdg-open`）打开该文件或目录**，实现即时可见与可操作。

## 生成或更新工作空间 Tips

用于从已生效的工作空间规则与声明中生成 Tips 更新候选。

1. 先读取 `.data/tips.md`、`.data/registry.md`、根 `AGENTS.md` 及本次涉及的已生效规则；项目材料只在用户明确指定项目时读取。
2. 输出新增、修改、停用候选及每条的真源路径；不得提取凭据、外部系统 ID、个人信息、未确认会议内容、草稿或推断性结论。
3. 默认只生成候选，不直接改写 `.data/tips.md`。用户确认后再最小化更新该文件，并保留已有有效 Tips。
4. Tips 只能描述可验证的操作入口或已生效规则，不得替代项目决策、任务状态或原始资料。
## 同步

用于核对项目本地状态与配置的外部看板。

1. 按 `项目组织.md` 定位项目，按稳定任务 ID 和 `source_ref` 配对。
2. 读取各端状态与可用时间证据，先列差异。
3. 修改时间只能辅助判断，不能单独决定语义真源；发生冲突时优先采用项目声明的本地状态真源，无法判断则报告待确认。
4. 经授权后按 `看板联动.md` 幂等更新，并回读验证。
5. 删除、关闭、覆盖或无法回滚的差异不自动处理。

## 同步任务

用于把已经人工确认的会议或事件行动项写入配置的外部任务看板。

- 先定位来源文件并提取项目、负责人、截止日期、内容和稳定 `source_ref`。
- 未经人工确认的会议纪要行动项只保留为草稿。
- 写入方式与回读检查见团队看板 Skill（source_ref 与准入标准）。
- 输出逐项成功、失败与缺失字段，不用汇总成功掩盖部分失败。

## 任务

用于把用户明确要求登记的自然语言任务写入任务系统。

- 按 `项目组织.md` 解析项目、负责人、截止日期和可执行内容。
- 项目有 `docs/.board.json` 时按 `看板联动.md` 使用同一任务 ID；其他项目只写用户指定的系统。
- 不因纯问答、查找或建议自动建任务。
- 多个项目同样匹配或关键字段会改变归属时再询问。

## 记录 / 沉淀

按 `知识沉淀.md` 判断目标形态：

- 离散事实或交付物：新文档。
- 持续演进的基线：更新既有真源。
- 长期行为约束：修改相应层级的规则。
- 高频、可复用且步骤稳定的流程：评估为 Skill。

先读取目标文件并保留现有内容。用户已经明确要求修改规则时，不重复索取同一授权；写入外部系统或扩大范围仍需单独授权。

## 复盘

用于回顾用户指定项目和时间范围，识别重复劳动、纠正、知识缺口、决策变化与未闭环事项。

- 默认产出分析和建议；只有用户明确要求落盘时才创建复盘文档。
- 规则建议进入相应规则真源，项目事实进入当前状态真源，行动项只有在“任务/同步任务”被明确触发时才写入外部系统。
- 证据不足的判断标为待确认，不补写不存在的历史。

## 审计

用于对当前项目、文件夹或分支中已经出现的最新的方案进行对抗性审计，并输出结构化审计报告。

1. **触发意图**：用户输入 `审计`、`方案审计`、`审核方案`、`评审方案`、`对最新方案进行审计` 等。
2. **受审对象定位**：
   - 自动在当前上下文（当前所在项目、当前目录/主题工作胶囊文件夹、或当前 Git 分支）中检索最新出现的方案或实施规格；
   - 优先匹配当前主题工作胶囊内的 `02_方案.md` 或 `04_Spec_Tech-N.md`、代码工程库内的 `docs/YYYYMMDD_主题/Spec_<ID>_主题方案.md`、或最近修改的独立方案文档；
   - 存在多个候选或方案歧义时，先向用户说明已定位的候选方案并确认。
3. **审计认知模态与审查维度**：
   - 切换为 **Reviewer (审计/红队)** 认知模态，开展独立对抗性评审与深度合规/架构/可行性核验；
   - 审计维度涵盖：
     - **业务完备性**：是否覆盖既定业务需求与全流程边界，有无悬空逻辑或未定义分支；
     - **架构与技术可行性**：是否遵循最小作用量（YAGNI）、接口契约是否清晰、是否存在过度设计或性能瓶颈；
     - **安全性与边界防御**：是否存在越权漏洞、数据敏感性隐患、单点故障或异常降级缺失；
     - **可验证性与质量门禁**：验收标准是否清晰可测，测试用例与验证路径是否完备。
4. **认知模态承载方式**：Reviewer 可由当前 Agent 会话内直接切换承担；也可外置为独立 CLI/Agent 会话承担（跨 CLI 审修协调），此时当前会话兼任协调者，通过终端切换/发送/等待原语驱动外置 Reviewer 会话完成审计并写回同一份 `05_审计报告.md`，具体外置 CLI 与启动命令见 `.data/workspace-config.md` 的实例声明，本规则不绑定具体产品名；`.data/workspace-config.md` 未声明或声明的 CLI 在本机不可执行时，自动降级为会话内直接切换，不阻断审计流程。
5. **产物规范与连续生命周期**：
   - 主题工作胶囊内落盘为 `05_审计报告.md`；代码工程独立 Spec 对应落盘为 `Audit_<ID>_主题方案审计.md`（收敛于同容器目录下）；
   - 报告须包含 YAML Front Matter（`type: Audit`、`topic`、`date`、`author: Reviewer`、`status: active`）、受审对象路径与指纹、审计结论总览（通过/附条件通过/阻断退回）、分级问题清单（Critical 阻断级、Major 严重级、Minor 建议级，包含现象、根因、整改建议）；
   - 遵循连续审计事件生命周期：同一审计事件复审时在原报告中逐轮追加受审指纹与问题关闭记录，不新建碎片副本；方案审计全过程严禁改动 `Tasks.md`。
6. **终审判据与人工锚点**：遵循 `角色协作.md` 方案审修协同闭环——Reviewer 复核关闭全部问题即终审通过；Critical/阻断级问题关闭需额外人工签字；同一事件轮次达到上限或出现单条问题僵局时，停止自动复审并转人工仲裁。
7. **物理动作闭环**：严格遵循《文件交付》第 4 节铁律，落盘后自动调用系统默认程序打开生成的审计报告文件。

## 修正

用于根据当前项目、文件夹或分支中出具的审计报告，对审计意见逐条进行质疑或接纳，并把质疑或接纳更新到方案真源。

1. **触发意图**：用户输入 `修正`、`修正方案`、`根据审计修正`、`响应审计报告`、`方案修正` 等。
2. **方案与审计报告定位**：
   - 自动在当前上下文（当前项目/文件夹/分支）中定位最新出具的方案文档（如 `02_方案.md` / `Spec_*.md`）及对应的审计报告（如 `05_审计报告.md` / `Audit_*.md`）；
   - 确认二者属于同一次方案设计与审计事件。
3. **执行决策响应矩阵 (Accept vs. Challenge)**：
   - 切换为 **Designer / Builder** 认知模态，逐条审查审计报告中列出的各级问题与建议；
   - 对每条审计意见进行明确裁定：
     - **接纳 (Accept)**：认可该意见，明确具体修订点，并将实质变更直接改写到方案正文的对应章节（如补全接口契约、加固防御机制、调整架构设计）；
     - **质疑 (Challenge / Reject)**：对不合理、超出需求范围（Non-goals）、脱离实际约束或存在技术误解的意见，列出充分客观的辩驳事实、边界依据与理由。
   - 本步骤产出的接纳/质疑均为 Designer/Builder 的裁定意见，不直接构成问题关闭：是否关闭由 Reviewer 在下一轮复核确认（见 `角色协作.md` 方案审修协同闭环第 4 步），Reviewer 驳回裁定则问题保持开放。
4. **方案真源更新闭环**：
   - **单一真源就地更新**：直接在原方案文档中改写，严禁新建 `v2.md` / `修正方案.md` 等冗余副本；
   - **响应记录持久化**：在方案文档末尾维护 `## 审计意见响应与修订记录` 章节，以表格或结构化条目完整记录：审计问题与级别、响应决策（接纳/质疑）、修订说明或辩驳理由、对应章节锚点；
   - 更新方案 Front Matter 中的状态（如 `status: revised`）与修改日期；方案修正阶段聚焦于方案本身，严禁改动 `Tasks.md`。
5. **物理动作闭环**：严格遵循《文件交付》第 4 节铁律，落盘后自动调用系统默认程序打开更新后的方案文件。

## 系统自检

用于对 Entropaxis 控制面自身健康度做一次全面检查，不涉及业务项目内容本身。

1. **触发意图**：用户输入 `系统自检`、`自检`、`Entropaxis 自检`等。
2. **检查范围**：`.system/` 六个子目录（`rules/`、`tools/`、`templates/`、`skills/`、`tests/`、`root-configs/`）及其部署产物（根 `AGENTS.md`/`CLAUDE.md`）；不含 `.data/` 与各业务项目自身内容，但需递归核验全工作区项目 `AGENTS.md`/`CLAUDE.md` 的结构契约（单锚点回链、零废弃引用、薄壳纯净度、声明外置悬空兜底），不评判项目业务内容本身。
3. **两遍检查**：
   - 第一遍依据 `00_元规则.md` 九条公理逐条核对 Entropaxis 现状；
   - 第二遍依据 `01_根系统治理.md` 规则审计流程与完成标准执行，含运行 `python3 -m unittest discover -s .system/tests` 与 `python3 .system/tools/lint_workspace.py` 双重体检。
4. **CLAUDE.md 违规自动改写**：追加执行 `python3 .system/tools/lint_workspace.py --fix-claude-md`，检测到非纯薄壳的项目 `CLAUDE.md` 直接改写为标准形式（一行标题 + `@AGENTS.md`）；既有排除名单、符号链接例外与嵌套独立 git 仓库排除照旧生效，不触碰上游/第三方内容。
5. **产物（必显五维评估表）**：会话内输出检查结论清单（通过项/需整改项/已自动改写项），并**必须附带五维评估表**——4 列格式 `| 评估维度 | 实测得分 | 门禁结论 | 量化评估依据 |`，门禁线与打分细则见 [`五维评估.md`](五维评估.md)，量化依据一律引用本轮双重体检的实测锚点与命中数，严禁凭语感给分；命中该表「已知盲区」条目时须补一句人工核查结论。不强制落盘报告；确有必要落盘时遵循《文件交付》第 1 节触发门禁与 2.6 节根系统研究产物归属。

## 新迭代 / 新 Feature

用于检查当前分支健康度，完成测试验证与原子提交，合入主干并检出新工作分支开启新迭代。

1. **触发意图**：用户输入 `新迭代`、`新 feature`、`new feature`、`feature`、`开始新迭代`、`开新分支` 等。
2. **适用范围**：应用代码仓库与工程项目（遵循《软件工程》研发迭代标准闭环）。
3. **五步执行闭环**：
   1. **分支健康度检查 (Health Check)**：检查 `git status --short --branch` 与未追踪文件，排查未完成改动、未暂存脏数据或未闭环状态；
   2. **自动化测试与质量门禁（该测测）**：运行项目全量单元测试、集成测试与代码检查（Lint/体检），确保当前分支 100% 绿灯通过；若存在失败测试或编译报错，必须就地修复或提示阻断，严禁带病推进；
   3. **履历记录与原子提交（该提交提交）**：核对本次已完成任务，在 `docs/Changelog.md` 追加变更条目（遵循 Keep a Changelog 规范），在 `docs/Tasks.md` 中将对应 Task 标记为完成 (`done`)，执行规范的单 Task Git Commit（提交信息注明 Task ID 与摘要）；
   4. **合入主干（该合并到 main 合并到 main）**：切换至主干分支（`main` 或默认主干），将已验证通过的功能分支合并至主干（Fast-Forward 或 Merge/Squash），并在主干确认测试通过与工作区干净；
   5. **检出新分支开启新迭代（开新分支）**：从干净的 `main` 主干检出并创建新的独立工作分支（命名规范：`feat/<topic>` 或 `feat/Task-<ID>-<topic>`，用户已指定分支名时按指定名称创建）。**开辟新分支正式进入开发实施后，方可在 `docs/Tasks.md` 中将新迭代的任务认领并置为 `in_progress`**。


## 机制转工具 / 制作工具 (Tool Crafter)

用于扫描工作区高频机制、复合命令、脚手架或数据校验逻辑，按照 ApX 高级工具工程规范与《工具技能》规则，标准化转化为系统级 Python 工具。

1. **触发意图**：用户输入 `机制转工具`、`制作工具`、`创建工具`、`机制工具化`、`tool-crafter`、`toolify` 等。
2. **执行流程（唤起 `tool-crafter` Skill）**：
   1. **五维准入审查**：对照 `工具技能.md` 核验确定性、频次>2、安全收敛、Token ROI与零系统绑定 5 项判据；不满足则说明理由并转为 Rule 或 Skill；
   2. **接口契约设计 (Spec)**：设计动词_名词命令名、参数类型、结构化输出及行动导向的 `ToolError` 自愈指引；
   3. **纯标准库实现 (Code)**：基于 `tool.template.py` 编写 `.system/tools/<name>.py`，严格使用纯 Python 内置标准库，杜绝外部 pip 依赖；
   4. **自动化单测驱动 (TDD)**：在 `.system/tests/test_<name>.py` 编写完整单元测试，覆盖正常输出与异常阻断；
   5. **双重体检门禁 (Verify)**：运行 `unittest` 与 `lint_workspace.py`，确保测试与 15 项控制面体检 100% 绿灯；
   6. **路由装配与五维评估**：在 `.data/tips.md` 注册操作入口，依据 `五维评估.md` 输出量化交付评估表。
