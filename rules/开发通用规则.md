# 开发通用规则

适用于本工作区下的一方开发项目。项目 `AGENTS.md` 或 Spec 可以补充更严格的要求；第三方和上游仓库优先遵循其局部契约。

## 开始前

1. 读取最近的 `AGENTS.md`，再按需读取 README、Spec 和配置说明。
2. 检查 `git status --short --branch`，识别用户改动、生成物和不应提交的文件。
3. 明确本次改动的行为边界、验收方式和文档真源。
4. 多文件或行为性改动应有 Spec；小型、局部且验收明确的修复可直接实施。
5. 大型复杂工程（多阶段流水线、深层调用网）进行架构重构、全景盘点或专利挖掘时，推荐按需调用拓扑分析工具（如 `graphify`）提取中枢节点与调用链；提炼出的架构结论必须收敛至 Spec 或文档真源，其派生缓存（`graphify-out/`）删了可重建，不作为唯一真源。日常局部修改优先使用 `lsp` / `grep`，严禁滥用全量建图。

## 实现原则
- 先复用现有代码、标准库和已安装依赖；不为假想需求增加抽象、兼容层或配置。
- 修复共享根因，不在每个调用点重复打补丁。
- 重构优先删除无用层次与死代码，不盲目新增抽象；保留必要的输入校验、安全防御与可恢复性。
- 尊重现有接口和数据；破坏性迁移必须在 Spec 中写明影响、回滚与验证。
- 配置、密钥和环境差异不得硬编码；示例配置只放占位值。
- 错误和阻断应可见，不用静默降级伪装成功。
- 独立代码库应用自身工程管理机制（内部依赖、私有配置与测试套件），工作区通用规则不强行介入其内部结构。

## 研发迭代标准闭环 (Feature / Bug Loop)

日常功能开发与缺陷修复遵循端到端的 7 步标准闭环：

1. **新建分支 (New Branch)**：基于主干创建独立工作分支（如 `feat/<topic>` 或 `fix/<issue>`），隔离特性改动；
2. **认领任务 (Claim Task)**：从 `Tasks.md` 中认领对应 Task ID（如 `Tech-92`、`Bug-31`），状态置为进行中 (`in_progress`)；
3. **规格设计 (Spec)**：对多文件、跨模块、协议变更或破坏性改动，先在 `docs/04_architecture/specs/<ID>_<Topic>.md` 编写实施规格，明确输入输出契约与验收条件；小型局部改动可直接实施；
4. **测试驱动开发 (TDD)**：先编写或更新能复现预期的最小自动化测试用例，再编写实现代码，确保全量测试回归通过；
5. **履历与成效记录 (ChangeLog & Benchmark)**：
   - 在 `docs/00_project/ChangeLog.md`（或应用 `ChangeLog.md`）顶部追加本次变更明细（新增/变更/修复/精简/安全）；
   - 涉及性能、准确率或量化指标变更时，在 `docs/00_project/Benchmark.md` 顶部追加前后对比评估快照；
6. **精确提交 (Git Commit)**：单 Task 单 Commit，提交信息必须包含 Task ID 与改动范围摘要（如 `fix(agent): [Bug-31] 模型流式重试...`），严禁包含未授权的无关改动；
7. **合并与状态同步 (Merge & Done)**：将功能分支 Merge 回主干，在 `Tasks.md` 中将对应条目勾选完成 (`done`)。

## 环境交付与发布指令锚定

面向多环境部署与发版交付，自然语言指令与底层工程动作建立严格的确定性映射：

### 1. “发布测试” (Deploy Test)
* **触发口令**：“发布测试”、“部署测试环境”、“发一版测试”、“跑测试部署”
* **执行边界与动作**：
  1. **测试前置门禁**：确认当前分支所有单元测试与集成测试 100% 通过；
  2. **测试环境部署**：构建测试镜像或更新测试集群配置（如 apply `overlays/test` 或 local overlay），部署至测试环境；
  3. **冒烟与健康检查**：运行 Smoke Test 或健康探测，确认服务 Pod/API 正常就绪；
  4. **输出状态报告**：向用户输出测试环境访问地址、测试版本号及部署状态；
  5. ⚠️ **严格限制**：**不改动生产环境、不打生产 Git Tag、不更新对外正式 ReleaseNote**。

### 2. “发布 / 发布正式” (Deploy Prod & Release)
* **触发口令**：“发布”、“发布正式”、“正式发版”、“上线”、“部署生产”
* **执行闭环 (Release Workflow)**：
  1. **主干就绪确认**：确认所有待发特性已 Merge 至主干（`main`），测试全量绿灯；
  2. **发版说明落盘 (ReleaseNote)**：在 `04_运营增长/01_上线发布/ReleaseNote.md` 中编写/更新本次发布的正式版本号、核心业务价值、新特性说明与升级指引；
  3. **生产部署 (Deploy Prod)**：触发生产环境部署流水线（如 Jenkins `deploy prod` 或生产 Kubernetes rollout），执行零停机发布；
  4. **生产健康检查**：验证生产服务可用性与关键业务链路健康度；
  5. **版本固化 (Git Commit & Tag)**：将 ReleaseNote 交付物提交至仓库，打上语义化版本标签（如 `git tag -a v0.3.0 -m "Release v0.3.0"`）并推送至远端；
  6. **发版通告输出**：输出正式交付确认单、生产访问入口与 ReleaseNote 核心摘要。

## 测试与验证

- 非平凡逻辑先写或更新能复现预期的最小测试，再实现。
- 优先运行最贴近改动的检查；交付前再运行项目 `AGENTS.md` 指定的完整检查。
- 不宣称未实际运行的测试通过。无法运行时说明原因和剩余风险。
- 纯文档改动至少检查链接、命令、术语和规则冲突。

## Git 与外部操作

- 日常开发严格遵循上述 **研发迭代标准闭环 (Feature / Bug Loop)**；
- 未经明确授权，不拉取、推送、合并、部署、发布或向外部系统写入；
- 只提交本次任务文件，不覆盖、不清理无关改动。

## 文档与任务

- 架构、行为或配置发生变化时，更新其唯一真源；不要在多个 README、规则和 Spec 中复制同一段内容。
- 命名、交付文件和项目索引见 `项目运行规则.md`。
- Spec、任务状态和 Dashboard / Board-Platform 同步见 `开发项目联动规则.md`。
- 表达和图示见 `表达文风规则.md`；只有在图示显著提升理解时才使用。
