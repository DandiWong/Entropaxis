# 开发通用规则

适用于本工作区下的一方开发项目。项目 `AGENTS.md` 或 Spec 可以补充更严格的要求；第三方和上游仓库优先遵循其局部契约。

## 开始前

1. 读取最近的 `AGENTS.md`，再按需读取 README、Spec 和配置说明。
2. 检查 `git status --short --branch`，识别用户改动、生成物和不应提交的文件。
3. 明确本次改动的行为边界、验收方式和文档真源。
4. 多文件或行为性改动应有 Spec；小型、局部且验收明确的修复可直接实施。
5. 大型复杂工程（多阶段流水线、深层调用网）进行架构重构、全景盘点或专利挖掘时，推荐按需调用拓扑分析工具（如 `graphify`）提取中枢节点与调用链；提炼出的架构结论必须收敛至 Spec 或文档真源，其派生缓存（`graphify-out/`）删了可重建，不作为唯一真源。日常局部修改优先使用 `lsp` / `grep`，严禁滥用全量建图。

## 实现原则

- 先复用现有代码、标准库和已安装依赖；不为假想需求增加抽象、兼容层或配置。
- 修复共享根因，不在每个调用点重复打补丁。
- 尊重现有接口和数据；破坏性迁移必须在 Spec 中写明影响、回滚与验证。
- 配置、密钥和环境差异不得硬编码；示例配置只放占位值。
- 错误和阻断应可见，不用静默降级伪装成功。

## 测试与验证

- 非平凡逻辑先写或更新能复现预期的最小测试，再实现。
- 优先运行最贴近改动的检查；交付前再运行项目 `AGENTS.md` 指定的完整检查。
- 不宣称未实际运行的测试通过。无法运行时说明原因和剩余风险。
- 纯文档改动至少检查链接、命令、术语和规则冲突。

## Git 与外部操作

- 分支、提交和合并遵循项目局部规则；工作区不统一强制新建分支或自动提交。
- 未经明确授权，不拉取、推送、合并、部署、发布或向外部系统写入。
- 只提交本次任务文件，不覆盖、不清理无关改动。

## 文档与任务

- 架构、行为或配置发生变化时，更新其唯一真源；不要在多个 README、规则和 Spec 中复制同一段内容。
- 命名、交付文件和项目索引见 `项目运行规则.md`。
- Spec、任务状态和 Dashboard / Board-Platform 同步见 `开发项目联动规则.md`。
- 表达和图示见 `表达文风规则.md`；只有在图示显著提升理解时才使用。
