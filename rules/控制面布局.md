# 控制面布局

`.system/` 与 `.data/` 的物理布局、写入语义与来源映射。治理流程（演进准则、审计流程、自迭代 SOP）见 [`01_根系统治理.md`](01_根系统治理.md)；三权分立公理见 [`00_元规则.md`](00_元规则.md) 第 9 条。

## `.system/` 目录写入语义（禁止合并 root-configs 与 templates）

两者写入语义**相反**，合并会让「该覆盖」与「不该覆盖」躺在同一目录，是人工真源被误覆盖的温床：

| 目录 | 目标已存在时 | 消费方 |
|---|---|---|
| `root-configs/` | **删掉重写**（源是唯一真源，根副本是派生镜像）| `bootstrap.py sync_root_configs` |
| `templates/data/` | **跳过不动**（种子落地后实例成为真源）| `bootstrap.py` → `.data/templates/` |
| `templates/project/` | 跳过不动 | `init_project.py` / `init_app.py` |

`templates/` 按消费方分子目录，目录本身即白名单，不得再用硬编码文件名单分流。

## `.data/` 目录结构（路径即来源指针）

按**定义方**分三个桶，看路径就知道去哪找它的定义；`credentials/`（凭据）与 `docs/`（系统研究产物）独立，不参与映射。

| 桶 | 内容 | 对应关系（`lint` 第 20 项双向核验）|
|---|---|---|
| `templates/` | 模板渲染产物，与源模板同名 | `.data/templates/X` ⟺ `.system/templates/X.template.*` |
| `rules/` | 规则声明外置的实例数据，无模板 | 具体由哪条规则声明，见文件头 `source` 字段 |
| `skills/<名>/` | Skill 私有配置 | `.data/skills/<名>/` ⟺ `.system/skills/<名>/` |

新增实例文件必须先判定定义方再归桶；顶层散落文件、找不到对应模板的 `templates/` 文件、找不到对应 Skill 的 `skills/<名>/` 目录，均为体检告警项。

## `.data/` 写入规约（防人工真源被覆盖）

**文件一旦存在即视为人工真源**，任何写入方（工具、Skill、Agent）只允许字段级增量更新，**严禁整体重写、重新生成或"检测后重建"**。每个文件在 Front Matter（`.md`）或 `_meta`（`.json`）中声明 `source`/`managed_by`/`policy`——`merge-only`（只回填缺失字段）、`append-only`（只追加条目）、`regenerate-safe`（派生数据可重建）——由 `stamp_data_provenance.py` 加盖、`lint_workspace.py` 第 19 项核验。

**硬约束**：
1. 写入前必须先读取目标文件并检查 `policy`；无标记的按 `merge-only` 处理。
2. 标记为人工仲裁的条目（如 `file-opener.json` 中 `arbitrated: true`）任何情况下不得覆盖——**用户手工注册的程序通常不在模板候选列表里，一次"重新检测"就会把它冲掉**。
3. 全量重建须由用户显式指令触发（如 `--force-rescan-opener`），不得因初始化、自检或体检顺带执行。
4. 工具输出必须区分「检测到的候选」与「实际生效的配置」，二者混淆会诱导 Agent 去"修正"本来正确的配置。
