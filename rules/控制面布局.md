# 控制面布局

`.entropaxis/`（含其下嵌套的 `data/` 实例面）的物理布局、写入语义与来源映射。治理流程（演进准则、审计流程、自迭代 SOP）见 [`01_根系统治理.md`](01_根系统治理.md)；三权分立公理见 [`00_元规则.md`](00_元规则.md) 第 9 条。

`data/` 嵌套在 `.entropaxis/` 之内而非工作区根的兄弟目录：一是消除同一份实例数据「装了控制面就在里面、独立分发又要单独打包」的两套心智，二是让 `.gitignore` 只需锚定一处（`/data/`，见下）即可把全部实例数据、凭据挡在版本库外。**副作用**：`.entropaxis/` 内禁止执行 `git clean -x`/`git stash -a` 等会波及被忽略文件的命令，否则实例数据随之清空。

## `.entropaxis/` 目录职责

| 目录 | 内容 | 读者 |
|---|---|---|
| `rules/` | 规则正文（判据、门禁、归属）| 人与模型 |
| `config/` | 机器可读的控制面数据，由规则正文派生 | 工具 |
| `schemas/` | 结构化契约声明（字段集、取值域、必填项）| 工具 |
| `templates/` | 一次性种子（`instance/` 渲染到 `data/`，`project/` 是项目脚手架）| 工具 |
| `entrypoints/` | 根入口真源，物理同步到工作区根目录 | 人与模型 |
| `tools/` | 纯标准库 Python 工具 | 执行 |
| `skills/` | 多阶段 SOP 能力包 | 模型 |
| `tests/` | 单元测试与测试夹具 | 执行 |
| `data/` | 实例数据与凭据（`.gitignore` 排除，见下）| 人、工具、模型 |

`rules/` 只放 `.md`：机器可读数据归 `config/`，契约声明归 `schemas/`，混放会让规则体检（行数预算、复述检测）与机器解析互相误伤。

## 写入语义（禁止合并 entrypoints 与 templates）

两者写入语义**相反**，合并会让「该覆盖」与「不该覆盖」躺在同一目录，是人工真源被误覆盖的温床：

| 目录 | 目标已存在时 | 消费方 |
|---|---|---|
| `entrypoints/` | **删掉重写**（源是唯一真源，根副本是派生镜像）| `bootstrap.py sync_entrypoints` |
| `templates/instance/` | **跳过不动**（种子落地后实例成为真源）| `bootstrap.py` → `data/templates/` |
| `templates/project/` | 跳过不动 | `init_project.py` / `init_app.py` |

`templates/` 按消费方分子目录，目录本身即白名单，不得再用硬编码文件名单分流。`instance/` 此前曾叫 `data/`，与实例桶 `data/` 同名异义，遂改名消歧。

## `data/` 目录结构（路径即来源指针）

按**定义方**分三个桶，看路径就知道去哪找它的定义；`credentials/`（凭据）与 `docs/`（系统研究产物）独立，不参与映射。

| 桶 | 内容 | 对应关系（`lint` 第 20 项双向核验）|
|---|---|---|
| `templates/` | 模板渲染产物，与源模板同名 | `data/templates/X` ⟺ `.entropaxis/templates/instance/X.template.*` |
| `rules/` | 规则声明外置的实例数据，无模板 | 具体由哪条规则声明，见文件头 `source` 字段 |
| `skills/<名>/` | Skill 私有配置 | `data/skills/<名>/` ⟺ `.entropaxis/skills/<名>/` |

新增实例文件必须先判定定义方再归桶；顶层散落文件、找不到对应模板的 `templates/` 文件、找不到对应 Skill 的 `skills/<名>/` 目录，均为体检告警项。

## `data/` 写入规约（防人工真源被覆盖）

**文件一旦存在即视为人工真源**，任何写入方（工具、Skill、Agent）只允许字段级增量更新，**严禁整体重写、重新生成或"检测后重建"**。每个文件在 Front Matter（`.md`）或 `_meta`（`.json`）中声明 `source`/`managed_by`/`policy`——`merge-only`（只回填缺失字段）、`append-only`（只追加条目）、`regenerate-safe`（派生数据可重建）——由 `stamp_data_provenance.py` 加盖、`lint_workspace.py` 第 19 项核验标记完整性、第 19b 项核验声明的来源与写入者真实可兑现（声明了写入者却无人落笔，该真源在新环境永远是空壳）。

**硬约束**：
1. 写入前必须先读取目标文件并检查 `policy`；无标记的按 `merge-only` 处理。
2. 标记为人工仲裁的条目（如 `file-opener.json` 中 `arbitrated: true`）任何情况下不得覆盖——**用户手工注册的程序通常不在模板候选列表里，一次"重新检测"就会把它冲掉**。
3. 全量重建须由用户显式指令触发（如 `--force-rescan-opener`），不得因初始化、自检或体检顺带执行。
4. 工具输出必须区分「检测到的候选」与「实际生效的配置」，二者混淆会诱导 Agent 去"修正"本来正确的配置。

### 用户授权例外（策略不会自行放宽）

自动流程保护已有数据；用户明确指令允许定向修改。可重建数据按标记处理，归档数据按状态流转：

| 策略 | 默认行为 | 允许的例外 |
|---|---|---|
| `merge-only` | 保留已有值，只补缺失字段 | 用户明确要求时更新指定字段；全量重建需明确指定对象与范围 |
| `append-only` | 只追加，不修改已有条目 | 用户明确要求更正指定条目时可定向修改，并保留更正记录 |
| `regenerate-safe` | 对应工作流需要时，允许根据真源重新生成派生数据 | 重建前确认来源可用、文件确为派生数据；不顺带重建其他文件 |
| 人工选择的程序配置 | 自动检测、初始化和补填不得覆盖人工选择 | 用户明确改选时，只更新指定格式的程序映射 |

策略不会自行放宽：不得为了覆盖内容而把文件改标为 `regenerate-safe`。含人工维护内容的文件不能直接按纯派生数据重建；写入失败时保留原文件，不用半成品替换。例如：“重新检测打开程序”保留人工选择只补缺失配置；“以后 Markdown 用 Orca 打开”只更新 Markdown 映射，其他格式不变。
